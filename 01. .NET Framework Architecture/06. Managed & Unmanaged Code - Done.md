# Managed & Unmanaged Code

## Why This Boundary Matters

Every .NET program eventually touches the world outside the CLR — a Windows API, a performance library, hardware driver, or legacy COM component. Understanding where managed execution ends and native code begins is foundational for systems programming, interop work, and diagnosing hard-to-reproduce memory bugs. It explains why `IDisposable` exists, why `unsafe` is a reserved keyword, and why `Span<T>` was invented.

---

## 1. Managed vs Unmanaged Code — The Division

**Managed code** is any code that executes under CLR supervision. The CLR provides:

- **Garbage collection** — automatic memory reclamation; the GC tracks object roots and collects unreachable objects
- **Type safety** — the CLR verifies IL at JIT time; invalid casts and out-of-bounds accesses raise exceptions rather than silently corrupting memory
- **Structured exception handling** — `try/catch/finally` semantics are enforced across all managed call frames
- **JIT compilation** — IL is compiled to native machine code at runtime with platform-specific optimizations
- **Metadata** — every managed assembly carries a rich type description; reflection, attributes, and tooling all rely on it
- **Security** — code access security checks are enforced per assembly origin

**Unmanaged code** is native machine code running directly on the CPU outside CLR control — C/C++ DLLs, COM servers, Win32 API functions, hardware drivers. There is no GC, no type-safety net, and memory management is entirely manual. A single bad pointer can corrupt the process heap silently.

### When to Cross the Boundary

The BCL covers most OS services. You cross only when the BCL does not expose what you need:

- OS APIs not wrapped by the BCL (hardware interfaces, kernel objects, low-level system calls)
- High-performance native libraries (OpenSSL, FFmpeg, BLAS, libuv)
- COM automation servers built before .NET existed
- Hardware driver interfaces that demand raw memory layouts

### Transition Cost

Each managed-to-native crossing is not free. Every P/Invoke or COM call involves:

- **Marshaling** — argument types must be converted between managed and native representations
- **Execution context switch** — the CLR switches the thread from cooperative GC mode to preemptive GC mode at the crossing point, allowing the GC to run concurrently during the native call
- **GC lock coordination** — if the native call re-enters managed code via a callback, GC synchronization is required
- **Stack frame overhead** — the CLR pushes a transition stub frame so the unwind mechanism works correctly on exceptions

The crossing is deliberate, not accidental. Cross only for calls that justify the overhead.

| Aspect | Managed code | Unmanaged code |
|---|---|---|
| Memory management | GC automatic | Manual (`malloc`/`free`, OS handles) |
| Type safety | Enforced at runtime by CLR | None — pointer arithmetic is unchecked |
| Exception model | Structured (`try/catch/finally`) | OS SEH or C++ exceptions; must be translated |
| Debugging | Rich metadata + PDB symbols | Native debugger required (WinDbg, lldb) |
| Performance | JIT overhead; GC pauses | Predictable; no GC pauses |
| Portability | Cross-platform via CLR | Platform-specific binaries |
| Interop effort | Zero (internal BCL calls) | P/Invoke or COM interop required |

## 2. P/Invoke — Platform Invocation Services (Deep Theory)

P/Invoke is the CLR's mechanism for calling exported functions from unmanaged DLLs. The developer writes a `static extern` method annotated with `[DllImport]`; the CLR handles DLL loading, stub generation, marshaling, and the managed-to-native transition at each call site.

### How the CLR Generates a P/Invoke Stub

At JIT time, when the CLR first compiles a method containing a P/Invoke call, it generates a **native stub** — a short native function that performs the following steps on every call:

```
  Managed caller
       |
       ▼
  P/Invoke stub  (CLR-generated native thunk)
       |── marshal managed arguments to native form
       |── switch thread: cooperative GC mode → preemptive GC mode
       |── (GC may now run concurrently on other threads)
       ▼
  Native function (DLL export)
       |
       ▼
  P/Invoke stub  (return path)
       |── if SetLastError=true: capture GetLastError() immediately
       |── switch thread: preemptive GC mode → cooperative GC mode
       |── marshal return value and out/ref arguments back to managed form
       ▼
  Managed caller (resumes)
```

The cooperative/preemptive mode switch is essential: while the thread is in preemptive mode the GC treats it as suspended at a safe point and may run a collection. Without the mode switch, the GC would have to wait for every P/Invoke call to complete before collecting.

### Calling Conventions

The calling convention determines how arguments are placed on the stack and who cleans the stack after the call. A mismatch causes **stack corruption** — typically a crash or wrong results that only appear intermittently.

- `Cdecl` — caller cleans the stack; standard for C functions and variadic functions (`printf`-style)
- `StdCall` — callee cleans the stack; the standard convention for Win32 API functions
- `Winapi` — resolves to `StdCall` on 32-bit x86 Windows, unified ABI on x64; the correct choice for Win32 API calls on all Windows architectures
- `ThisCall` — the `this` pointer is passed in the `ecx` register; used for C++ instance methods; rarely needed in direct P/Invoke

On x64 (AMD64 and ARM64), the platform ABI is unified and the `Cdecl` vs `StdCall` distinction is irrelevant. On 32-bit x86, a convention mismatch causes real, silent stack corruption.

### `[DllImport]` Property Reference

| Property | Purpose | Important detail |
|---|---|---|
| `CallingConvention` | Stack argument convention | Default `Winapi`; always set explicitly for clarity |
| `CharSet` | String encoding | `Unicode` for modern APIs; `Ansi` for legacy; `Auto` for OS-native |
| `SetLastError` | Capture Win32 last-error | Must be `true` to call `Marshal.GetLastWin32Error()` reliably |
| `ExactSpelling` | Suppress A/W suffix probing | Set `true` when the function has no `A`/`W` variant |
| `EntryPoint` | Override native export name | Use when the managed method name differs from the export |
| `PreserveSig` | `HRESULT` conversion | `false` converts `HRESULT` failure to a thrown `COMException` |

### `SetLastError = true` — Why It Matters

Win32 last-error (`GetLastError()`) is a thread-local value. If the CLR executes any managed code before reading it, the CLR itself may overwrite it. Setting `SetLastError = true` instructs the stub to call `GetLastError()` as its very first operation on return from native code — before any managed execution — and save the value in a thread-local slot. Only then can `Marshal.GetLastWin32Error()` return the correct value. Without the attribute, the result is arbitrary.

### `[LibraryImport]` — Source-Generated P/Invoke (.NET 7+)

`[LibraryImport]` is the modern replacement for `[DllImport]`. The key difference is where the marshaling code lives:

- `[DllImport]`: the CLR generates the stub **at runtime** using the reflection-based interop marshaler. This is incompatible with AOT compilation and IL trimming because the marshaling logic is opaque to static analysis.
- `[LibraryImport]`: a Roslyn source generator emits the marshaling code as **ordinary C# at compile time**. The generated code is fully visible to the trimmer and the AOT compiler. No runtime stub generation occurs. The method must be declared `static partial`.

Example declaration (1 line of intent, generated code handles the rest):

    [LibraryImport("kernel32.dll", SetLastError = true)]
    static partial uint GetCurrentProcessId();

`[LibraryImport]` also accepts `[MarshalAs]` and `[MarshalUsing]` for custom marshaling and is the preferred form for all new code targeting .NET 7+.

### Blittable vs Non-Blittable Types

A **blittable** type has an identical in-memory representation in both managed and native code. Marshaling it requires only a memory copy — or in many cases just passing the pointer directly. A **non-blittable** type requires active conversion: allocating temporary native memory, copying and transforming data, then freeing the temporary memory on return. This conversion cost is why marshaling is not free.

**Blittable**: `byte`, `sbyte`, `short`, `ushort`, `int`, `uint`, `long`, `ulong`, `float`, `double`, `nint`, `nuint`, and any struct composed entirely of blittable fields with a fixed sequential layout.

**Non-blittable**: `string` (managed object with header and length field), `bool` (1-byte managed vs 4-byte Win32 `BOOL`), `char` (2-byte UTF-16 in CLR vs encoding-dependent in native), managed arrays (array header, bounds, type info), delegates (function pointer wrapper).

## 3. Marshaling — Type Conversion at the Boundary

Marshaling is the process of converting managed types to their native equivalents when data crosses the P/Invoke boundary, and converting native types back to managed equivalents on return. The CLR provides automatic marshaling for common type pairs; `[MarshalAs]` overrides the default when the native type differs from the managed default.

### Automatic Marshaling Rules

- `string` marshals to `LPWSTR` (UTF-16, null-terminated) by default on Unicode builds. Use `[MarshalAs(UnmanagedType.LPStr)]` for ANSI or `[MarshalAs(UnmanagedType.LPUTF8Str)]` for UTF-8.
- `bool` marshals to a 4-byte `BOOL` by default (Win32 convention: 0 = false, non-zero = true). Use `[MarshalAs(UnmanagedType.U1)]` for a 1-byte C++ `bool`.
- `int[]` marshals to `int*` with the array pinned for the duration of the call. Use `[MarshalAs(UnmanagedType.LPArray, SizeConst = N)]` to specify a fixed element count.
- `delegate` marshals to a native function pointer via a CLR-generated thunk. The delegate object must be kept alive (rooted in a GC-visible variable) for as long as the native code holds the pointer — if the delegate is collected, the thunk becomes dangling.

### `[StructLayout]` — Controlling Struct Memory Layout

For a struct to be passed safely to native code, its field layout must exactly match the native declaration. Three `LayoutKind` values control this:

- `LayoutKind.Sequential` — fields are laid out in declaration order, with default or specified padding (`Pack` property). Required for almost all native structs. The CLR still pads for natural alignment unless `Pack = 1` is specified.
- `LayoutKind.Explicit` + `[FieldOffset(n)]` — each field is placed at an explicit byte offset. Use this to model C unions (overlapping fields at offset 0) or structs with non-standard padding.
- `LayoutKind.Auto` — the CLR optimizes field placement for its own purposes, ignoring declaration order. This is the default for managed classes and is **never safe for P/Invoke** because the layout is unpredictable and not guaranteed between CLR versions.

`Marshal.SizeOf<T>()` returns the size of the **native** representation, which may differ from `sizeof(T)` in managed code because padding rules differ between the managed and native layouts.

### Pitfall: Passing `string` Where Native Code Writes Back

`string` is immutable in managed code. If a native function writes into a character buffer, passing a managed `string` is incorrect — the managed string object is not writable. Pass a `StringBuilder` with a pre-allocated capacity instead:

    var sb = new StringBuilder(256);
    GetWindowText(hwnd, sb, sb.Capacity);

The CLR marshals `StringBuilder` as a writable character buffer and updates its contents on return.

### Marshaling Type Reference

| Managed type | Default native type | Override attribute | Notes |
|---|---|---|---|
| `string` | `LPWSTR` (UTF-16) | `[MarshalAs(UnmanagedType.LPStr)]` | ANSI override for legacy APIs |
| `bool` | `BOOL` (4-byte int) | `[MarshalAs(UnmanagedType.U1)]` | 1-byte C++ `bool` override |
| `int[]` | `int*` (pinned) | `[MarshalAs(UnmanagedType.LPArray, SizeConst=N)]` | Fixed-length array |
| `delegate` | Function pointer | `[UnmanagedFunctionPointer(CallingConvention.Cdecl)]` | Keep delegate rooted for lifetime |
| `struct` | Inline by value | `[StructLayout(LayoutKind.Sequential)]` required | `Auto` layout is unsafe for P/Invoke |
| `StringBuilder` | `LPWSTR` (writable) | N/A — use instead of `string` for out buffers | `string` is immutable |

## 4. `unsafe` Code and Pointers

The `unsafe` keyword removes CLR type safety checks for a block, method, or class, enabling raw pointer types. It is necessary for direct memory manipulation, certain interop scenarios where native APIs require pointer arguments not expressible otherwise, and implementing low-level algorithms requiring pointer arithmetic.

### Enabling `unsafe` Code

The project must opt in explicitly in the `.csproj` file:

    <AllowUnsafeBlocks>true</AllowUnsafeBlocks>

This is a deliberate security boundary. `unsafe` code can corrupt the GC heap, produce dangling pointers, and bypass access checks in ways that ordinary managed code cannot.

### Pointer Types and Arithmetic

- `int*`, `byte*`, `char*`, `void*` — typed pointer to the respective element type
- `&x` — address-of operator; takes the address of a stack variable or a `fixed`-pinned variable
- `*p` — dereference; reads or writes the value at the pointer address
- `p + n` — pointer arithmetic; advances by `n × sizeof(*p)` bytes, not by `n` bytes

### `fixed` Statement — Pinning Managed Objects

Managed objects live on the GC heap, which is compacted periodically. Compaction moves live objects to consolidate free space, which invalidates any raw pointers into the heap. The `fixed` statement pins a specific object for the duration of its block, preventing the GC from relocating it:

    fixed (int* p = managedArray) { /* GC will not move managedArray here */ }

While an object is pinned the GC must work around it, introducing **heap fragmentation pressure**. Avoid long-lived `fixed` blocks and never pin inside a hot loop. `Span<T>` and `Memory<T>` exist largely to eliminate the need for `fixed`.

### `stackalloc` — Stack-Based Allocation

`stackalloc` allocates a contiguous block on the current thread's call stack, bypassing the GC heap entirely. In modern C#, assigning directly to `Span<T>` does not require `unsafe`:

    Span<byte> buffer = stackalloc byte[64];

Stack memory has no GC involvement and is reclaimed automatically when the method returns. The key constraint is **stack size**: typical thread stacks are 1 MB (4 MB for the main thread on Windows). Allocating more than a few kilobytes on the stack risks `StackOverflowException`. Prefer `ArrayPool<T>` for buffers larger than roughly 256–512 bytes.

### `nint` / `nuint` — Pointer-Sized Integers

`nint` and `nuint` are managed aliases for `IntPtr` and `UIntPtr`. They hold a value the size of a native pointer (4 bytes on 32-bit, 8 bytes on 64-bit) and support arithmetic operators without `unsafe`. They are the idiomatic type for native handle values and pointer-sized integers in interop code that does not need full pointer semantics.

### Memory Region Overview

```
  Stack (thread-local, ~1 MB default)
  ┌──────────────────────────────────────────┐
  │  stackalloc buffers                      │
  │  local value types (int, struct)         │
  │  unsafe pointers to stack variables      │
  └──────────────────────────────────────────┘

  GC Heap (managed by CLR GC)
  ┌──────────────────────────────────────────┐
  │  managed objects (classes, arrays)       │
  │  moved during GC compaction              │
  │  fixed pinned objects: GC works around   │
  └──────────────────────────────────────────┘

  Unmanaged Heap (Marshal.AllocHGlobal / native malloc)
  ┌──────────────────────────────────────────┐
  │  nint / IntPtr handles                   │
  │  native strings (LPWSTR)                 │
  │  NOT tracked by GC — must free manually  │
  └──────────────────────────────────────────┘
```

## 5. Span\<T\> and Memory\<T\> — Safe High-Performance Access

`Span<T>` and `Memory<T>` provide a unified, type-safe, bounds-checked abstraction over contiguous memory — whether that memory lives on the stack, the GC heap, or an unmanaged allocation — without copying the data. They are the modern answer to the question: how do you achieve pointer-level performance without raw pointers?

### `Span<T>` — The ref struct Constraint

`Span<T>` is a **ref struct**: a value type constrained to live only on the call stack. This constraint has precise implications:

- Cannot be boxed (stored as `object`)
- Cannot be stored in a regular class or struct field
- Cannot be used as a generic type argument in most contexts
- Cannot appear in `async` methods or `yield` iterator methods (these compile to heap-allocated state machines; a `Span` field would require heap storage, breaking the contract)

These restrictions exist because the CLR's verifier guarantees that a `Span<T>` never outlives the memory it points to. If `Span<T>` could be stored on the heap, a span over a `stackalloc` buffer could escape its stack frame, producing a dangling pointer. The ref struct constraint prevents this at compile time.

### Three Memory Sources for `Span<T>`

1. **Managed array**: `span = array.AsSpan()` — zero copy; the span holds a reference to the array object
2. **Stack allocation**: `Span<byte> s = stackalloc byte[128]` — no heap allocation; reclaimed when method returns
3. **Native pointer**: requires `unsafe`; use `MemoryMarshal.CreateSpan` to wrap a native pointer with a length

### `Memory<T>` — The Heap-Compatible Sibling

`Memory<T>` is a regular struct (not ref struct) that can be stored in class fields, passed across `await` boundaries, and used in async methods. It wraps the same kinds of memory as `Span<T>`. The trade-off is a small indirection: to perform span operations you call `.Span` on the `Memory<T>` instance, which costs one additional dereference per operation.

`IMemoryOwner<T>` extends `IDisposable` and represents ownership of a `Memory<T>` block — the pattern used for rented buffers that need explicit lifetime management.

### `MemoryMarshal` — Advanced Reinterpretation

`MemoryMarshal.Cast<TFrom, TTo>(span)` reinterprets a span's element type without any data copy or `unsafe` code:

    Span<int> ints = MemoryMarshal.Cast<byte, int>(byteSpan);

`Cast` enforces that both types are blittable and computes the resulting span length correctly. It is the idiomatic approach for parsing binary protocols and file formats.

### `ArrayPool<T>` — Avoiding Large Allocations

`ArrayPool<T>` maintains a shared pool of reusable arrays. Renting from the pool avoids allocating on the Large Object Heap (LOH) — objects over 85 KB go to the LOH, which is collected rarely and with full compaction overhead.

- `ArrayPool<byte>.Shared.Rent(minLength)` — returns an array at least `minLength` long; the actual array may be larger (next power of two or bucket size)
- `ArrayPool<byte>.Shared.Return(buffer)` — returns the array to the pool; always call in a `finally` block

**Pitfall**: `Rent()` returns dirty data from the previous use. Always initialize or fill the slice you will actually read before reading it. Pass `clearArray: true` to `Return()` only when the buffer contained sensitive data — it costs a `memset`.

### Type Reference Table

| Type | Ref struct (stack-only)? | Usable in async? | Memory source | Primary use case |
|---|---|---|---|---|
| `Span<T>` | Yes | No | Array, stack, native | Hot-path parsing, slicing, `stackalloc` buffers |
| `ReadOnlySpan<T>` | Yes | No | Array, stack, native, string literals | Read-only views, string parsing |
| `Memory<T>` | No | Yes | Array | Async pipelines, buffers stored in fields |
| `ReadOnlyMemory<T>` | No | Yes | Array, string | Async read-only access |
| `IMemoryOwner<T>` | No | Yes | Pool (ArrayPool) | Owned, disposable rented buffers |

## 6. IDisposable and Unmanaged Resource Cleanup

The GC manages managed heap memory but has **no knowledge of unmanaged resources**: OS file handles, database connections, socket descriptors, native memory allocations, COM object reference counts, OS mutex handles, and GPU resources. A class that acquires any of these must release them explicitly. `IDisposable` establishes the deterministic cleanup contract.

### The Dispose Contract

`IDisposable.Dispose()` is called by the consumer — directly or via a `using` statement — to release resources deterministically. The `using` statement compiles to a `try/finally` block that calls `Dispose()` even when an exception is thrown.

`IAsyncDisposable.DisposeAsync()` supports async cleanup (for example, flushing an async stream before closing it), used with `await using`.

### Why a Finalizer Exists

A finalizer (`~T()`) is a safety net. If a consumer forgets to call `Dispose()`, the GC will eventually call the finalizer on the dedicated **finalizer thread**. The finalizer cannot safely access managed objects (they may already have been collected), so it can only release native handles. Finalization adds latency: the object survives one extra GC cycle to be queued for finalization, then another cycle to be reclaimed after the finalizer runs. Relying on finalization for resource cleanup is never correct — `Dispose()` is the primary mechanism; the finalizer is a backstop.

### The Full Dispose Pattern

The canonical pattern separates deterministic disposal from finalizer-based cleanup using a `Dispose(bool disposing)` overload:

- `public void Dispose()` — called by consumers and `using` statements; calls `Dispose(true)` then `GC.SuppressFinalize(this)`
- `protected virtual void Dispose(bool disposing)` — performs the actual cleanup; `disposing = true` means a deterministic call (safe to access managed objects); `disposing = false` means the GC finalizer (managed objects may be collected — do not touch them)
- `~T()` — finalizer safety net; calls `Dispose(false)`

```
  Consumer calls Dispose() or using block ends
       │
       ▼
  public Dispose()
       ├─► Dispose(disposing: true)
       │       ├─ [disposing == true]  release managed IDisposable fields
       │       └─ [always]             release native handles; _disposed = true
       └─► GC.SuppressFinalize(this) ─► object removed from finalizer queue

  Consumer forgets Dispose()
       │
       ▼ (eventual GC cycle)
  Finalizer thread
       └─► ~T() ─► Dispose(disposing: false)
                       └─ [only native handles released; managed objects not touched]
                       └─ extra GC cycles consumed
```

**`GC.SuppressFinalize(this)`** removes the object from the finalization queue. If `Dispose()` was called, the finalizer is unnecessary. Without `SuppressFinalize`, every disposed object still goes through two extra GC cycles via the finalizer — wasted work that compounds under load.

**Idempotency**: `Dispose()` must be safe to call multiple times. Guard with a `bool _disposed` field and return immediately on subsequent calls. Throwing from `Dispose()` is an error — it breaks `using` blocks and `finally` cleanup chains.

### `SafeHandle` — The Preferred Handle Wrapper

`SafeHandle` is a CLR-provided base class for wrapping OS handles. It has several advantages over storing a raw `nint`:

- Its finalizer is a **critical finalizer** — guaranteed to run even during AppDomain unload or asynchronous thread abort
- It cooperates with P/Invoke marshaling: the runtime adds a ref count to the handle before a native call and releases it on return, preventing the GC from reclaiming the handle while the native call is in progress (a race called "handle recycling attack")
- `IsInvalid` and `IsClosed` properties provide reliable state queries

Built-in subclasses: `SafeFileHandle`, `SafeWaitHandle`, `SafeMemoryMappedViewHandle`, `SafeProcessHandle`. When your type holds an OS handle, derive from `SafeHandle` rather than storing a raw `nint`.

### `unsafe` vs `Span<T>` vs `Memory<T>` — Decision Guide

| Feature | `unsafe` + pointers | `Span<T>` | `Memory<T>` |
|---|---|---|---|
| GC safety | No — must `fixed` to pin heap objects | Yes — bounds checked | Yes — bounds checked |
| Stack-only (ref struct) | No | Yes | No |
| Store in class field | Yes | No | Yes |
| Use across `await` | No | No | Yes |
| Heap allocation overhead | Manual or none | None (`stackalloc` or slice) | Slice of array (no extra alloc) |
| Requires `unsafe` project setting | Yes | No (except native ptr source) | No |
| Native pointer as source | Yes | Yes (via `MemoryMarshal`) | No |
| When to use | C-level interop, custom allocators | Hot-path parsing, `stackalloc` buffers | Async pipelines, buffers in fields |

### Dispose Pattern — Canonical Template

```
public class MyResource : IDisposable
{
    private bool _disposed;

    public void Dispose()
    {
        Dispose(disposing: true);
        GC.SuppressFinalize(this);
    }

    protected virtual void Dispose(bool disposing)
    {
        if (_disposed) return;
        if (disposing)
        {
            // release managed IDisposable fields here
        }
        // release native handles / unmanaged memory here
        _disposed = true;
    }

    ~MyResource() => Dispose(disposing: false);
}
```
