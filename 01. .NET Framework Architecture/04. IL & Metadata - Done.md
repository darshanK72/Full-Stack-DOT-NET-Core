# IL & Metadata

## Why It Matters

Intermediate Language (IL) and metadata are the two inseparable halves of every .NET assembly. IL is the CPU-neutral instruction set that the CLR JIT-compiles to native machine code at runtime; metadata is the structured binary database that describes every type, method, field, parameter, and attribute that IL ever refers to. Together they enable the platform's four core promises: cross-language interoperability (a C# class looks identical from F# or VB.NET because they share the same metadata format), runtime reflection (an ORM inspects your entity properties without a code generator), late-binding extensibility (a DI container wires dependencies it has never seen at compile time), and ahead-of-time tooling (analyzers, source generators, and trimmer-safe serializers all parse metadata). Understanding IL and metadata is what separates a developer who uses the platform from one who can extend, debug, and optimize it.

## Section 1: What Is IL (Intermediate Language)?

### Definition and Naming

When the C# compiler (`dotnet build` / `csc.exe`) compiles source code it does not produce native machine code. It produces **Intermediate Language** — universally abbreviated **IL**. The same bytecode format has three historical names that mean exactly the same thing:

- **IL** — the common short form used throughout modern .NET documentation
- **MSIL** (Microsoft Intermediate Language) — the original .NET Framework name
- **CIL** (Common Intermediate Language) — the formal ECMA-335 specification name

All three refer to the same binary instruction set stored inside a .NET assembly. You will see all three in documentation and job interviews; treat them as synonyms.

### The Stack-Based Virtual Machine Model

IL is defined against a **stack-based virtual machine** — a conceptual CPU that has no named registers. All operations work exclusively through an **evaluation stack**: instructions push values onto the stack, and consuming instructions pop values off. This contrasts with register-based native code (x86/x64/ARM), where operations name registers explicitly (`mov eax, ebx`).

Consider `int Add(int a, int b) => a + b`. The C# compiler emits:

```
ldarg.0     // push argument 0 (a) → stack: [a]
ldarg.1     // push argument 1 (b) → stack: [a, b]
add         // pop a and b, push a+b → stack: [result]
ret         // pop result and return it → stack: []
```

The stack starts empty at method entry and must be empty at `ret` (except for the return value, which is on the stack when `ret` executes). The CLR verifier enforces this; a method whose stack is not consistent across all control paths fails verification.

### IL Is Not Interpreted

A common misconception is that IL is interpreted like Python bytecode. It is not. The CLR's **JIT compiler** translates each method's IL to native machine code the **first time** that method is called. Subsequent calls execute the cached native code directly — the IL is never executed again after the first JIT compilation. This is why startup latency (the cost of JIT) is the main IL-related performance concern, not per-instruction overhead.

### Where IL Lives

Each method body inside an assembly is stored as a raw opcode stream in the PE file's IL code section. The IL stream for a method is accessed at runtime through the `MethodBase.GetMethodBody()` API, which returns a `MethodBody` object. The `MethodBody.GetILAsByteArray()` call returns the raw bytes of the opcode stream — for example, the four-byte stream `02 03 58 2A` decodes as `ldarg.0`, `ldarg.1`, `add`, `ret`.

### Inspection Tools

| Tool | How to use | Best for |
|---|---|---|
| `ildasm.exe` | Ships with .NET Framework SDK; `ildasm MyAssembly.dll` | GUI disassembly of local assemblies |
| `dotnet-ildasm` | `dotnet tool install -g dotnet-ildasm` | Cross-platform CLI disassembly |
| SharpLab (sharplab.io) | Paste C# in browser, select "Results: IL" | Instant IL view for any snippet |
| ILSpy | Open-source GUI decompiler | IL + decompiled C# side-by-side |

SharpLab is the fastest way to understand what any C# construct compiles to. For example, `x++` on a local `int x` compiles to `ldloc.0, ldc.i4.1, add, stloc.0` — four instructions that make the performance implications concrete.

### Common IL Opcodes Reference

| Opcode | Meaning | Stack effect (→ = result pushed) |
|---|---|---|
| `nop` | No operation; debug breakpoint target | none |
| `ldarg.0` / `ldarg.1` | Push method argument 0 / 1 | → arg |
| `ldarg N` | Push method argument N (any index) | → arg |
| `ldc.i4.N` | Push small integer constant (−1 to 8, encoded in opcode) | → int |
| `ldc.i4` | Push any 4-byte integer constant | → int |
| `ldc.i8` | Push any 8-byte integer constant | → long |
| `ldc.r8` | Push 8-byte float constant | → double |
| `ldstr` | Push interned string literal from #US heap | → string ref |
| `ldnull` | Push null reference | → null |
| `ldloc.N` | Push local variable N | → value |
| `stloc.N` | Pop and store into local variable N | pops value |
| `dup` | Duplicate top of stack | → copy |
| `pop` | Discard top of stack | pops value |
| `add` | Pop two values, push sum | pops a,b → a+b |
| `sub` | Pop two values, push difference | pops a,b → a−b |
| `mul` | Pop two values, push product | pops a,b → a×b |
| `div` | Pop two values, push quotient | pops a,b → a÷b |
| `rem` | Pop two values, push remainder | pops a,b → a%b |
| `neg` | Negate top of stack | pops a → −a |
| `and` / `or` / `xor` | Bitwise operations | pops a,b → result |
| `shl` / `shr` | Shift left / right | pops val,amount → result |
| `ceq` | Compare equal; push 1 or 0 | pops a,b → 0/1 |
| `clt` / `cgt` | Compare less-than / greater-than; push 1 or 0 | pops a,b → 0/1 |
| `br` | Unconditional branch to label | pops nothing |
| `brtrue` / `brfalse` | Branch if top is nonzero / zero | pops condition |
| `beq` / `bne.un` | Branch if equal / not equal | pops a,b |
| `blt` / `bgt` / `ble` / `bge` | Signed comparison branches | pops a,b |
| `call` | Call a static or non-virtual method | pops args → return val |
| `callvirt` | Call a virtual method via vtable; includes null check | pops this+args → return val |
| `calli` | Call via unmanaged function pointer | pops ptr+args → return val |
| `newobj` | Allocate heap object, call constructor | pops ctor args → new ref |
| `box` | Wrap a value type in a heap-allocated object | pops val → object ref |
| `unbox.any` | Unwrap a boxed value type with type check | pops object ref → val |
| `castclass` | Cast reference type; throws `InvalidCastException` on failure | pops ref → typed ref |
| `isinst` | Test-cast; pushes null instead of throwing | pops ref → typed ref or null |
| `ldind.i4` / `stind.i4` | Load / store through a managed pointer | pointer dereference |
| `conv.i4` / `conv.i8` | Numeric type conversions | pops val → converted val |
| `ret` | Return from method (with return value on stack if non-void) | pops return val |
| `throw` | Throw exception on top of stack | pops exception ref |
| `leave` | Exit a protected region (try/catch/finally) cleanly | clears stack to exit |
| `endfinally` | End of a finally or fault clause | returns to calling handler |

### What C# Statements Look Like in IL

Understanding the mapping between C# constructs and IL reveals performance implications:

- `x++` (local int) → `ldloc.0`, `ldc.i4.1`, `add`, `stloc.0`
- `string s = "hi"` → `ldstr "hi"`, `stloc.0`
- `object o = 42` (boxing) → `ldc.i4 42`, `box System.Int32`, `stloc.0`
- `callvirt` is emitted for all instance method calls in C# (even on non-virtual methods) because it performs a null check; `call` is used for static calls and `base.Method()` calls

## Section 2: PE File Format and Assembly Structure

### The Portable Executable Container

A .NET assembly is a **Portable Executable (PE) file** — the same binary format used by all Windows `.exe` and `.dll` files since the Win32 era. The PE format predates .NET; Microsoft extended it with a CLR-specific header to embed IL, metadata, and resources while remaining a valid Windows executable. A .NET PE file can be loaded by both the Windows PE loader (for native headers) and the CLR runtime (for the CLR header and managed content).

### PE File Layout

```
+------------------------------------------+
|  MS-DOS stub (legacy "This program        |
|  cannot be run in DOS mode" message)      |
+------------------------------------------+
|  PE signature: "PE\0\0"                  |
+------------------------------------------+
|  COFF File Header                        |
|  (machine type, section count, etc.)     |
+------------------------------------------+
|  Optional Header (PE32 / PE32+)          |
|  - subsystem, stack/heap sizes           |
|  - data directory entries                |
|    [14] = CLR runtime header RVA+size    |
+------------------------------------------+
|  Section Table (array of section hdrs)   |
+------------------------------------------+
|  .text section                           |
|  +--------------------------------------+|
|  | CLR Header (IMAGE_COR20_HEADER)      ||
|  |  - CLR version required              ||
|  |  - metadata directory (RVA + size)   ||
|  |  - entry-point token                 ||
|  |  - resources directory               ||
|  |  - strong-name signature RVA         ||
|  |  - vtable fixups, flags              ||
|  +--------------------------------------+|
|  | IL code stream                       ||
|  |  (raw opcode bytes for all methods)  ||
|  +--------------------------------------+|
|  | Metadata section (#~)                ||
|  |  - metadata tables (see Section 3)   ||
|  |  - #Strings heap (type/member names) ||
|  |  - #US heap (user string literals)   ||
|  |  - #GUID heap                        ||
|  |  - #Blob heap (signatures, values)   ||
|  +--------------------------------------+|
+------------------------------------------+
|  .rsrc section (optional)                |
|  (embedded .resx, icons, images)         |
+------------------------------------------+
|  .reloc section (optional)               |
|  (base-relocation table for ASLR)        |
+------------------------------------------+
|  Native code section (R2R or NativeAOT)  |
|  (pre-compiled native code, if present)  |
+------------------------------------------+
```

### Key PE Structures

**IMAGE_COR20_HEADER** is the bridge between the Windows PE loader and the CLR. Its most important fields:

| Field | Purpose |
|---|---|
| `MajorRuntimeVersion` / `MinorRuntimeVersion` | Minimum CLR version required (usually 2.5) |
| `MetaData` (RVA + Size) | Points to the root of the metadata section |
| `EntryPointToken` | Metadata token of the entry-point method (`Main`) or zero |
| `Resources` (RVA + Size) | Points to embedded managed resources |
| `StrongNameSignature` | RVA of the strong-name signature blob (if signed) |
| `Flags` | `COMIMAGE_FLAGS_ILONLY` (pure IL), `COMIMAGE_FLAGS_32BITREQUIRED` (x86 only), etc. |

### Metadata Heaps

The metadata section contains four string/binary heaps in addition to the compact tables:

| Heap | Content |
|---|---|
| `#Strings` | Null-terminated UTF-8 strings for type names, member names, namespace names |
| `#US` (User Strings) | UTF-16 string literals used by `ldstr` instructions |
| `#GUID` | 16-byte GUIDs for module identity |
| `#Blob` | Variable-length binary data: method signatures, field types, constant values, custom attribute blobs |

Table rows do not embed strings directly — they store an offset (index) into the appropriate heap. This sharing means that two methods with the same name share one `#Strings` entry.

### Single-File vs. Multi-File Assemblies

- **Single-file assembly** (universal today): the manifest, metadata, and IL all live in one `.dll` or `.exe`. This is the only form produced by `dotnet build`.
- **Multi-file assembly** (legacy, .NET Framework only): one manifest assembly references satellite `.netmodule` files, each containing its own metadata and IL. The manifest `File` table lists them. This construct is effectively dead — .NET Core and .NET 5+ never supported it.

## Section 3: Metadata Tables

### What Metadata Is

Metadata is a compact binary database stored inside the PE file that describes everything about an assembly: every type it defines, every member those types contain, every other assembly it references, and every attribute applied to any element. The CLR reads metadata directly from the memory-mapped PE file — it does not copy or re-parse it after load. Metadata is **immutable at runtime** (you cannot edit the loaded file); the only way to create or modify metadata at runtime is through `System.Reflection.Emit`.

### Metadata Token Structure

Every row in every metadata table is identified by a **metadata token** — a 4-byte (`uint32`) integer with a precise structure:

```
Bits 31–24: table index (one byte)
Bits 23– 0: row number (three bytes, 1-based)
```

For example, token `0x02000003` means table `0x02` (TypeDef), row 3 — the third type defined in this assembly. These tokens appear throughout the IL opcode stream: a `call` instruction embeds the 4-byte token of the method it calls, and the CLR uses that token to look up the method's IL offset and JIT it. The `Type.MetadataToken`, `MethodInfo.MetadataToken`, and `FieldInfo.MetadataToken` properties expose these raw tokens through the Reflection API.

### The Major Metadata Tables

| Table name | Token prefix | What it holds | Primary use |
|---|---|---|---|
| `Module` | `0x00` | Current module's GUID and name | Module identity |
| `TypeRef` | `0x01` | References to types defined in other assemblies | Cross-assembly type resolution |
| `TypeDef` | `0x02` | Types defined in this assembly (classes, structs, interfaces, enums, delegates) | Core type registry |
| `FieldDef` | `0x04` | Fields belonging to types in this assembly | `FieldInfo` lookups |
| `MethodDef` | `0x06` | Methods belonging to types in this assembly; each row stores IL RVA | `MethodInfo` + JIT entry |
| `Param` | `0x08` | Method parameters: name, index, flags (in/out/optional) | `ParameterInfo` |
| `InterfaceImpl` | `0x09` | Maps TypeDef rows to the interfaces they implement | Interface dispatch |
| `MemberRef` | `0x0A` | References to methods and fields defined in other assemblies | Cross-assembly member calls |
| `CustomAttribute` | `0x0C` | Encoded attribute instances (parent token, ctor token, blob offset) | `GetCustomAttributes()` |
| `StandAloneSig` | `0x11` | Standalone method and locals signatures (used by `calli`) | Signature blobs |
| `Event` | `0x14` | Event definitions | `EventInfo` |
| `Property` | `0x17` | Property definitions | `PropertyInfo` |
| `MethodImpl` | `0x19` | Explicit interface method body mappings | Explicit interface impl |
| `ModuleRef` | `0x1A` | References to unmanaged DLLs (P/Invoke) | `DllImport` resolution |
| `TypeSpec` | `0x1B` | Generic type instantiations (e.g., `List<int>`) | Generic type resolution |
| `AssemblyDef` | `0x20` | This assembly's identity: name, version, culture, public key | `Assembly.GetName()` |
| `AssemblyRef` | `0x23` | Every other assembly this one depends on | Binding and loading |
| `ManifestResource` | `0x28` | Names and RVAs of embedded resources | `Assembly.GetManifestResourceStream()` |
| `GenericParam` | `0x2A` | Generic type and method parameters (`T`, `TKey`, etc.) | Generic reflection |
| `MethodSpec` | `0x2B` | Generic method instantiations (e.g., `Enumerable.Where<int>`) | Generic method dispatch |
| `DeclSecurity` | `0x0E` | CAS permission demands (legacy; effectively obsolete in .NET Core+) | Code Access Security |

### How the CLR Reads Metadata

When a method containing a `call 0x06000005` instruction is JIT-compiled, the JIT:

1. Reads the 4-byte token `0x06000005`
2. Extracts the table index `0x06` (MethodDef) and row `5`
3. Looks up row 5 in the MethodDef table to get the IL RVA (relative virtual address)
4. If the method has not yet been JIT-compiled, compiles it and stores the native code pointer
5. Patches the call site with the native address for future calls

This is why the first call to a method is slower than subsequent calls — step 4 can happen on any first call, not just the very first call in the program.

### Metadata vs. IL: Relationship

```
IL stream references:              Metadata resolves:
  call 0x06000005       ──────►    MethodDef row 5: IL RVA, name, flags
  newobj 0x060000A1     ──────►    MethodDef row 161: constructor body
  ldstr 0x70001234      ──────►    #US heap offset 0x1234: UTF-16 string
  isinst 0x02000003     ──────►    TypeDef row 3: type to check against
```

Every operand in the IL stream that names a type, method, or field is a metadata token. The token is the glue between the executable code and its description.

## Section 4: Reflection — Reading Metadata at Runtime

### What Reflection Is

**Reflection** is the ability to read the metadata tables at runtime and surface their contents as .NET objects. The Reflection API translates raw metadata rows into strongly-typed descriptors: `Assembly` (wraps AssemblyDef), `Module` (wraps Module table), `Type` (wraps TypeDef), `MethodInfo` (wraps MethodDef), `FieldInfo` (wraps FieldDef), `PropertyInfo` (wraps Property), `ParameterInfo` (wraps Param), and `ConstructorInfo` (a subclass of `MethodBase` pointing to a `.ctor` MethodDef row).

### Entry Points

Every reflection chain starts from a `Type` reference obtained in one of two ways:

- `typeof(SomeClass)` — resolved at JIT time to an internal type handle; this is the fastest path
- `instance.GetType()` — reads the method table pointer from the object header at runtime; needed for polymorphic dispatch

From a `Type` you navigate to members, then to parameters and custom attributes. From a `MethodInfo` you can reach the IL body through `GetMethodBody()`. The `Type.Assembly` property gives back the owning `Assembly`, from which you can enumerate all types or read resources.

### Core Reflection API

**Assembly-level APIs**

| API | Returns | Notes |
|---|---|---|
| `Assembly.GetExecutingAssembly()` | `Assembly` | The assembly containing the executing method |
| `Assembly.GetCallingAssembly()` | `Assembly` | The assembly that called the current method |
| `Assembly.Load(AssemblyName)` | `Assembly` | Load by identity; respects binding redirects |
| `assembly.GetTypes()` | `Type[]` | All types including private and nested |
| `assembly.GetExportedTypes()` | `Type[]` | Public types only |
| `assembly.GetName()` | `AssemblyName` | Name, version, culture, public key token |
| `assembly.Location` | `string` | File path on disk (empty for dynamic assemblies) |

**Type-level APIs**

| API | Returns | Notes |
|---|---|---|
| `type.GetMethods(BindingFlags)` | `MethodInfo[]` | Pass flags to include non-public / static / inherited |
| `type.GetMethod(name, BindingFlags)` | `MethodInfo?` | First match by name; ambiguous for overloads |
| `type.GetMethod(name, flags, null, types[], null)` | `MethodInfo?` | Resolve a specific overload by parameter types |
| `type.GetFields(BindingFlags)` | `FieldInfo[]` | Includes compiler-generated backing fields |
| `type.GetProperties(BindingFlags)` | `PropertyInfo[]` | Excludes backing fields |
| `type.GetConstructors(BindingFlags)` | `ConstructorInfo[]` | All constructors |
| `type.GetInterfaces()` | `Type[]` | All implemented interfaces (flat, includes inherited) |
| `type.BaseType` | `Type?` | Direct base class (`null` for `object` itself) |
| `type.IsGenericType` | `bool` | True for closed generics like `List<int>` |
| `type.GetGenericArguments()` | `Type[]` | Type arguments of a closed generic type |
| `type.MetadataToken` | `int` | Raw 4-byte TypeDef token (e.g., `0x02000003`) |

**Member invocation APIs**

| API | Returns | Notes |
|---|---|---|
| `methodInfo.Invoke(obj, args[])` | `object?` | Late-bound call; boxes all value-type args |
| `Activator.CreateInstance(type)` | `object?` | Calls default constructor |
| `Activator.CreateInstance(type, args[])` | `object?` | Matches constructor by arg types |
| `fieldInfo.GetValue(obj)` | `object?` | Reads field value; boxes value types |
| `fieldInfo.SetValue(obj, value)` | `void` | Writes field value |
| `propertyInfo.GetValue(obj)` | `object?` | Invokes getter |
| `propertyInfo.SetValue(obj, value)` | `void` | Invokes setter |

### BindingFlags

`BindingFlags` is a flags enum that filters which members are returned. The most useful combinations:

| Scenario | BindingFlags |
|---|---|
| Public instance members | `Public \| Instance` |
| Public static members | `Public \| Static` |
| All instance members including non-public | `Public \| NonPublic \| Instance` |
| Members declared on this type only (no inherited) | add `DeclaredOnly` |
| Everything | `Public \| NonPublic \| Instance \| Static` |

Without `DeclaredOnly`, `GetMethods()` returns inherited methods too — including all the `object` methods (`ToString`, `GetHashCode`, `Equals`, `GetType`). This is a common source of unintended results.

### The Reflection Performance Model

The first reflective access to a type causes the CLR to parse that type's metadata rows and build an internal cache of descriptor objects. Subsequent calls return cached descriptors — the metadata parse is paid only once per type per `AppDomain`. However, array allocation is not cached: every call to `GetMethods()` or `GetFields()` allocates a new array even though the underlying `MethodInfo` objects come from the cache. This is the primary performance concern.

A rough performance hierarchy for method dispatch:

```
Direct compiled call          ~1 ns     (baseline)
Delegate from Delegate.CreateDelegate   ~3–5 ns   (near-native after creation)
Compiled Expression tree       ~5–10 ns  (JIT-compiled lambda)
MethodInfo.Invoke             ~200–500 ns (boxing, arg array, metadata lookup)
```

`MethodInfo.Invoke` is approximately 100–200× slower than a direct call because it:
1. Allocates an `object[]` array for arguments
2. Boxes every value-type argument
3. Performs a per-call security check (in older runtimes)
4. Unboxes the return value

For hot-path dispatch, create a `Delegate` using `Delegate.CreateDelegate(typeof(Func<T,R>), methodInfo)` or compile an `Expression<Func<T,R>>` tree once and cache the resulting delegate.

### Key Pitfalls

- Never call `GetMethods()` / `GetFields()` in a tight loop — cache the array in a `static readonly` field
- `typeof(T)` is cheaper than `obj.GetType()` because it resolves at JIT time to a type handle constant
- `assembly.GetTypes()` materializes every `Type` in the assembly — use `GetExportedTypes()` when you only need public types, or use `System.Reflection.Metadata.MetadataReader` for zero-allocation enumeration in tooling scenarios

## Section 5: Custom Attributes — User-Defined Metadata

### Attributes as Metadata Annotations

A **custom attribute** is a class derived from `System.Attribute`. When you annotate a declaration with `[MyAttribute(arg)]`, the C# compiler:

1. Resolves the attribute class via metadata
2. Validates the call against `AttributeUsage` restrictions
3. Encodes the constructor arguments and named property values as a binary blob in the `#Blob` heap
4. Writes a row in the `CustomAttribute` table: (parent token, constructor MethodRef token, blob offset)

Critically, **the attribute object is never instantiated** at assembly load time or at any point unless code explicitly reads the attribute through Reflection. An attribute that is defined and applied but never read has exactly zero runtime cost.

### AttributeUsage

`[AttributeUsage]` is itself an attribute applied to attribute classes. Its three properties control the attribute's behavior:

| Property | Type | Meaning |
|---|---|---|
| `ValidOn` (first positional arg) | `AttributeTargets` | Flags enum: which declaration types are allowed (Class, Method, Property, Field, Assembly, etc.) |
| `AllowMultiple` | `bool` | Whether the same attribute can appear more than once on the same target (default: false) |
| `Inherited` | `bool` | Whether subclasses / overriding methods see the attribute through `GetCustomAttributes(inherit: true)` (default: true) |

If you apply an attribute where its `ValidOn` mask does not include that target, the compiler rejects it with a compile-time error — no runtime cost, no runtime check needed.

### Attribute Instantiation Timing

The `CustomAttribute` table row stores only the raw blob. When you call any of the read APIs, the CLR:

1. Finds the matching row(s) in the `CustomAttribute` table for the requested member token
2. Reads the blob: first two bytes are always `01 00` (prolog), followed by encoded constructor args, then named properties
3. Invokes the attribute constructor with the decoded arguments
4. Sets any named properties
5. Returns the resulting instance

This means attribute reading is lazy, per-call, and allocating. If you read the same attribute a thousand times in a loop, you instantiate it a thousand times.

### Three Read Patterns

| Pattern | API | When to use |
|---|---|---|
| Existence check (no instantiation) | `member.IsDefined(typeof(X), inherit)` | Cheapest: no attribute object created; just scans the table |
| Single attribute | `Attribute.GetCustomAttribute(member, typeof(X))` or `member.GetCustomAttribute<X>()` | When you expect at most one instance |
| All attributes | `member.GetCustomAttributes(typeof(X), inherit)` → `object[]` | When multiple instances are possible or you want all attributes |

`IsDefined` is the best choice for checking attribute presence in hot code paths because it reads only the table row tokens without deserializing the blob or constructing any object.

### The [Conditional] Attribute — Compile-Time, Not Runtime

`[System.Diagnostics.Conditional("DEBUG")]` applied to a method causes the **C# compiler** to omit all call sites to that method when the named compilation symbol is not defined. The mechanism is purely compile-time:

- The method still exists in the assembly and its IL is present
- The callers simply do not emit a `call` instruction for those call sites
- This is not runtime reflection behavior — it requires no attribute read at runtime

This is the canonical example of an attribute that communicates from one compilation unit to another through metadata, with zero runtime overhead.

### Attribute Use-Case Summary

| Attribute | Location | Read by |
|---|---|---|
| `[Obsolete]` | Any member | C# compiler (produces CS0618 warning) |
| `[DllImport]` / `[LibraryImport]` | `extern` static methods | CLR P/Invoke layer |
| `[Serializable]` | Classes | BinaryFormatter (legacy) / runtime type checks |
| `[JsonPropertyName]` | Properties | `System.Text.Json` serializer via reflection or source gen |
| `[Required]`, `[Range]`, `[MaxLength]` | Model properties | ASP.NET Core model validation via reflection |
| `[Authorize]` | Controller / action | ASP.NET Core filter pipeline via reflection |
| `[TestMethod]` / `[Fact]` | Test methods | Test runner via reflection |

## Section 6: Reflection.Emit — Writing IL at Runtime

### What Reflection.Emit Does

`System.Reflection.Emit` is a set of builder classes that allow you to construct brand-new metadata tables and IL opcode streams inside a running process without writing any source code. The generated assembly lives in memory (or optionally on disk in .NET 9+) and behaves identically to a compiler-produced assembly: its types can be instantiated, its methods called, and its IL JIT-compiled.

### The Builder Hierarchy

The classes mirror the logical structure of a PE assembly:

```
AssemblyBuilder     — the virtual assembly (wraps AssemblyDef + AssemblyRef tables)
  └─ ModuleBuilder  — the virtual module (wraps Module table, owns all tables)
       └─ TypeBuilder    — a type being defined (appends to TypeDef, FieldDef tables)
            ├─ FieldBuilder       — a field (appends to FieldDef)
            ├─ MethodBuilder      — a method (appends to MethodDef)
            │    └─ ILGenerator   — emits the IL opcode stream for the method
            └─ PropertyBuilder    — a property (appends to Property table)
```

You must call `TypeBuilder.CreateType()` to finalize a type — this validates the IL, resolves all internal cross-references, and produces the actual runtime `Type` object. After `CreateType()` the builder is frozen; no further modifications are allowed.

### ILGenerator API

`ILGenerator` is the central class for writing method bodies. Its primary methods:

| Method | Purpose |
|---|---|
| `Emit(OpCode)` | Emit a zero-operand instruction (`ret`, `add`, `ldarg.0`) |
| `Emit(OpCode, int)` | Emit instruction with 4-byte integer operand (`ldc.i4`) |
| `Emit(OpCode, string)` | Emit `ldstr` with a string literal |
| `Emit(OpCode, MethodInfo)` | Emit `call` / `callvirt` targeting a method |
| `Emit(OpCode, Type)` | Emit `newobj`, `castclass`, `isinst`, `box`, etc. |
| `Emit(OpCode, FieldInfo)` | Emit `ldfld` / `stfld` |
| `DeclareLocal(Type)` | Reserve a local variable slot; returns `LocalBuilder` |
| `DefineLabel()` | Allocate a branch target label |
| `MarkLabel(Label)` | Place the label at the current instruction position |
| `BeginExceptionBlock()` | Start a try block |
| `BeginCatchBlock(Type)` | Start a catch clause |
| `BeginFinallyBlock()` | Start a finally clause |
| `EndExceptionBlock()` | Close the try/catch/finally structure |

A minimal `Emit` sequence that returns a constant string:

```csharp
il.Emit(OpCodes.Ldstr, "Hello from emitted IL");
il.Emit(OpCodes.Ret);
```

### Real-World Use Cases

| User | What they emit | Why |
|---|---|---|
| Dapper | Per-type `IDataReader` → POCO materializer delegates | Avoid reflection per row; 10–50× faster than `GetValue()` |
| Entity Framework Core | Lazy-loading proxy types derived from entity classes | Override navigation properties transparently |
| Castle DynamicProxy / Moq | Proxy types that intercept all virtual method calls | AOP and test mocking |
| ASP.NET Core DI container | Compiled service factory delegates | Avoid `Activator.CreateInstance` overhead at scale |
| `Expression.Compile()` | Converts expression trees to delegates via Emit internally | Typed compiled lambda from runtime-constructed trees |

### PersistedAssemblyBuilder (.NET 9+)

Before .NET 9, `AssemblyBuilder.DefineDynamicAssembly` with `AssemblyBuilderAccess.Run` created an in-memory-only assembly that could not be saved to disk. `AssemblyBuilderAccess.Save` existed in .NET Framework but was never ported to .NET Core. In .NET 9, `PersistedAssemblyBuilder` was introduced as a new type that supports saving to a `.dll` file via `Save(string path)`. This is useful for generating assemblies during build workflows or ahead-of-time tool generation.

### NativeAOT Incompatibility

`Reflection.Emit` is entirely incompatible with NativeAOT publishing. NativeAOT compiles all IL to native code at publish time and strips the JIT compiler from the output. Without a JIT, there is no mechanism to compile dynamically emitted IL at runtime. Any library that uses `Reflection.Emit` internally (Castle DynamicProxy, some DI containers, some ORMs) requires rewriting for AOT compatibility. The alternative is **source generators** (Section 7) — they emit C# at compile time rather than IL at runtime.

## Section 7: Source Generators — Compile-Time Metadata Processing

### The Core Idea

A **Roslyn source generator** is a class that implements `IIncrementalGenerator` and runs as part of the `dotnet build` compilation pipeline. It receives the full Roslyn syntax tree and semantic model of the code being compiled, and it emits additional C# source files that are compiled into the same assembly along with the user's code. The generated files appear as `.g.cs` files under `obj/` and are fully visible to IntelliSense and the debugger.

This is fundamentally different from `Reflection.Emit`:

| Dimension | Source Generator | Reflection.Emit |
|---|---|---|
| When it runs | At compile time | At runtime |
| Output | C# source → IL via normal compiler | IL bytes directly |
| Debuggable | Yes (generated C# is in source) | No (raw IL, no C# mapping) |
| AOT compatible | Yes | No |
| Trimmer-safe | Yes | Requires explicit `[DynamicDependency]` annotations |
| Can react to runtime data | No | Yes |
| Output visible in IDE | Yes (`.g.cs` in obj/) | No |

### Incremental Generators

Modern generators implement `IIncrementalGenerator` rather than the older `ISourceGenerator`. The incremental API defines a **pipeline of transformations** over syntax nodes, each step declaring what it depends on. The build system caches each pipeline stage and only re-runs stages whose inputs have changed. This makes large-solution builds fast even with many active generators.

The pipeline pattern:

```
SyntaxProvider.CreateSyntaxProvider(predicate, transform)
  → filtered syntax nodes
  → semantic model lookups
  → code generation
  → RegisterSourceOutput(context, action)
```

Only the stages downstream of a changed file re-execute — unchanged methods in unchanged files contribute zero work.

### Real-World Source Generators in .NET

| Generator | Trigger attribute/API | What it replaces | Key benefit |
|---|---|---|---|
| `[GeneratedRegex]` | `System.Text.RegularExpressions` | `new Regex(pattern)` | Compiled DFA at build time; zero-allocation hot path |
| `JsonSerializerContext` | `System.Text.Json` | Runtime-reflection-based serializer | AOT-safe serialization; no `GetProperties()` at runtime |
| `[LoggerMessage]` | `Microsoft.Extensions.Logging` | `logger.LogInformation(...)` with string interpolation | Zero boxing, zero string allocation on non-matching log levels |
| `[LibraryImport]` | `System.Runtime.InteropServices` | `[DllImport]` | AOT-compatible P/Invoke with generated marshalling stubs |
| `[GeneratedComInterface]` | `System.Runtime.InteropServices` | `[ComImport]` + `[Guid]` | AOT-safe COM interop |

### Why Source Generators Beat Runtime Reflection for Common Cases

1. **Zero runtime overhead**: the generated code is compiled and JIT-compiled like any other code; there is no per-call metadata lookup
2. **AOT compatibility**: no runtime code generation needed; the output is plain IL in the assembly
3. **Trimmer safety**: the IL tree linker can see exactly which types and members are referenced by generated code and cannot trim them by mistake
4. **IDE integration**: generated code participates in IntelliSense, Go-to-Definition, and debugging; reflection-produced behavior is invisible to the IDE
5. **Compile-time errors**: a source generator can emit Roslyn diagnostics (errors and warnings) when it detects incorrect usage, surfacing problems at build time instead of as runtime exceptions

### The [GeneratedRegex] Example

`[GeneratedRegex(@"\d+")]` on a `static partial Regex Pattern()` method in a `partial` class instructs the generator to emit a class that derives from `Regex`, overrides the virtual `RunnerFactory`, and implements the full deterministic finite automaton (DFA) for the pattern as compiled C# code. The result: no regex parsing at startup, no interpreter overhead per character, and no allocations from pattern compilation. The generated `.g.cs` file is hundreds of lines of state-machine code that you never have to write or read.

### Reflection Performance Comparison

| Approach | Approximate cost | Notes |
|---|---|---|
| Direct compiled call | ~1 ns | Baseline |
| `delegate` via `Delegate.CreateDelegate` | ~3–5 ns | One-time cost to create; near-native dispatch |
| Compiled `Expression<T>` tree | ~5–10 ns | One-time compile cost; typed delegate result |
| `MethodInfo.Invoke` | ~200–500 ns | ~100–200× slower; boxes args, allocates array |
| `PropertyInfo.GetValue` | ~300–600 ns | Similar to Invoke; boxes value types |
| `assembly.GetTypes()` | ~50–500 µs | Proportional to type count; avoid in hot paths |

### Source Generator vs. Runtime Reflection Decision Guide

| Question | Prefer Source Generator | Prefer Reflection |
|---|---|---|
| Is the set of types known at compile time? | Yes | No |
| Do you need AOT / NativeAOT compatibility? | Yes | No (use reflection) |
| Is this a hot serialization / deserialization path? | Yes | Use compiled expressions |
| Do you need to process types from external plugins loaded at runtime? | No | Yes |
| Is the logic complex enough to justify a generator project? | Yes | No (reflection is simpler) |
