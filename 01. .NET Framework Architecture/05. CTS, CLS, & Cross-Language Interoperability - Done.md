# CTS, CLS, & Cross-Language Interoperability

## Why It Matters

The .NET platform's central promise is language neutrality: a class written in C# can be inherited in VB.NET, called from F#, and exposed to a COM client — without marshaling glue or duplicate declarations. That promise rests on two specifications the CLR enforces at every type boundary: the **Common Type System (CTS)** and the **Common Language Specification (CLS)**. Without them, each .NET language would have its own isolated runtime, and "interoperability" would mean manual bridges at every boundary.

Understanding CTS and CLS directly shapes how you design public APIs, how you diagnose boxing performance issues, how you trace mutable-struct bugs in collections, and how you integrate legacy COM components or native libraries into a modern .NET application.

## Section 1: Common Type System (CTS)

### What CTS Is

The **Common Type System** is the CLR's complete type catalog. It defines every kind of type that any .NET language may define or consume — the rules for how types are declared, how they relate to one another, how they are stored, and how they behave at runtime. Every type in every .NET language (C#, F#, VB.NET, IronPython, Eiffel.NET, and any third-party compiler targeting .NET) maps to exactly one CTS type. This single mapping is what makes a `System.Int32` in C# and a `Integer` in VB.NET the same binary entity at runtime: identical layout, same metadata representation in the PE file, same IL opcodes.

CTS is not a class library — it is a specification. The BCL (Base Class Library) is built on top of CTS, but CTS itself exists at the metadata and execution-engine level.

### The Type Hierarchy

Every CTS type is ultimately rooted at `System.Object`. This single root gives every type — regardless of language of origin — a guaranteed common set of behaviors: `ToString()`, `Equals()`, `GetHashCode()`, `GetType()`, and `MemberwiseClone()`.

The two major branches beneath `System.Object` are value types and reference types:

```
CTS Type Hierarchy
══════════════════════════════════════════════════════
System.Object
├── System.ValueType
│   ├── Primitive value types
│   │   ├── System.Boolean   (bool)
│   │   ├── System.Byte      (byte)
│   │   ├── System.SByte     (sbyte)
│   │   ├── System.Int16     (short)
│   │   ├── System.UInt16    (ushort)
│   │   ├── System.Int32     (int)
│   │   ├── System.UInt32    (uint)
│   │   ├── System.Int64     (long)
│   │   ├── System.UInt64    (ulong)
│   │   ├── System.Single    (float)
│   │   ├── System.Double    (double)
│   │   ├── System.Decimal   (decimal)
│   │   └── System.Char      (char)
│   ├── System.Enum
│   │   └── (any user-defined enum)
│   └── (any user-defined struct)
│
└── Reference types (directly under System.Object)
    ├── System.String
    ├── System.Array
    │   └── (T[], int[,], jagged arrays …)
    ├── System.Delegate
    │   └── System.MulticastDelegate
    │       └── (Action, Func, any custom delegate)
    ├── System.Exception
    │   └── (all exception hierarchy)
    └── User-defined types
        ├── (any class or abstract class)
        └── (any interface)
══════════════════════════════════════════════════════
```

### Important Subtleties in the Hierarchy

**Value types and the `System.ValueType` relationship at the IL level**

In C# source, `int` appears to inherit from `System.ValueType`, and `System.ValueType` inherits from `System.Object`. This is true at the metadata level — the CLR type system records this lineage. However, at the IL execution level, value types do not actually carry an object header or a vtable pointer when stored as their own type. The "inheritance" from `System.ValueType` is a metadata convention that enables the compiler and runtime to provide shared behavior (like `ToString()`) without a real inheritance chain in memory. The layout only becomes object-like when a value type is **boxed** — at that point the CLR creates a true heap object that wraps the value.

**C# keyword aliases map directly to CTS types**

C# keywords for primitive types are syntactic aliases — they are resolved by the compiler to the identical CTS type name. There is zero difference at the IL or runtime level:

| C# alias | CTS type |
|---|---|
| `int` | `System.Int32` |
| `long` | `System.Int64` |
| `bool` | `System.Boolean` |
| `string` | `System.String` |
| `object` | `System.Object` |
| `float` | `System.Single` |
| `double` | `System.Double` |
| `decimal` | `System.Decimal` |
| `char` | `System.Char` |
| `byte` | `System.Byte` |

**Delegate types**

A delegate definition in C# (`delegate string Transform(string s)`) compiles to a sealed class that inherits from `System.MulticastDelegate`. The compiler generates a constructor, an `Invoke` method, and `BeginInvoke`/`EndInvoke` stubs. A delegate is therefore a fully first-class CTS type — it can be stored in a variable of type `System.Object`, passed as a method argument, and reflected on at runtime.

**Interface types**

An interface in CTS is a pure contract — it specifies method signatures, property signatures, and (since C# 8 / .NET Core 3.0) default interface implementations, but it holds no instance state. Crucially, interfaces sit under `System.Object` in the hierarchy even though they do not explicitly inherit from it; any reference to an interface variable is still a reference type, and the CLR knows how to call `GetType()`, `ToString()`, etc. on it via the concrete implementing type's vtable.

## Section 2: Value Types vs Reference Types — Deep Comparison

### Storage Model

The most fundamental difference between value types and reference types is **where and how their data lives in memory**.

**Value types** store their payload inline — directly in the variable itself. If the variable is a local variable, the payload lives on the thread's stack. If the variable is a field of a class, the payload lives embedded inside that class's heap allocation. Value types are never independently heap-allocated in their unboxed form.

**Reference types** always allocate their payload on the managed heap. The variable holds a **reference** (a managed pointer) to that heap allocation. If the variable is a local variable, only the reference (4 or 8 bytes) sits on the stack; the actual object data is on the heap.

```
Stack                    Managed Heap
───────────────────────  ───────────────────────────────────────
int x = 42              │  (nothing — x is entirely on the stack)
  [ 42 ]                │
                        │
string s = "hi"         │  [ sync block | method table ptr | "hi" ]
  [ ref ─────────────── → object ]
                        │
Point p = new Point()   │  (nothing — p is entirely on the stack or inline in its owner)
  [ X=1 | Y=2 ]         │
```

### The Object Header

Every reference type instance on the managed heap begins with a **two-word object header** that precedes the user-visible fields:

- **Sync block index** (one pointer-sized word): used by the CLR's monitor lock mechanism (`lock` keyword / `Monitor.Enter`), and also repurposed for hash code caching when `GetHashCode()` is first called and the type does not override it.
- **Method table pointer** (one pointer-sized word): points to the type's **method table** (vtable equivalent). The method table holds the function pointers for all virtual and interface methods. When the CLR performs a virtual dispatch, it reads this pointer to find the correct implementation.

Value types in their unboxed form have neither header word. This is one reason value types cannot be null, cannot be locked on, and cannot participate in virtual dispatch without boxing.

### Assignment Semantics

**Value types copy the data.** Assigning `p2 = p1` where both are `Point` structs copies every byte of `p1`'s payload into `p2`. They are fully independent afterward — mutating `p2` has no effect on `p1`.

**Reference types copy the reference.** Assigning `b2 = b1` where both are class instances copies only the reference (the 4 or 8 byte pointer). Both variables now point to the same heap object. Mutating the object through `b2` is immediately visible through `b1`.

### Boxing and Unboxing

**Boxing** is the process of wrapping a value type in a `System.Object` reference-type shell so it can be stored on the heap and passed as an object reference. It is implicit in these situations:

- Passing a value type to a parameter of type `object` or `dynamic`
- Storing a value type in a non-generic collection (`ArrayList`, `Hashtable`)
- Calling a virtual method defined on `System.Object` (like `ToString()` via an `object` variable) on a value type
- Assigning a value type to an interface variable that it implements

Boxing always allocates a new heap object. The CLR copies the value type's payload into the new object's body and returns a reference. This means boxing creates **GC pressure** — tight loops that box frequently can trigger more frequent garbage collections.

**Unboxing** extracts the value back from the box. It requires an explicit cast, and the cast must name the *exact* type that was originally boxed. Unboxing to a different numeric type (e.g., unboxing an `int` as `long`) throws `InvalidCastException` even if the value would fit.

```
// Boxing:   int → object (heap allocation occurs)
object box = 42;

// Unboxing: object → int (must match original type exactly)
int val = (int)box;

// Wrong type throws at runtime:
long bad = (long)box;   // InvalidCastException — int ≠ long
```

### Default Values

Value types are always **zero-initialized** by the CLR — there is no such thing as an "uninitialized" value type field in a class. `int` defaults to `0`, `bool` defaults to `false`, a `struct` defaults to all its fields zero-initialized.

Reference types default to `null`. Attempting to dereference a null reference throws `NullReferenceException`.

### The Mutable Struct Pitfall

Retrieving a struct from a `List<T>` (or any indexer that returns by value) returns a **copy**, not the stored element. Modifying the copy does not modify the list element. The C# compiler detects the direct mutation pattern (`list[0].X = 10`) and issues **CS1612** ("Cannot modify the return value … because it is not a variable"). The fix is to retrieve the copy into a named variable, mutate it, then write it back.

```
// CS1612 — compile error:
points[0].X = 10;

// Correct pattern:
Point tmp = points[0];
tmp.X = 10;
points[0] = tmp;
```

### Comparison Table

| Aspect | Value Type | Reference Type |
|---|---|---|
| Storage | Inline (stack if local; embedded in owner if field) | Managed heap |
| Variable holds | The data itself | A reference (pointer) to heap data |
| Assignment | Copies the payload | Copies the reference |
| Object header | None (in unboxed form) | 2-word header (sync block + method table ptr) |
| Default value | Zero-initialized | `null` |
| Null by default | No (use `Nullable<T>` / `T?`) | Yes |
| GC participation | Only when boxed | Always |
| Virtual dispatch | No (sealed unless boxed) | Yes, via method table pointer |
| Inheritance | Only from `System.ValueType` (fixed) | Full class hierarchy |
| `lock` | Not permitted (no sync block) | Permitted |
| Typical C# keyword | `struct`, `enum`, primitives | `class`, `interface`, `delegate`, `record class` |

## Section 3: Common Language Specification (CLS)

### What CLS Is

The **Common Language Specification** is a *subset* of CTS rules. CTS defines everything the CLR can represent; CLS defines the minimum that all .NET languages must *understand* for a public API to be usable across every .NET language without special handling.

The distinction is important: CTS is broader than CLS. Features like unsigned integer types (`uint`, `ulong`), pointer types, and case-only-distinct identifiers are all valid CTS — the CLR supports them perfectly well. But not every .NET language exposes them. VB.NET has no unsigned integer literals. Many languages are case-insensitive. Therefore, CLS says: "if you want your public API to be callable from any .NET language, restrict your public surface to these safer types and naming rules."

### Scope: Public API Only

CLS rules apply **only to publicly visible members** — `public` and `protected` members of `public` types. Internal implementation details can freely use any CTS feature. A `private` method that takes a `uint` parameter is perfectly fine even in a `[CLSCompliant(true)]` assembly.

### Key CLS Rules

**Rule 1 — No unsigned integers in public signatures**

`uint`, `ulong`, `ushort`, and `sbyte` are not CLS-compliant in public APIs. The reason is that several .NET languages do not natively surface these types. Use `int`, `long`, `short`, and `byte` instead. For cases where a parameter must be non-negative, the convention is to document the constraint and throw `ArgumentOutOfRangeException` rather than using an unsigned type.

**Rule 2 — No case-only-distinct public member names**

Two publicly visible members whose names differ only by case violate CLS. VB.NET and certain other languages cannot distinguish `Process` from `process` or `Foo` from `foo`. This rule also extends to type names within a namespace.

**Rule 3 — No pointer types in public signatures**

Pointer types (`int*`, `void*`) are not CLS-compliant in public API. Use `ref`, `out`, `in`, or `Span<T>`/`ReadOnlySpan<T>` instead.

**Rule 4 — Identifier names**

CLS reserves leading underscores in identifiers as a tool-generated or implementation convention. Public identifiers starting with `_` are technically non-CLS-compliant.

**Rule 5 — Array element types must be CLS-compliant**

A public method that accepts or returns `uint[]` violates CLS even though arrays themselves are CLS-compliant.

**Rule 6 — Operator overloads must have named alternates**

Languages that do not support operator syntax (not all do) need a callable named method as an alternative. A public `operator +` should be accompanied by a named `Add()` method.

### CLS Compliance Attributes

- `[assembly: CLSCompliant(true)]`: instructs the C# compiler to emit **CS3001**, **CS3002**, and **CS3003** warnings whenever a `public` or `protected` member of a `public` type violates a CLS rule. Without this attribute, no warnings are emitted.
- `[CLSCompliant(false)]` on a specific member: explicitly marks that member as outside the CLS guarantee. The assembly-level warning is suppressed for that member. Use this when you need a non-CLS overload for performance reasons but still want to provide a CLS-compliant alternative alongside it.

### CLS Rules Summary Table

| Rule | Non-compliant example | CLS-compliant alternative |
|---|---|---|
| No unsigned integers | `public void Foo(uint x)` | `public void Foo(long x)` |
| No `sbyte` | `public sbyte Count` | `public short Count` |
| No `ulong` return | `public ulong GetSize()` | `public long GetSize()` |
| No case-only-distinct names | `public void Process()` and `public void process()` | Rename one distinctly |
| No pointer types | `public unsafe void Read(int* p)` | `public void Read(ref int p)` or `Span<int>` |
| Operator overloads must have named alternates | `operator +` only | Provide `public T Add(T other)` |
| Array elements must be CLS-compliant | `public uint[] GetIds()` | `public long[] GetIds()` |

## Section 4: Cross-Language Inheritance — How It Works

### The CTS Guarantee

Cross-language inheritance works because all .NET languages compile their types to **IL** (Intermediate Language) that conforms to the same CTS metadata format. When the CLR loads an assembly, it does not know — or care — which source language produced it. All it sees is a type defined by its metadata: the method table, the field layout, the virtual slot assignments, and the interface map.

A C# class and an F# class compiled to IL are indistinguishable to the CLR. Therefore, a subclass written in VB.NET can extend a base class written in C# with zero friction — the subclass simply names the base class by its full CTS type name in its metadata, and the CLR hooks up the vtable relationships normally.

### Virtual Dispatch Across Languages

When a virtual method is called, the CLR performs these steps regardless of the source language:

1. Read the **method table pointer** from the object's header (the second word of the object header).
2. Index into the method table at the slot corresponding to the virtual method.
3. Jump to the function pointer stored at that slot.

This mechanism is purely CLR-level. The language that defined the virtual method, and the language that overrides it, have no bearing on the dispatch. The override simply writes a new function pointer into the relevant vtable slot in the subtype's method table.

### Interface Contracts Across Languages

An interface defined in a C# assembly is, at the CTS level, simply a metadata record describing a set of method signatures with a unique type identity (a module + type token). Any other .NET language that references the assembly can implement that interface by writing the required method signatures and declaring the implementing type as implementing that interface in its own metadata. The CLR validates the contract at JIT time — it checks that the implementing type's method table satisfies every slot in the interface map.

This is why interface-based design is the idiomatic pattern for cross-assembly and cross-language extensibility in .NET: the interface is a pure CTS contract with no language-specific implementation detail. Concrete class inheritance across languages also works, but it is more tightly coupled to the exact method signatures and access modifiers, which are occasionally tricky between languages with different accessibility models.

### Practical Reality

Most modern .NET codebases that span multiple languages use **interface-based contracts** rather than concrete class inheritance for cross-assembly extensibility. Concrete inheritance across languages works, but it requires careful attention to:

- Access modifiers (`protected internal` behaves differently across language boundaries)
- Constructor chaining requirements (some languages require explicit base constructor calls, others assume a parameterless base constructor)
- Language-specific members (F# units of measure, VB.NET `WithEvents`, C# `partial` classes) that the other language may not be able to consume meaningfully

Interface-based design sidesteps all of these concerns because an interface imposes only method signatures — no inheritance chain, no constructor, no state.

## Section 5: COM Interoperability

### Background: What COM Is

**COM (Component Object Model)** is Microsoft's pre-.NET binary interoperability standard, introduced in the early 1990s. COM defines a binary interface protocol based on `IUnknown` (reference counting + `QueryInterface`) and optionally `IDispatch` (late-bound automation). COM is still widely used today:

- Office automation (Excel, Word, Outlook object models)
- Windows shell extensions and legacy Windows APIs
- ActiveX controls in older applications
- Various system-level COM servers (WMI, DirectX/Media Foundation legacy paths)

The CLR bridges .NET's garbage-collected world and COM's reference-counted world through two transparent proxy wrappers: the **Runtime Callable Wrapper (RCW)** and the **COM Callable Wrapper (CCW)**.

### Runtime Callable Wrapper (RCW)

When managed .NET code creates or receives a COM object, the CLR automatically generates an **RCW** — a managed class that stands between .NET code and the COM object.

```
.NET code
    │
    ▼
┌─────────────────────────────┐
│  Runtime Callable Wrapper   │  ← managed object on the GC heap
│  (generated by CLR)         │
│  - looks like a .NET object │
│  - wraps COM IUnknown ptr   │
│  - forwards calls to COM    │
└─────────────────────────────┘
    │
    ▼  (COM vtable calls)
┌─────────────────────────────┐
│  COM Object                 │  ← unmanaged; reference-counted
│  (unmanaged code / DLL)     │
└─────────────────────────────┘
```

The RCW presents the COM object as a normal .NET object to the caller. Under the hood, the RCW:
- Holds a single COM reference (AddRef) on behalf of all managed references to it
- Forwards method calls through the COM vtable
- Handles `HRESULT` → .NET exception translation (a failed `HRESULT` becomes a `COMException`)
- Is tracked by the GC — when the RCW is collected, the finalizer releases the COM reference

**Critical pitfall — non-deterministic release**

The GC finalizer does eventually call `Release()` on the underlying COM object, but GC timing is non-deterministic. COM servers (especially out-of-process ones like Excel) will stay alive until the GC collects the RCW. For Office automation and similar scenarios, you must call `Marshal.ReleaseComObject(rcw)` explicitly and then set the variable to `null`. This decrements the COM reference count immediately rather than waiting for the next GC.

### COM Callable Wrapper (CCW)

When COM code (or native code expecting a COM interface) needs to call a .NET object, the CLR generates a **CCW** — an unmanaged COM wrapper that presents the .NET object as a COM server with a fixed vtable.

```
COM / native client
    │
    ▼  (IUnknown / IDispatch vtable calls)
┌─────────────────────────────┐
│  COM Callable Wrapper       │  ← unmanaged vtable; reference-counted
│  (generated by CLR)         │
│  - exposes IUnknown vtable  │
│  - translates COM calls     │
│    into managed calls       │
└─────────────────────────────┘
    │
    ▼  (managed dispatch)
┌─────────────────────────────┐
│  .NET Object                │  ← on the managed GC heap
└─────────────────────────────┘
```

The CCW bridges two memory management models: COM's reference counting and .NET's GC. The CCW itself is reference-counted (COM clients call `AddRef`/`Release` on the CCW). As long as any COM client holds a reference to the CCW, the GC is prevented from collecting the underlying .NET object. When the last COM client releases the CCW, the .NET object becomes eligible for collection.

### Key COM Interop Attributes

| Attribute | Where applied | Purpose |
|---|---|---|
| `[ComImport]` | Interface or class declaration | Marks the type as defined in an existing COM type library, not in managed code |
| `[Guid("...")]` | Interface, class, or struct | Associates the .NET type with its COM GUID (IID for interfaces, CLSID for classes) |
| `[InterfaceType(ComInterfaceType.InterfaceIsIUnknown)]` | Interface | Specifies the COM vtable base: `IUnknown` (pure vtable), `IDispatch` (late-bound), or `IDispatchAndIUnknown` (dual) |
| `[ComVisible(false)]` | Type or assembly | Prevents the CLR from generating a CCW for the type; hides it from COM client view and tlbexp |
| `[ClassInterface(ClassInterfaceType.None)]` | Class | Suppresses the auto-generated class interface; requires the class to implement explicit interfaces for COM exposure |

### Wrapper Comparison Table

| Wrapper | Direction | Created by | Manages COM lifetime? | Use case |
|---|---|---|---|---|
| RCW | .NET → COM | CLR, automatically | No — must call `Marshal.ReleaseComObject()` | Calling Office automation, legacy COM servers |
| CCW | COM → .NET | CLR, automatically | N/A (GC keeps .NET object alive while CCW is referenced) | Exposing a .NET class as a COM server |

## Section 6: P/Invoke — Platform Invocation Services

### What P/Invoke Is

**P/Invoke (Platform Invocation Services)** is the CLR mechanism that lets managed .NET code call functions exported from unmanaged native DLLs — Win32 API functions, C runtime functions, or any function exported from a DLL using the C calling convention. P/Invoke handles the transition between the managed execution environment (with its heap, GC, and type safety) and the native world (raw memory, pointers, C types).

P/Invoke is distinct from COM interop: COM goes through vtable dispatch and `IUnknown`; P/Invoke goes through flat DLL exports by name or ordinal.

### How a P/Invoke Declaration Works

A P/Invoke call is declared as a `static extern` method on a class, decorated with `[DllImport("library.dll")]`. There is no method body — the method body lives in the native DLL. At the first call, the CLR:

1. Locates and loads the named DLL (searching a platform-defined set of paths)
2. Resolves the exported function symbol
3. Generates a **managed-to-native stub** (a small piece of JIT-generated code that performs the transition)
4. Patches the call site to jump through the stub on subsequent calls

The stub is responsible for **marshaling** — converting each managed argument to its native equivalent before the call, and converting the native return value back to a managed type after the call.

```
// Minimal P/Invoke declaration:
[DllImport("kernel32.dll")]
static extern uint GetCurrentProcessId();
```

### `[DllImport]` Properties

`[DllImport]` accepts several named parameters that control marshaling and runtime behavior:

| Property | Type | Purpose | Default |
|---|---|---|---|
| `EntryPoint` | `string` | Name (or ordinal `"#42"`) of the native export, if different from the method name | Same as the method name |
| `CallingConvention` | `CallingConvention` | How arguments are pushed and who cleans the stack (`Cdecl`, `StdCall`, `Winapi`) | `Winapi` (same as `StdCall` on Windows) |
| `CharSet` | `CharSet` | String encoding for `string` and `char` parameters: `Unicode` (UTF-16), `Ansi` (code page), `Auto` (platform-dependent) | `Ansi` (historically; `Unicode` is almost always correct on modern Windows) |
| `SetLastError` | `bool` | Whether the CLR captures the Win32 `GetLastError()` value after the call, allowing `Marshal.GetLastWin32Error()` to return the correct value | `false` |
| `ExactSpelling` | `bool` | Prevents the CLR from appending `A`/`W` suffixes when searching for the export (Win32 ANSI/Unicode naming convention) | `false` |

### Calling Conventions

The calling convention governs two things: the order arguments are pushed onto the native stack, and who is responsible for cleaning up the stack after the call (the caller or the callee).

| Convention | Who cleans stack | When to use |
|---|---|---|
| `Cdecl` | Caller | C runtime functions; variadic functions (`printf`) |
| `StdCall` | Callee | Most Win32 API functions |
| `Winapi` | Same as `StdCall` on Windows, `Cdecl` on Unix | Default; correct for most Windows API calls |
| `ThisCall` | Callee (except last arg) | C++ non-static member functions (rare in P/Invoke) |

**Pitfall**: using the wrong calling convention causes stack corruption. On x86 (32-bit) this produces immediate crashes or stack imbalance exceptions. On x64 the Windows calling convention is a single unified ABI, so `CallingConvention` is less critical — but it is still good practice to specify it correctly for portability.

### String Marshaling

Strings are a common source of P/Invoke bugs:

- `string` parameters are marshaled as `LPCWSTR` (pointer to constant wide string) by default when `CharSet = CharSet.Unicode`. They are marshaled read-only — the CLR pins the managed string and passes its address.
- If the native function **modifies** the buffer (i.e., writes back into it), you must use `StringBuilder` instead of `string`. The CLR pre-allocates a native buffer for `StringBuilder`, lets the native function fill it, then copies the result back into the managed `StringBuilder`.
- `[MarshalAs(UnmanagedType.LPStr)]` explicitly controls the encoding of a single parameter, overriding the `CharSet` default.

**Pitfall**: forgetting `SetLastError = true` means calling `Marshal.GetLastWin32Error()` after the P/Invoke returns stale data — the CLR may have internally called other Win32 functions that overwrote `GetLastError`'s thread-local value. Always set `SetLastError = true` when the native function uses `GetLastError`/`SetLastError`.

### Struct Layout for P/Invoke

When passing a struct to a native function (e.g., `POINT`, `RECT`, `SYSTEMTIME`), the CLR must lay out the struct's fields in memory to match the native struct exactly. The default managed layout may reorder or pad fields differently from the native definition.

- `[StructLayout(LayoutKind.Sequential)]`: lay out fields in declaration order, with default platform alignment. This is the correct layout for most C structs.
- `[StructLayout(LayoutKind.Explicit)]` with `[FieldOffset(n)]` on each field: explicitly specify each field's byte offset. Used for C unions or packed structs.
- `[MarshalAs(UnmanagedType.ByValTStr, SizeConst = N)]` on a string field inside a struct: marshal it as an inline fixed-length character array.

### `[LibraryImport]` — The Modern Alternative (.NET 7+)

`[LibraryImport]` is a source-generator-based replacement for `[DllImport]`, introduced in .NET 7. At compile time, the source generator emits the marshaling stub as regular C# code, rather than having the CLR generate it at runtime via reflection.

Benefits over `[DllImport]`:
- **Trimmer-safe**: the marshaling code is explicit C# that the IL linker can analyze, so it is not excluded by trimming.
- **AOT-compatible**: since the stub is pre-generated C# rather than runtime IL generation, it works with NativeAOT.
- **Debuggable**: the generated stub is inspectable C# code, not a runtime-generated thunk.
- **Performance**: avoids the first-call JIT cost of the dynamic stub.

For new .NET 7+ code, prefer `[LibraryImport]` over `[DllImport]`. The analyzer CA1416 and CA1838 guide migration.

### P/Invoke Common Pitfalls

| Pitfall | Symptom | Fix |
|---|---|---|
| Wrong calling convention | Stack corruption, crashes, `AccessViolationException` | Match the native function's convention exactly |
| `string` used where native function writes back | Corrupted data or crash | Use `StringBuilder` for output string parameters |
| Forgot `SetLastError = true` | `Marshal.GetLastWin32Error()` returns 0 or wrong code | Add `SetLastError = true` to `[DllImport]` |
| Struct layout mismatch | Wrong field values, memory corruption | Apply `[StructLayout(LayoutKind.Sequential)]` and verify alignment |
| No platform guard on Windows-only DLL | `DllNotFoundException` on Linux/macOS at call site | Wrap in `if (RuntimeInformation.IsOSPlatform(OSPlatform.Windows))` |
| Native function holds a callback delegate but managed GC collects it | Crash in the callback | Pin the delegate with `GCHandle.Alloc()` or keep it in a static field |

## Quick Reference

### CTS Type Hierarchy (ASCII)

```
System.Object
├── System.ValueType
│   ├── Primitives: bool · byte · sbyte · short · ushort · int · uint
│   │              long · ulong · float · double · decimal · char
│   ├── System.Enum  →  (any user-defined enum)
│   └── User structs →  (any struct defined with the struct keyword)
└── Reference types (directly from Object)
    ├── System.String
    ├── System.Array          →  T[], int[,], jagged
    ├── System.Delegate       →  System.MulticastDelegate
    │                            → Action, Func, custom delegates
    ├── System.Exception      →  all exception hierarchy
    └── User-defined          →  class, abstract class, interface
```

### Value Type vs Reference Type

| Aspect | Value Type | Reference Type |
|---|---|---|
| Storage | Inline (stack or embedded) | Managed heap |
| Variable holds | The data | A reference (pointer) |
| Assignment | Copies data | Copies reference |
| Object header | None (unboxed) | Sync block + method table ptr |
| Default | Zero-initialized | `null` |
| Null possible | No (`T?` / `Nullable<T>` adds it) | Yes |
| Lockable | No | Yes |
| Virtual dispatch | No (without boxing) | Yes |
| GC tracked | Only when boxed | Always |

### CLS Rules Summary

| Rule | Non-compliant | CLS-compliant alternative |
|---|---|---|
| No unsigned integer in public API | `public void Foo(uint x)` | `public void Foo(long x)` |
| No `sbyte` in public API | `public sbyte Count` | `public short Count` |
| No case-only-distinct public names | `Foo()` and `foo()` both public | Rename to be clearly distinct |
| No pointer types in public API | `public unsafe void Read(int* p)` | `public void Read(ref int p)` |
| Operator overloads need named alternates | `operator +` only | Add `public T Add(T other)` |
| Array elements must be CLS-compliant | `public uint[] GetIds()` | `public long[] GetIds()` |

### Interop Mechanism Comparison

| Mechanism | Direction | How | Runtime support | Best for |
|---|---|---|---|---|
| P/Invoke (`[DllImport]`) | .NET → native DLL export | `static extern` declaration | CLR marshaling stub | Win32 API, C libraries, C-style exports |
| `[LibraryImport]` (.NET 7+) | .NET → native DLL export | Source-generated stub | AOT-safe, trimmer-safe | Same as P/Invoke; preferred for new code |
| COM RCW | .NET → COM object | CLR auto-generates managed proxy | CLR, reference counting bridged | Office automation, legacy COM servers |
| COM CCW | COM client → .NET object | CLR auto-generates COM vtable | CLR, prevents GC while COM holds ref | Exposing .NET as a COM server |
| C++/CLI | .NET ↔ native C++ | Mixed-mode assembly | Both CLR and native runtime | Wrapping C++ classes as .NET types |
| `unsafe` + pointers | .NET internal | Compiler `unsafe` context | No interop layer needed | Low-level memory ops within one process |
