# .NET Platform & Evolution

## Why It Matters

Every .NET developer encounters projects that span .NET Framework 4.x legacy codebases and modern .NET 8/10 services simultaneously. Knowing the platform's evolution lets you read a `.csproj` file at a glance, explain LTS support windows to stakeholders, choose the right runtime flavor for a deployment scenario, and make confident decisions about library targeting and migration paths. These topics appear in virtually every .NET technical interview.

## What You Will Learn

1. The full .NET version timeline from .NET Framework 1.0 (2002) through .NET 10 (2025) and the LTS/STS cadence
2. Target Framework Monikers (TFMs) — what they are, how to read them, and how they drive preprocessor guards
3. .NET Standard — what problem it solved, its limits, and why modern code targets `net10.0` instead
4. The three runtime flavors: CoreCLR, Mono, and NativeAOT, and when each is appropriate
5. NuGet package management — `PackageReference`, Central Package Management, and dependency resolution
6. Modern SDK-style `.csproj` features: nullable reference types, implicit usings, top-level statements, and multi-targeting

## 1. .NET Timeline & Version History

### Three Eras of .NET

The .NET platform has passed through three distinct eras, each with a different mission and target audience.

**Era 1 — .NET Framework (2002–2019)**
.NET Framework was Microsoft's original managed runtime. It was Windows-only by design, shipped as a redistributable component tied to the Windows OS, and was patched via Windows Update. Versions accumulated gradually from 1.0 through 4.8, with each version adding APIs and language features while maintaining strict backward compatibility. Starting from .NET Framework 4.0, each release was an in-place upgrade — multiple Framework versions could be installed side-by-side (e.g., 3.5 and 4.8 coexist), but apps within the 4.x family all shared a single CLR version. Since 4.8, .NET Framework has been in maintenance mode: Microsoft ships security patches but will never release a version 5 under the Framework brand. It remains in Windows because removing it would break enormous volumes of enterprise software.

**Era 2 — .NET Core (2016–2019)**
.NET Core was a ground-up, open-source rewrite of the runtime designed for cross-platform deployment (Windows, Linux, macOS). It introduced true side-by-side versioning — multiple major versions can run on the same machine independently — and a modular NuGet-first packaging model where the framework itself ships as packages. The ASP.NET Core stack was a complete redesign that could serve tens of thousands of requests per second on Linux. .NET Core 3.1 was the final release under the "Core" brand and remained a popular LTS target until its end-of-life in December 2022.

**Era 3 — Unified .NET (2020–present)**
.NET 5 (November 2020) merged .NET Framework's capabilities and .NET Core's cross-platform architecture under a single brand. The "Core" and "Framework" suffixes were dropped. The number skipped from 3.1 to 5 specifically to avoid confusion with the non-existent ".NET 4.x" (which could be mistaken for ".NET Framework 4.x"). An annual November release cadence was established: even-numbered versions are **Long Term Support (LTS)** with three years of support; odd-numbered versions are **Standard Term Support (STS)** with 18 months. The current LTS release is **.NET 10** (November 2025, EOL November 2028).

### Version Table

| Version | Release Year | EOL | Type | Key Milestone |
|---|---|---|---|---|
| .NET Framework 1.0 | 2002 | Maintenance | — | First managed runtime |
| .NET Framework 2.0 | 2005 | Maintenance | — | Generics introduced |
| .NET Framework 3.5 | 2007 | Maintenance | LTS | LINQ, WCF, WPF |
| .NET Framework 4.5 | 2012 | Maintenance | — | `async`/`await` |
| .NET Framework 4.8 | 2019 | No set EOL | Final Framework | Last Framework version ever |
| .NET Core 1.0 | 2016 | Jun 2019 | STS | Cross-platform rewrite |
| .NET Core 2.1 | 2018 | Aug 2021 | LTS | Span, `IAsyncEnumerable` |
| .NET Core 3.1 | 2019 | Dec 2022 | LTS | WPF/WinForms on Core |
| .NET 5 | Nov 2020 | May 2022 | STS | Unified brand; no "Core" |
| .NET 6 | Nov 2021 | May 2024 | LTS | Hot reload, minimal APIs |
| .NET 7 | Nov 2022 | May 2024 | STS | Native AOT, rate limiting |
| .NET 8 | Nov 2023 | Nov 2026 | LTS | Keyed DI, `TimeProvider` |
| .NET 9 | Nov 2024 | May 2026 | STS | `SearchValues`, LINQ new ops |
| **.NET 10** | **Nov 2025** | **Nov 2028** | **LTS (current)** | **Target for new projects** |

### LTS vs. STS Decision Rule

For long-lived enterprise applications, always target LTS (even-numbered) versions — 6, 8, 10 — to avoid a forced upgrade within 18 months. STS versions (7, 9) are appropriate for projects that want cutting-edge features and can absorb upgrades on the faster cadence.

### Key Pitfalls

- There is no such thing as ".NET 4.8". The unified platform jumped from .NET Core 3.1 to .NET 5 precisely to avoid confusion with ".NET Framework 4.8". Any mention of ".NET 4" in modern context refers to .NET Framework.
- .NET Framework applications cannot run on Linux or macOS. Cross-platform deployment requires .NET 5 or later.
- .NET Framework 4.8 is not "dead" — it still receives security patches and will remain available on Windows indefinitely. However, it receives no new language features or performance improvements.
- .NET Core 3.1 reached end-of-life in December 2022. Running EOL runtimes means no security patches.

## 2. Target Framework Monikers (TFM)

### What a TFM Is

A **Target Framework Moniker** is the string placed in the `<TargetFramework>` element of a `.csproj` file. It is a contract declaration: it tells the SDK which platform API surface to compile against, which NuGet assets to restore, which preprocessor constants to define, and — for OS-specific TFMs — which platform-native APIs are available.

TFMs are not just metadata. The build system physically selects different reference assemblies, enables different language features, and includes different NuGet package assets depending on the active TFM.

### TFM Format Rules

```
net{version}              → Cross-platform .NET (any OS)
net{version}-{os}         → OS-specific variant (restricts portability)
netstandard{version}      → API specification (compatibility bridge)
net{major}{minor}         → .NET Framework (e.g., net48, net472)
```

Examples:
- `net10.0` — Modern .NET 10, any OS
- `net10.0-windows` — Modern .NET 10, Windows-only (WinForms, WPF, Registry APIs)
- `net10.0-android` — Modern .NET 10, Android-only (.NET MAUI)
- `net48` — .NET Framework 4.8, Windows-only
- `netstandard2.0` — Compatibility specification (see Section 3)

### TFM Comparison Table

| TFM | Platform | Supports .NET Framework consumers? | Supports .NET Core/5+ consumers? | Notes |
|---|---|---|---|---|
| `net10.0` | Any OS | No | Yes | Use for all new projects |
| `net10.0-windows` | Windows only | No | Yes (Windows only) | Unlocks WinForms, WPF, Registry |
| `net8.0` | Any OS | No | Yes | LTS until Nov 2026 |
| `net48` | Windows only | Yes (4.8 only) | No | Legacy maintenance target |
| `netstandard2.0` | Any OS | Yes (4.6.1+) | Yes (2.0+) | Max compatibility bridge |
| `netstandard2.1` | Any OS | No | Yes (3.0+) | Never supported by Framework 4.x |

### OS-Specific TFMs and Portability

Adding an OS suffix to a TFM (e.g., `net10.0-windows`) unlocks OS-specific APIs but immediately restricts where the binary can run. A project targeting `net10.0-windows` will not compile on Linux. If a project needs to call Windows-specific APIs from a broader codebase, the correct approach is to use the `[SupportedOSPlatform("windows")]` attribute alongside an OS runtime guard so non-Windows callers are warned by the analyzer.

### Multi-Targeting

Using the plural `<TargetFrameworks>` element (note the "s") instructs the SDK to build the project once per TFM and produce a separate set of output assets for each:

```xml
<TargetFrameworks>net10.0;net48;netstandard2.0</TargetFrameworks>
```

Each build pass defines its own preprocessor constants, allowing a single source file to include TFM-conditional code branches using `#if` directives.

### Preprocessor Constants from TFMs

The C# compiler automatically defines preprocessor symbols from the active TFM during each build pass. The naming convention is: dots become underscores, all letters uppercase. Two forms exist:

- **Exact version** (e.g., `NET10_0`) — true only on that specific version. Almost never use this form.
- **Range (`_OR_GREATER`)** (e.g., `NET10_0_OR_GREATER`) — true on that version and any later version. Use this form in nearly all cases.

```csharp
#if NET10_0_OR_GREATER
// Code compiled only when targeting .NET 10 or newer
#endif

#if NETFRAMEWORK
// Code compiled only when targeting any .NET Framework version
#endif

#if WINDOWS
// Code compiled only when the TFM includes -windows suffix
#endif
```

| TFM | Exact constant | Range constant (prefer) |
|---|---|---|
| `net10.0` | `NET10_0` | `NET10_0_OR_GREATER` |
| `net8.0` | `NET8_0` | `NET8_0_OR_GREATER` |
| `net6.0` | `NET6_0` | `NET6_0_OR_GREATER` |
| `net48` | `NET48` | `NETFRAMEWORK` |
| `netstandard2.0` | `NETSTANDARD2_0` | `NETSTANDARD2_0_OR_GREATER` |
| `netstandard2.1` | `NETSTANDARD2_1` | `NETSTANDARD2_1_OR_GREATER` |
| `net10.0-windows` | `NET10_0` + `WINDOWS` | `NET10_0_OR_GREATER` + `WINDOWS` |

### Key Pitfalls

- Using `#if NETCOREAPP` in .NET 5+ code is incorrect. The `NETCOREAPP` constant belongs to the .NET Core era. The correct modern guard is `NET5_0_OR_GREATER` or `NET10_0_OR_GREATER`.
- Using `NET10_0` (no `_OR_GREATER`) means the guarded code is excluded from .NET 11, 12, and beyond. This is almost never the intent.
- `#if WINDOWS` is a **compile-time** guard: the code inside it does not exist in a non-Windows binary at all. `RuntimeInformation.IsOSPlatform(OSPlatform.Windows)` is a **runtime** check: the code compiles on all platforms but branches at runtime. Both have valid uses and are not interchangeable.
- `net10.0-windows` does not build for non-Windows. If the same library needs to support all platforms but call Windows APIs on Windows, use `<TargetFrameworks>net10.0;net10.0-windows</TargetFrameworks>` with OS guards.

## 3. .NET Standard — The Compatibility Bridge

### The Problem .NET Standard Solved

Before .NET 5, a library author targeting .NET Framework could not be consumed by .NET Core projects, and vice versa. The two runtimes had different BCL implementations, different APIs, and incompatible assemblies. This created a painful split in the NuGet ecosystem where popular libraries had to publish separate packages for each runtime.

**.NET Standard** resolved this by defining a **versioned API specification** — not an implementation, but a contract. Both .NET Framework and .NET Core committed to implementing the same contract for a given Standard version. A library compiled against `netstandard2.0` could be referenced from any runtime that implemented the standard, without recompilation.

```
                 ┌─────────────────────────────────┐
                 │        .NET Standard 2.0         │
                 │       (API Specification)        │
                 └──────────────┬──────────────────┘
                                │
              ┌─────────────────┼─────────────────┐
              ▼                 ▼                  ▼
   .NET Framework 4.6.1+   .NET Core 2.0+      Xamarin/Unity
   (implements the spec)  (implements the spec) (implements the spec)
```

### .NET Standard Versions

`netstandard2.0` covers approximately 32,000 APIs — the intersection of what .NET Framework and .NET Core both support. It is the most widely compatible target and is the correct choice when a library must support consumers on .NET Framework 4.x.

`netstandard2.1` adds roughly 3,000 additional APIs, including `Span<T>`, `IAsyncEnumerable<T>`, range-based string operations, and new LINQ overloads. However, .NET Framework 4.x never implemented `netstandard2.1` — Microsoft determined that the API additions were too breaking to retrofit onto the legacy stack. As a result, a library targeting `netstandard2.1` is invisible to any .NET Framework project.

| .NET Standard Version | Min .NET Framework | Min .NET Core / .NET | API Count | Span / IAsyncEnumerable |
|---|---|---|---|---|
| `netstandard1.0` | 4.5 | 1.0 | ~7,900 | No |
| `netstandard1.6` | N/A | 1.0 | ~13,500 | No |
| `netstandard2.0` | 4.6.1 | 2.0 | ~32,000 | No |
| `netstandard2.1` | **Not supported** | 3.0 | ~35,000 | Yes |

### When to Use .NET Standard Today

.NET Standard is in maintenance — no new versions will be released. For new libraries:

- **If consumers may include .NET Framework projects**: target `netstandard2.0`. This is the only standard version that bridges to Framework 4.x.
- **If all consumers are .NET 5+**: target `net10.0` directly. You gain access to the full modern API surface and avoid the API subset restrictions of the standard.
- **If you need to support both**: use `<TargetFrameworks>net10.0;netstandard2.0</TargetFrameworks>`. The `net10.0` asset is used by modern consumers; the `netstandard2.0` asset by Framework consumers.

### Key Pitfalls

- Targeting `netstandard2.1` under the mistaken belief that it supports .NET Framework. It does not. Only `netstandard2.0` bridges to Framework 4.x.
- Depending on a package whose NuGet assets target `net8.0` while your library targets `netstandard2.0`. The build may succeed (NuGet selects the closest available asset), but consumers on .NET Framework will encounter `PlatformNotSupportedException` or `TypeLoadException` at runtime because the selected asset uses APIs that do not exist on Framework.
- Targeting `netstandard2.0` for a library that will only ever be consumed by `net10.0` projects. There is no benefit and you unnecessarily lose access to modern APIs.

## 4. Runtime Flavors (CoreCLR, Mono, NativeAOT)

### Why There Are Three Runtimes

Modern .NET ships three distinct runtime implementations because no single design optimizes for all deployment contexts simultaneously. Server workloads need maximum throughput and full API surface. Browser and mobile workloads need small download size and platform sandbox compliance. Serverless and CLI workloads need minimal startup time and a single-file executable. Each runtime makes different trade-offs.

```
┌──────────────────────────────────────────────────────────────────┐
│                      .NET Application                            │
└───────────────┬─────────────────┬──────────────────┬────────────┘
                ▼                 ▼                   ▼
         ┌────────────┐   ┌────────────┐   ┌──────────────────┐
         │  CoreCLR   │   │    Mono    │   │   NativeAOT      │
         │  (default) │   │(WASM/MAUI) │   │(AOT compilation) │
         └────────────┘   └────────────┘   └──────────────────┘
         JIT at runtime   JIT or Interp     No JIT at runtime
         Full reflection  Full reflection   Trimmed reflection
         Server/Desktop   Browser/Mobile    CLI/Serverless
```

### CoreCLR

CoreCLR is the default runtime for console applications, ASP.NET Core web services, Worker Services, WPF, and WinForms on Windows, Linux, and macOS. It uses **RyuJIT** to compile Intermediate Language (IL) to native machine code at runtime. RyuJIT applies **tiered compilation**: methods are initially compiled at tier 0 (fast, unoptimized) to minimize startup latency, then recompiled at tier 1 (fully optimized) if they are called frequently enough. When **Profile-Guided Optimization (PGO)** is enabled, tier 1 compilation uses collected runtime profile data to make better inlining and layout decisions. CoreCLR supports the complete .NET BCL surface including full reflection, dynamic code generation (`Reflection.Emit`, `System.Linq.Expressions`), and runtime assembly loading.

### Mono

Mono is the original cross-platform .NET runtime, developed as an open-source project before Microsoft's .NET Core effort began. It was acquired by Microsoft and is now the engine behind two deployment targets:

- **Blazor WebAssembly**: Mono runs inside the browser sandbox. Because browsers prohibit runtime code generation (no JIT is possible in a WebAssembly environment), Mono runs in **interpreter mode** — IL is interpreted directly rather than compiled to native code. This means startup is fast (no JIT warm-up) but steady-state throughput is lower than CoreCLR.
- **.NET MAUI on iOS and Android**: On iOS, Apple's App Store rules historically prohibited JIT compilation, so Mono used its AOT mode. On Android, JIT is permitted, so Mono JITs code as on a desktop.

### NativeAOT

NativeAOT (Native Ahead-Of-Time) compiles the entire application — all IL, all referenced assemblies, the runtime itself — into a single self-contained native binary at **build time**. There is no CLR embedded in the output, no JIT at startup, and no IL in the binary. The result is a platform-native executable that starts in milliseconds, consumes a fraction of the memory of a CoreCLR equivalent, and has no dependency on an installed .NET runtime on the target machine.

The trade-offs are significant:
- **Reflection is restricted**: all reflection roots (types, methods, constructors accessed via reflection) must be declared at compile time through trim annotations (`[DynamicallyAccessedMembers]`) or an `rd.xml` manifest. Any reflective access not declared may be trimmed from the binary and throw at runtime.
- **No dynamic code generation**: `Reflection.Emit`, runtime `Expression` compilation, and `Assembly.Load` from arbitrary paths are not supported.
- **Trim warnings become errors**: the NativeAOT publish pipeline treats any "potentially trimmed member" warning as a build error, forcing all reflection to be explicit.

NativeAOT is ideal for AWS Lambda functions, Azure Container Apps, standalone CLI tools distributed as single files, and any scenario where cold-start latency or binary footprint is the primary concern.

### Runtime Comparison Table

| Runtime | Primary Use Cases | JIT at Runtime? | Reflection | Dynamic Codegen | Cold Start | Binary Size |
|---|---|---|---|---|---|---|
| CoreCLR | Server, desktop, worker | Yes (RyuJIT, tiered) | Full | Yes | Moderate | Large (includes JIT) |
| Mono (WASM) | Blazor WebAssembly | No (interpreted) | Limited | No | Fast | Moderate |
| Mono (mobile) | .NET MAUI iOS/Android | Yes (mobile) / AOT (iOS) | Full | Limited (iOS) | Moderate | Moderate |
| NativeAOT | CLI, serverless, containers | No | Trimmed only | No | Near-zero | Smallest |

### Key Pitfalls

- Assuming Blazor WebAssembly uses CoreCLR. It uses Mono in interpreter mode, which has different performance characteristics — benchmarks from a CoreCLR server project do not apply to Blazor WASM.
- Using NativeAOT with libraries that rely heavily on undecorated reflection — common in older serializers, many DI containers, and some ORMs. The binary may build successfully but throw `MissingMethodException` or `InvalidOperationException` at runtime on the first reflective access.
- Treating tiered compilation as always-on optimization. Tier 0 code runs until a method reaches the call threshold. In short-lived processes (CLI tools, Lambda cold starts), many methods never get recompiled at tier 1. NativeAOT or ReadyToRun (R2R) are better choices for those scenarios.
- Confusing `PublishReadyToRun` (`<PublishReadyToRun>true</PublishReadyToRun>`) with NativeAOT. ReadyToRun pre-compiles IL to native code but **keeps the IL in the binary** so the JIT can recompile it later. NativeAOT removes the IL entirely and has no JIT at runtime at all.

## 5. NuGet & Package Ecosystem

### What NuGet Is

NuGet is the .NET package manager. A NuGet package (`.nupkg`) is a ZIP archive containing compiled DLLs organized by TFM, a `.nuspec` manifest declaring metadata and dependencies, and optional MSBuild `.props`/`.targets` files that inject build logic into consuming projects. The NuGet client (integrated into `dotnet` CLI and Visual Studio) handles resolution, download, caching, and restore.

### PackageReference vs. packages.config

There are two ways to declare package dependencies in a project. Modern SDK-style projects use `<PackageReference>` elements inside the `.csproj`. Legacy (pre-SDK) projects used a separate `packages.config` file. The two formats differ fundamentally in how they handle transitive dependencies.

| Feature | `PackageReference` (SDK-style) | `packages.config` (legacy) |
|---|---|---|
| Location | Inside `.csproj` | Separate `packages.config` file |
| Transitive resolution | Automatic — only direct deps need listing | Manual — every transitive dep must be listed explicitly |
| Central version management | `Directory.Packages.props` supported | Not supported |
| `dotnet restore` | Native | Requires NuGet CLI or Visual Studio |
| Asset pruning | Unused compile/runtime assets excluded | No pruning |
| Lock file support | `packages.lock.json` (opt-in) | Not available |

A `PackageReference` element inside a project file looks like:

```xml
<PackageReference Include="Newtonsoft.Json" Version="13.0.3" />
```

### How NuGet Selects Assets

When a package supports multiple TFMs, NuGet selects the **best-matching** asset at restore time using a compatibility graph. If a project targets `net10.0` and a package provides assets for `net8.0`, `netstandard2.0`, and `net48`, NuGet selects the `net8.0` asset (closest compatible match). If the package provides only `netstandard2.0`, that asset is selected instead.

This selection is invisible during builds but has runtime implications — an asset built for a lower TFM may be missing APIs the application attempts to call.

### Central Package Management

In a monorepo with many projects, each project independently declaring package versions creates **version drift** — different projects use different versions of the same package, leading to inconsistent behavior and difficult upgrades. Central Package Management (CPM) solves this by declaring all package versions in a single `Directory.Packages.props` file at the repository root.

When CPM is enabled (`<ManagePackageVersionsCentrally>true</ManagePackageVersionsCentrally>`), individual `.csproj` files reference packages by name only, omitting the `Version` attribute entirely. The version is inherited from the central file. If a specific project needs to override, it uses `VersionOverride` on its own `PackageReference`.

```xml
<!-- Directory.Packages.props — at repo root; declares versions once for all projects -->
<Project>
  <PropertyGroup>
    <ManagePackageVersionsCentrally>true</ManagePackageVersionsCentrally>
  </PropertyGroup>
  <ItemGroup>
    <PackageVersion Include="Newtonsoft.Json" Version="13.0.3" />
    <PackageVersion Include="Microsoft.Extensions.Logging" Version="10.0.0" />
  </ItemGroup>
</Project>
```

Individual projects then reference packages without a version:

```xml
<PackageReference Include="Newtonsoft.Json" />
```

### Dependency Resolution and the "Nearest Wins" Rule

When two packages in the dependency graph declare different version requirements for the same transitive dependency, NuGet uses the **nearest dependency wins** rule: the version declared by the package closest to the root of the dependency graph is selected. This can result in unexpected version downgrades if a direct dependency requests an older version of a shared transitive package. The fix is to add an explicit `PackageReference` in the consuming project to pin the transitive dependency to the desired version.

### nuget.config

A `nuget.config` file configures NuGet behavior for a project or solution: package sources (nuget.org, private Azure Artifacts feeds, local folder feeds), credential providers for authenticated feeds, global package cache location, and fallback behavior when a source is unavailable. It is typically committed to source control so all developers and CI agents use the same feed configuration.

### Key Pitfalls

- Mixing `packages.config` and `<PackageReference>` in the same project. The two formats cannot coexist; use the NuGet Package Manager migration tool in Visual Studio to convert, or manually remove `packages.config` and add `<PackageReference>` elements.
- Using floating version ranges such as `Version="*"` or `Version="[1.0,)"`. This makes builds non-deterministic — different machines and CI runs may restore different versions. Always pin exact versions in production projects. Use a lock file (`RestorePackagesWithLockFile`) to enforce reproducibility.
- Forgetting to run `dotnet restore` after editing `Directory.Packages.props` on CI systems that cache the NuGet global packages folder. The cache may satisfy restore with old assets while the props file declares a new version.
- Treating transitive package resolution as stable across version upgrades. Upgrading one direct dependency can silently change which version of a transitive dependency is resolved.

## 6. Modern SDK-Style Project Format

### What Makes It "SDK-Style"

The SDK-style `.csproj` format was introduced with .NET Core and is the only format supported by the `dotnet` CLI. It is defined by the `Sdk` attribute on the root `<Project>` element (e.g., `Sdk="Microsoft.NET.Sdk"`). Compared to the legacy MSBuild format used by .NET Framework projects, SDK-style files are dramatically smaller — a complete console app project needs only five lines of XML — because the SDK imports sensible defaults automatically and discovers source files by convention rather than explicit inclusion.

A minimal but complete SDK-style project:

```xml
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <OutputType>Exe</OutputType>
    <TargetFramework>net10.0</TargetFramework>
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>
    <LangVersion>latest</LangVersion>
  </PropertyGroup>
</Project>
```

### Key Properties in Detail

**`TargetFramework` / `TargetFrameworks`**
The singular form declares a single TFM. The plural form (note the "s") enables multi-targeting, building one output per TFM in a single `dotnet build` invocation. All other properties in the project apply uniformly to every TFM pass unless wrapped in `<PropertyGroup Condition="'$(TargetFramework)' == 'net48'">` conditions.

**`Nullable`**
Controls the compiler's null-state flow analysis. When set to `enable`, every reference type is non-nullable by default — `string` cannot hold `null` without a compiler warning. Appending `?` to a type (e.g., `string?`) explicitly declares it as nullable. The compiler tracks null state through assignments, null checks, and pattern matching, emitting warnings (CS8600 series) for any dereference that could fail at runtime. Setting `warnings` enables the analysis but downgrades errors to warnings; `disable` turns it off entirely.

**`ImplicitUsings`**
When set to `enable`, the SDK generates a file `obj/Debug/{tfm}/{ProjectName}.GlobalUsings.g.cs` containing `global using` directives for the most common namespaces. For `Microsoft.NET.Sdk` (console apps and libraries), these include:

- `System`
- `System.Collections.Generic`
- `System.IO`
- `System.Linq`
- `System.Net.Http`
- `System.Threading`
- `System.Threading.Tasks`

Web SDK projects additionally include `Microsoft.AspNetCore.Builder`, `Microsoft.Extensions.DependencyInjection`, and others. The generated file is machine-readable — inspect it to understand exactly what is auto-imported when an unexpected type resolves or an ambiguous name error appears.

**`LangVersion`**
Specifies which C# language version the compiler enforces. `latest` enables all features the installed compiler supports; `preview` enables experimental pre-release features; a pinned value such as `13.0` locks the language version for reproducibility across compiler upgrades. Importantly, `LangVersion` controls **syntax** only — it does not affect which BCL types are available. Setting `LangVersion` to a high value while targeting `netstandard2.0` enables new syntax but does not make newer BCL APIs available.

**`OutputType`**
Determines the output format. `Exe` produces a console executable. `WinExe` produces a Windows application (no console window). `Library` (the default when omitted) produces a DLL. Setting `OutputType` to `Exe` is required for projects that use top-level statements.

**`PublishAot`**
When set to `true`, `dotnet publish` uses NativeAOT compilation instead of CoreCLR. This changes the entire output pipeline: the linker trims unused code, the AOT compiler converts IL to native code, and the output is a single self-contained native binary with no dependency on an installed .NET runtime.

### Nullable Reference Types — Conceptual Model

Before nullable reference types (C# 8+), the `string` type could hold `null` even though nothing in the type declaration suggested it. This was a historical design limitation. With `<Nullable>enable</Nullable>`, the compiler distinguishes between `string` (never null, enforced by flow analysis) and `string?` (explicitly nullable, must be checked before dereference). The compiler performs flow-sensitive analysis: after a null check or a pattern match, it narrows the type within the guarded scope.

The **null-forgiving operator** `!` suppresses a nullable warning for a specific expression:

```csharp
string forced = possiblyNullValue!; // compiler accepts without warning
```

This operator is appropriate only when external guarantees make null impossible but the compiler cannot prove it — for example, after calling an initialization method or when interoperating with pre-nullable APIs. Using it to silence warnings rather than address the underlying concern creates deferred `NullReferenceException` risk.

### Top-Level Statements

Before C# 9, every program required at minimum a `class Program` wrapper with a `static void Main(string[] args)` method. Top-level statements (C# 9+) eliminate this boilerplate: one source file per project may contain executable statements directly at the file level. The compiler synthesizes the entry-point class and method automatically. The implicitly declared variable `args` is available as a `string[]` in that file.

Top-level statements are syntactic sugar — the generated IL is identical to a hand-written `Main`. They have no runtime performance effect.

### SDK Property Reference Table

| Property | Values | Effect |
|---|---|---|
| `TargetFramework` | `net10.0`, `net48`, etc. | Single-TFM build |
| `TargetFrameworks` | Semicolon-separated TFMs | Multi-TFM build |
| `Nullable` | `enable`, `warnings`, `disable` | Null-state flow analysis |
| `ImplicitUsings` | `enable`, `disable` | Auto-generated global usings |
| `LangVersion` | `latest`, `preview`, `13.0`, etc. | C# syntax version |
| `OutputType` | `Exe`, `WinExe`, `Library` | Output binary type |
| `AllowUnsafeBlocks` | `true`, `false` | Enables `unsafe` pointer code |
| `PublishAot` | `true` | Enables NativeAOT on `dotnet publish` |
| `InvariantGlobalization` | `true` | Removes ICU globalization data (smaller, faster, limited locale support) |
| `PublishSingleFile` | `true` | Bundles all files into one executable (CoreCLR, not NativeAOT) |

### Key Pitfalls

- Enabling `<Nullable>enable</Nullable>` across an entire large legacy codebase in one commit. The resulting flood of CS8600–CS8604 warnings can exceed hundreds. Migrate incrementally using `#nullable enable` per-file, or enable warnings-only mode first before escalating to errors.
- Using `null!` (the null-forgiving operator) as a routine mechanism to suppress warnings rather than addressing the underlying nullability. Every `!` is a potential `NullReferenceException` deferred to runtime.
- Setting `<LangVersion>latest</LangVersion>` in a library targeting `netstandard2.0` and then using newer BCL APIs (like `string.Contains(char)`, `ReadOnlySpan<char>`, or `Index`/`Range`) that do not exist in the `netstandard2.0` API surface. The syntax compiles; the library type lookup fails for Framework consumers at runtime.
- Relying on implicit usings without knowing what they import. If a type resolves to an unexpected namespace or an ambiguous reference error appears, inspect `obj/Debug/net10.0/<ProjectName>.GlobalUsings.g.cs` to see exactly what was auto-imported, and add explicit `using` directives to disambiguate.
- Confusing `<PublishSingleFile>` with NativeAOT. Single-file publishing bundles all assemblies into one executable that self-extracts to a temp directory at startup — the CLR is still required and JIT still occurs. NativeAOT produces a genuinely self-contained native binary with no runtime extraction step.
