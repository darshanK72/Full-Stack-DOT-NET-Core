# Assemblies, Loading, Strong Naming & GAC

## Why It Matters

Every piece of code you write in .NET is packaged into an assembly before it reaches the runtime. The CLR never executes loose source files — it loads assemblies, resolves their identities, and enforces version and security boundaries at the assembly level. Understanding how assemblies are discovered, loaded, versioned, and isolated is what separates developers who debug mysterious `FileNotFoundException` and `MissingMethodException` crashes from developers who design plugin systems and multi-version deployments confidently. Assembly knowledge also sits at the heart of one of the biggest migration stories in .NET history: moving from the Global Assembly Cache (GAC) and binding redirects of .NET Framework to the `deps.json`, `AssemblyLoadContext`, and runtime store model of modern .NET.

---

## Section 1: What Is an Assembly?

An assembly is the **fundamental unit of deployment, versioning, type identity, and security** in .NET. Physically it is a **PE (Portable Executable)** file — either a `.dll` (class library or shared component) or an `.exe` (application entry point). The PE format is the same container Windows uses for native binaries; .NET simply extends it with additional sections that carry managed metadata and IL.

### Contents of a .NET Assembly

Every assembly contains up to five logical pieces:

| # | Component | What it contains |
|---|---|---|
| 1 | **Manifest** | Assembly identity (name, version, culture, public key token), list of files in the assembly, exported types, referenced assemblies, security permission requests |
| 2 | **Metadata** | Complete description of every type, method, field, property, and event defined in the assembly; stored as binary tables in the PE |
| 3 | **IL code** | Method bodies compiled to Intermediate Language bytecode; JIT-compiled to native on first call |
| 4 | **Resources** | Embedded binary data — images, strings, `.resx`-compiled resource streams, satellite assembly data |
| 5 | **Native code** (optional) | Ready-to-Run (R2R) pre-compiled native sections added by `dotnet publish -r` or crossgen2 to reduce startup JIT cost |

The manifest is the most important piece for identity resolution: the CLR reads it before executing any code to confirm the assembly is what the caller expected.

### Single-File vs Multi-File Assemblies

```
Single-file assembly (modern .NET — almost universal)
┌──────────────────────────────────────┐
│  MyLibrary.dll (one PE file)         │
│  ┌──────────┐  ┌──────────────────┐  │
│  │ Manifest │  │ Metadata tables  │  │
│  └──────────┘  └──────────────────┘  │
│  ┌──────────┐  ┌──────────────────┐  │
│  │ IL code  │  │ Resources (opt.) │  │
│  └──────────┘  └──────────────────┘  │
└──────────────────────────────────────┘

Multi-file assembly (.NET Framework only — deprecated)
┌────────────────────┐   ┌─────────────────┐
│  MyLibrary.dll     │   │  Helper.netmod  │
│  ┌──────────────┐  │   │  (netmodule)    │
│  │ Manifest     │──┼──>│  IL + Metadata  │
│  │ (lists .netm │  │   │  (no manifest)  │
│  │  odule files)│  │   └─────────────────┘
│  └──────────────┘  │
└────────────────────┘
```

Multi-file assemblies (linked with `al.exe`) are a .NET Framework concept; they do not exist in .NET Core or modern .NET.

### The Assembly as the Type Identity Boundary

The CLR does not identify types by name alone. **Type identity is assembly-qualified**: the same class name in two different assemblies produces two unequal types at runtime. `typeof(Foo)` from `Assembly A` and `typeof(Foo)` from `Assembly B` are different objects, and casting between them throws `InvalidCastException`. This is the root cause of many plugin and isolation bugs.

## Section 2: Assembly Identity — The Four-Part Name

The CLR identifies assemblies by a **four-part name**, not by file path. This four-part name is what makes side-by-side versioning and strong naming possible.

### The Four Parts

| Part | Description | Example |
|---|---|---|
| **Simple name** | No file extension | `System.Text.Json` |
| **Version** | `Major.Minor.Build.Revision` | `8.0.0.0` |
| **Culture** | `neutral` for code assemblies; locale tag for satellite (resource-only) assemblies | `neutral` / `en-US` |
| **PublicKeyToken** | 8-byte (16 hex chars) SHA-1 hash of the public key, last 8 bytes reversed; `null` if unsigned | `cc7b13ffcd2ddd51` |

The full display format concatenates all four with commas:

```
System.Text.Json, Version=8.0.0.0, Culture=neutral, PublicKeyToken=cc7b13ffcd2ddd51
```

### Version Semantics

The `Version` field follows `Major.Minor.Build.Revision`. The CLR uses it differently depending on context:

- In **.NET Framework** with the GAC, the loader enforces exact version matches by default, relaxed only by binding redirects in `app.config`.
- In **.NET Core**, the `deps.json` file records the exact version of every resolved assembly. The `rollForward` policy in `runtimeconfig.json` controls version flexibility for the runtime itself, but individual library versions are pinned at build time.

### Culture and Satellite Assemblies

The `Culture` part is `neutral` for all code-bearing assemblies. Satellite assemblies — resource-only DLLs that carry localized strings for a specific locale — carry a culture tag such as `en-US` or `fr-FR`. The runtime uses the culture part to select the right satellite assembly for the current `CultureInfo`.

### PublicKeyToken and Type Identity

The `PublicKeyToken` is a compact fingerprint derived from the full RSA public key (the SHA-1 hash of the key, last 8 bytes, byte-reversed). Its presence signals that the assembly is **strong-named** — cryptographically tied to a specific key pair.

**Important:** because type identity is assembly-qualified, an assembly loaded from two different contexts (or two different versions) produces incompatible types even when the class definitions are byte-for-byte identical. Every `==` comparison between types across assembly boundaries must account for this.

## Section 3: Assembly Loading — Three Mechanisms

The runtime exposes three static methods on `Assembly` for loading assemblies at runtime. They differ significantly in how they resolve dependencies and whether they unify with already-loaded copies.

### The Three APIs

**`Assembly.Load(AssemblyName)`**
- Resolves by identity using the current `AssemblyLoadContext` and the application's `deps.json` probe rules.
- If an assembly with the same identity is already loaded in the same context, the existing instance is returned — no duplicate.
- This is the **preferred API** for loading known dependencies by name.

**`Assembly.LoadFrom(string path)`**
- Loads from a file path, but first checks whether an assembly with the same four-part identity is already loaded in the Default ALC.
- If the identity matches, the existing instance is returned (identity unification).
- Dependencies are resolved relative to the directory containing the DLL.
- Useful for simple plugin loading when you know the absolute file path.

**`Assembly.LoadFile(string path)`**
- Loads from a file path in **complete isolation** — no dependency resolution, no identity unification.
- Two calls with the same path can produce two separate `Assembly` objects with distinct type identities.
- Types from an assembly loaded with `LoadFile` are **not equal** to the same types loaded via `Load` or `LoadFrom` — cross-cast fails.
- Almost never the right choice in application code; use a custom `AssemblyLoadContext` instead.

### Comparison Table

| API | Identity unification | Dependency resolution | Isolation | Typical use case |
|---|---|---|---|---|
| `Assembly.Load(AssemblyName)` | Yes — same identity, same context | Via ALC / `deps.json` | Shared with context | Load a known dependency by name |
| `Assembly.LoadFrom(path)` | Yes — checks existing by identity | Relative to DLL directory | Shared with Default ALC | Simple plugin loading with known path |
| `Assembly.LoadFile(path)` | No — always a new load | None | Fully isolated | Isolated PE inspection only |
| Custom `AssemblyLoadContext` | Per-context | Via `AssemblyDependencyResolver` | Per-context | Plugin systems, version isolation |

### The `LoadFile` Type Identity Pitfall

```
Assembly A loaded via LoadFrom("path/X.dll")  →  TypeA (in Default ALC)
Assembly B loaded via LoadFile("path/X.dll")  →  TypeB (in isolated context)

TypeA == TypeB  →  false
(TypeA) instanceOfTypeB  →  InvalidCastException
```

This silent failure is one of the most confusing bugs in plugin architectures. The solution is to load all plugins through a custom `AssemblyLoadContext` with `AssemblyDependencyResolver`, not through `LoadFile`.

## Section 4: AssemblyLoadContext — Isolation in .NET Core

`AssemblyLoadContext` (ALC) is the **.NET Core replacement for `AppDomain` isolation**. Modern .NET has exactly one `AppDomain` per process — creating additional domains throws `PlatformNotSupportedException`. However, you can have many ALCs, each acting as an independent assembly namespace.

### The Default ALC

Every process has a **Default ALC** (`AssemblyLoadContext.Default`) that hosts all the main application's assemblies. Framework assemblies and NuGet packages resolved from `deps.json` load here.

### Custom ALCs for Plugin Isolation

A custom ALC is a subclass of `AssemblyLoadContext` that overrides `Load(AssemblyName)` to map requested names to file paths. The canonical pattern uses `AssemblyDependencyResolver`, which reads a plugin's own `deps.json` to resolve its transitive dependencies:

```
Plugin A needs Newtonsoft.Json 12.x  →  loaded into PluginAContext
Plugin B needs Newtonsoft.Json 13.x  →  loaded into PluginBContext
Main app uses neither                →  Default ALC untouched
```

### ALC Load Algorithm

```
Request for assembly "Foo, Version=2.0.0.0"
        │
        ▼
  ALC.Load() override
  (returns path from AssemblyDependencyResolver?)
        │
   found? ──Yes──> LoadFromAssemblyPath(path) → Assembly in this ALC
        │
       No
        │
        ▼
  Fall back to Default ALC
  (for shared framework assemblies like System.Runtime)
        │
        ▼
  FileNotFoundException if not found anywhere
```

The fall-through to the Default ALC for framework assemblies is deliberate: plugins should not carry their own copy of `System.Runtime` — they should share the one already in the process.

### Collectible ALCs and Unloading

A **collectible ALC** (`isCollectible: true`) can be unloaded by calling `alc.Unload()`. After the call, the GC reclaims the ALC's memory once all managed references to types, `MethodInfo` objects, delegates, and instances defined in that context are released.

Pitfalls for collectible ALCs:
- Holding any `Type`, `MethodInfo`, or delegate that targets a method in the ALC **prevents collection** — even a LINQ expression tree or a closure that captured such a type counts.
- The standard practice is to communicate across the ALC boundary through interfaces defined in a **shared neutral assembly** loaded into the Default ALC, so the host never holds direct type references into the plugin's ALC.
- Use `WeakReference<AssemblyLoadContext>` to verify the ALC was actually collected after calling `Unload()`.

### ALC vs AppDomain Comparison

| Dimension | AppDomain (.NET Framework) | AssemblyLoadContext (.NET Core) |
|---|---|---|
| Isolation granularity | Separate managed heap, separate thread pool, separate static fields | Separate assembly namespace only; shared heap and thread pool |
| Can unload | Yes — `AppDomain.Unload()` | Collectible ALC only — `alc.Unload()` |
| Multiple per process | Yes | Yes |
| Cross-boundary marshaling | `MarshalByRefObject` required | Direct object references allowed (via shared interfaces) |
| Available in .NET Core | Creating new domains throws `PlatformNotSupportedException` | Full support |
| Static field isolation | Yes — each domain has its own copy | No — statics are per-type, not per-ALC |

## Section 5: Strong Naming

A **strong name** extends the four-part assembly identity with an RSA digital signature over the assembly manifest. The build toolchain hashes the manifest contents, signs the hash with the RSA private key, and embeds both the signature and the public key into the PE file. The public key token (a compact 8-byte fingerprint of the full key) appears in the four-part name and in every assembly that references this one.

### Key Concepts

- **Key pair**: generated by `sn.exe -k keypair.snk`; a 2048-bit RSA key pair stored in a `.snk` file.
- **Public key token**: SHA-1 hash of the public key, last 8 bytes, byte-reversed. This is the 16 hex-character value in the four-part name.
- **Signature**: hash of the manifest, signed with the private key; embedded in the PE.
- **Project configuration**: two MSBuild properties enable signing:
  - `<SignAssembly>true</SignAssembly>`
  - `<AssemblyOriginatorKeyFile>keypair.snk</AssemblyOriginatorKeyFile>`

### What Strong Naming Guarantees — and Does Not

| Guarantee | .NET Framework | .NET Core / .NET 5+ |
|---|---|---|
| Signature verified at load time | Yes — CLR verifies before loading any non-GAC strong-named assembly | **No** — signature is embedded but not verified at load time |
| Tamper detection at load time | Yes | No — signature is informational only |
| Required for GAC installation | Yes | GAC does not exist |
| Required for `InternalsVisibleTo` with a signed assembly | Must include `PublicKey=...` (full key) | Same requirement when granting assembly is signed |
| Unique identity within the CLR | Yes — two assemblies with same identity cannot coexist in same ALC | Yes — identity is still enforced; only signature verification was dropped |

The decision to drop signature enforcement in .NET Core was intentional: it simplified library sharing and eliminated a painful class of "strong name must reference strong name" build problems that blocked OSS adoption.

### Strong Naming vs Authenticode

These solve **different problems** and are often confused:

| Property | Strong Naming | Authenticode (Code Signing) |
|---|---|---|
| What it signs | The assembly manifest hash | The entire PE file with a trusted CA certificate |
| Trust established | CLR-level identity: this assembly came from the key pair holder | OS-level trust: Windows SmartScreen, installer dialogs |
| Verification enforced by | CLR (at load time in .NET Framework; not in .NET Core) | Windows kernel / OS security UI |
| Can be absent | Yes — weak-named assemblies are common | Yes — most internal DLLs have no Authenticode signature |
| Required for GAC | Yes | No |
| Certificate authority required | No — self-generated key pair | Yes — chained to a trusted CA |

An assembly can have a strong name, Authenticode, both, or neither. They do not replace each other.

### `InternalsVisibleTo` and Strong-Named Assemblies

When a strong-named assembly grants `InternalsVisibleTo` to a test project, the attribute must include the **full public key** (not just the token):

```csharp
[assembly: InternalsVisibleTo("MyLib.Tests, PublicKey=0024000004800000...")]
```

Using only the public key token will cause a compiler error. The full key can be extracted with `sn -p keypair.snk public.snk` followed by `sn -tp public.snk`.

## Section 6: GAC — Global Assembly Cache (Legacy)

### What the GAC Was

The **Global Assembly Cache** is a machine-wide repository for strong-named assemblies in .NET Framework, stored at `%windir%\Microsoft.NET\assembly`. Its two purposes were:

1. **Sharing**: multiple applications on the same machine reference a single on-disk copy of a DLL (e.g., all WPF apps share `PresentationFramework.dll`) rather than each app carrying its own.
2. **Side-by-side versioning**: `MyLib, Version=1.0.0.0` and `MyLib, Version=2.0.0.0` coexist in the GAC and are loaded independently by different apps.

Only **strong-named** assemblies can be installed in the GAC — the signature is what allows the CLR to trust a shared, machine-wide copy.

### GAC Management (`gacutil.exe`)

| Command | Purpose |
|---|---|
| `gacutil /i MyLib.dll` | Install (requires strong name) |
| `gacutil /u MyLib` | Uninstall by name |
| `gacutil /l` | List all installed assemblies |
| `gacutil /l MyLib` | List specific assembly and all its versions |

### GAC Does Not Exist in .NET Core / .NET 5+

The GAC concept was deliberately removed from modern .NET. It was replaced by two mechanisms:

**1. Shared Framework Store** — the .NET SDK ships all `Microsoft.NETCore.App` assemblies into a versioned directory that all framework-dependent apps reference. This directory is managed by the SDK installer and cannot accept custom assemblies.

```
Windows: C:\Program Files\dotnet\shared\Microsoft.NETCore.App\10.0.0\
Linux:   /usr/share/dotnet/shared/Microsoft.NETCore.App/10.0.0/
macOS:   /usr/local/share/dotnet/shared/Microsoft.NETCore.App/10.0.0/
```

**2. Application-local deployment** — each app carries its own copies of NuGet-resolved DLLs in its publish output directory. No system-wide registration needed.

### GAC vs .NET Core Shared Framework

| Property | GAC (.NET Framework) | Shared Framework (.NET Core) |
|---|---|---|
| Location | `%windir%\Microsoft.NET\assembly` | `{dotnet_root}/shared/Microsoft.NETCore.App/{ver}/` |
| Install tool | `gacutil.exe` | .NET SDK installer only |
| Accepts custom DLLs | Yes — any strong-named DLL | No — only SDK-shipped assemblies |
| Side-by-side versions | Yes — all registered assemblies | Yes — multiple SDK/runtime installs side by side |
| Required for deployment | Often yes (.NET Framework apps used GAC DLLs) | No — NuGet + app-local is the standard model |
| Strong name required | Yes | N/A — custom DLLs not accepted at all |

The practical implication: every modern .NET app is either **self-contained** (carries the entire runtime in its publish directory) or **framework-dependent** (relies on the shared framework store installed by the SDK). There is no system-wide custom library store to manage, version-conflict, or corrupt.

## Section 7: Dependency Resolution and Binding Redirects

### .NET Framework: Binding Redirects in `app.config`

In .NET Framework, version conflicts between assemblies were resolved at runtime through **binding redirects** — XML stanzas in `app.config` that tell the loader to treat one version range as another:

```xml
<configuration>
  <runtime>
    <assemblyBinding xmlns="urn:schemas-microsoft-com:asm.v1">
      <dependentAssembly>
        <assemblyIdentity name="MyLib" publicKeyToken="abc123" culture="neutral" />
        <bindingRedirect oldVersion="0.0.0.0-1.9.9.9" newVersion="1.2.0.0" />
      </dependentAssembly>
    </assemblyBinding>
  </runtime>
</configuration>
```

NuGet on package install would auto-generate these redirects, but they frequently got out of sync, especially in large projects with many transitive dependencies.

### .NET Core: `deps.json` and `runtimeconfig.json`

Modern .NET replaces XML binding redirects entirely with two JSON files generated at build time:

**`<appname>.runtimeconfig.json`** — specifies:
- The target framework and version (`"tfm": "net10.0"`)
- The `rollForward` policy controlling how runtime version mismatches are handled
- GC settings and other runtime knobs

**`<appname>.deps.json`** — a complete dependency graph specifying:
- Every NuGet package, its exact resolved version
- The relative path to each assembly asset
- Runtime identifier (RID)-specific asset selection

The runtime reads `deps.json` at startup and resolves every load request from it. No XML, no runtime redirect stanzas, no `app.config` for managed assembly resolution.

### Resolution Flow Comparison

```
.NET Framework resolution path
Request for "MyLib, Version=1.0.0.0"
  │
  ▼
Check app.config bindingRedirects
  │ redirect found (→ 1.2.0.0)?
  ▼
Probe GAC for MyLib 1.2.0.0
  │ not found?
  ▼
Probe app bin directory
  │ not found?
  ▼
FileNotFoundException


.NET Core resolution path
Request for "MyLib"
  │
  ▼
Look up in deps.json → exact path
  │ found?
  ▼
Load from that path
  │ not in deps.json?
  ▼
ALC.Load() override (if custom ALC)
  │ returns null?
  ▼
Probe app base directory
  │ not found?
  ▼
FileNotFoundException
```

### Key Pitfalls

- **`app.config` binding redirects are silently ignored in .NET Core** — you will not get an error, but you will also not get the redirect. Conflicts must be resolved by pinning versions in the `.csproj` with `<PackageReference Version="...">` or by adjusting `<NoWarn>` for intentional version skew.

- **`deps.json` is a build artifact, not a hand-edited file** — editing it manually is fragile and gets overwritten on next build. The canonical way to influence dependency resolution is through `PackageReference` entries in the project file.

- **`rollForward` in `runtimeconfig.json`** controls runtime version matching only (e.g., whether an app targeting `net10.0` runs on a machine that only has `net10.1` installed). It does not affect library assembly resolution.

- **Self-contained apps embed `deps.json` and the entire runtime** — there is no lookup against the machine's shared framework store; everything is in the app's publish directory.

## Quick Reference

### Assembly Loading API Comparison

| API | Input | Unifies with existing? | Dep resolution | When to use |
|---|---|---|---|---|
| `Assembly.Load(AssemblyName)` | Identity (name + version) | Yes — same identity, same context | Via `deps.json` / ALC | Load a known dep by name at runtime |
| `Assembly.LoadFrom(path)` | File path | Yes — if identity already loaded | Relative to DLL directory | Simple plugin loading with known path |
| `Assembly.LoadFile(path)` | File path | No — always new load | None | Isolated PE inspection only; avoid in apps |
| Custom `AssemblyLoadContext` | Path via `Load()` override | Per-context | `AssemblyDependencyResolver` + `deps.json` | Plugin systems, multi-version isolation |

### ALC vs AppDomain

| Dimension | AppDomain (.NET Framework) | AssemblyLoadContext (.NET Core) |
|---|---|---|
| Isolation granularity | Separate managed heap, thread pool, statics | Separate assembly namespace; shared heap |
| Can unload | Yes — `AppDomain.Unload()` | Collectible ALC only — `alc.Unload()` |
| Multiple per process | Yes | Yes |
| Cross-boundary marshaling | `MarshalByRefObject` required | Direct references via shared interfaces |
| Creating extras in .NET Core | Throws `PlatformNotSupportedException` | Full support |

### Strong Naming Commands (`sn.exe`)

| Command | Purpose |
|---|---|
| `sn -k keypair.snk` | Generate a new 2048-bit RSA key pair |
| `sn -p keypair.snk public.snk` | Extract just the public key from the pair |
| `sn -tp public.snk` | Display the public key token (the 16 hex chars) |
| `sn -v MyLib.dll` | Verify the strong name signature on a DLL |
| `sn -Vr MyLib.dll` | Skip verification for this assembly (dev machines only) |
| `sn -Vu MyLib.dll` | Re-enable verification (undo `-Vr`) |

### GAC (.NET Framework) vs Runtime Store (.NET Core)

| Property | GAC | .NET Core Shared Framework |
|---|---|---|
| Path | `%windir%\Microsoft.NET\assembly` | `{dotnet_root}/shared/Microsoft.NETCore.App/{ver}/` |
| Managed by | `gacutil.exe` | .NET SDK installer |
| Accepts custom DLLs | Yes (strong-named only) | No |
| Side-by-side versions | Yes | Yes — multiple SDK/runtime installs |
| Required for app deployment | Frequently yes in .NET Framework | No — apps are self-contained or framework-dependent |

### Common Assembly Loading Pitfalls

- **`LoadFile` with no dependency resolution** — if the DLL has transitive dependencies, `LoadFile` will not find them and you get `FileNotFoundException` at instantiation time. Use a custom ALC with `AssemblyDependencyResolver` instead.

- **Holding `Type` or `MethodInfo` after `alc.Unload()`** — the collectible ALC cannot be GC-collected while any managed reference to its types survives. Even a captured LINQ expression or a `delegate` pointing into the ALC counts. Use `WeakReference<AssemblyLoadContext>` to verify collection.

- **Two different `Type` objects for the same logical type** — when the same DLL is loaded into two ALCs, `typeA == typeB` is `false`. This causes silent `InvalidCastException` across ALC boundaries. Fix: define shared interfaces in a neutral assembly loaded into the Default ALC.

- **Binding redirects in .NET Core** — `app.config` `<bindingRedirect>` entries are silently ignored for managed assemblies. Resolve conflicts via explicit `PackageReference` version pinning in the `.csproj`.

- **Confusing strong naming with Authenticode** — strong names are a CLR identity mechanism; Authenticode is an OS-level publisher certificate. In .NET Core, strong name signatures are not verified at load time. Neither replaces the other.

- **`InternalsVisibleTo` with a signed assembly** — the `InternalsVisibleTo` attribute on a strong-named assembly must include the full `PublicKey=...` value (the full public key, not the 8-byte token). The compiler rejects the token alone.

- **`Assembly.Location` is empty in single-file apps** — in `dotnet publish --single-file` deployments, assemblies are bundled and `Location` returns an empty string. Use `AppContext.BaseDirectory` or `Assembly.GetManifestResourceStream` instead.
