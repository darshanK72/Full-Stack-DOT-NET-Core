## 1. Why Migrate? .NET Framework vs Modern .NET

### The Maintenance-Mode Reality

.NET Framework 4.8 shipped in April 2019 and was immediately placed into **maintenance mode** — defined by Microsoft as security patches and critical bug fixes only. No new APIs, no language feature enablement, no runtime performance investment. Every enhancement to C# from version 8 onward, every GC improvement, every new BCL type — none of it is backported. The platform is frozen.

The practical consequence: an enterprise application on .NET Framework 4.8 today is running on code whose internals are effectively unchanged from 2019. Its JIT, its GC, its I/O primitives are the same ones that shipped before the wholesale rewrite effort that produced Modern .NET.

**Delivery mechanism difference.** .NET Framework ships as a Windows component distributed through Windows Update. Installing a new version is system-wide — a machine cannot run .NET Framework 4.8 and 4.6.2 simultaneously in isolation. Modern .NET ships as an independently versioned runtime placed in a per-application or machine-wide directory. Side-by-side coexistence of net8.0 and net10.0 on the same machine is normal and supported.

### The Performance Gap

The Modern .NET runtime is architecturally different from .NET Framework at the JIT, GC, and BCL layers:

- **Tiered JIT + PGO (Profile-Guided Optimization):** Methods compile at Tier 0 (fast, unoptimized) on first call, then recompile at Tier 1 (fully optimized) after sufficient call counts accumulate. Dynamic PGO (introduced in .NET 6, improved through .NET 10) further specializes hot paths based on observed runtime types — something impossible to backport to .NET Framework's single-tier JIT.
- **Regions GC:** The .NET 7+ GC restructures the heap into variable-size regions instead of fixed segments, enabling the collector to return memory to the OS more aggressively and reduce pause times for large heap workloads.
- **`Span<T>` and `Memory<T>` throughout the BCL:** These stack-friendly slice types eliminate allocations in string parsing, I/O buffers, and collection operations. The entire BCL was audited and rewritten to use them where applicable. .NET Framework's BCL predates `Span<T>` and cannot be refactored without breaking ABI compatibility.
- **NativeAOT:** Compiles the entire application — including the runtime — to a standalone native binary at publish time. Eliminates JIT startup latency entirely. Only available on Modern .NET.
- **`System.Text.Json` (built-in):** The built-in JSON serializer uses source generators and `Span<T>`-based UTF-8 processing. On .NET Framework, the only option was `Newtonsoft.Json`, which allocates significantly more per call.

Real-world performance comparisons (TechEmpower and Microsoft internal benchmarks) consistently show:

| Workload | Approximate speedup (net10.0 vs net48) |
|---|---|
| HTTP request throughput (Kestrel) | 3–5× |
| JSON serialization (`System.Text.Json` vs `Newtonsoft.Json`) | 8–10× |
| LINQ over collections | 2–4× |
| GC throughput (large heap) | 2–3× |
| Cold startup time | 1.5–2× (JIT); 5–10× with NativeAOT |

These are not micro-benchmark artifacts — they reflect the architectural differences described above.

### What Does Not Migrate Directly

Several .NET Framework technologies have no direct equivalent in Modern .NET and require redesign, not just retargeting:

| .NET Framework technology | Status in Modern .NET | Migration target |
|---|---|---|
| **ASP.NET Web Forms** | Removed — no equivalent | Razor Pages or Blazor |
| **WCF server-side** | Removed | gRPC (`Grpc.AspNetCore`) or CoreWCF |
| **WCF client-side** | Partial | `System.ServiceModel` client NuGet |
| **.NET Remoting** | Removed | gRPC or SignalR |
| **`BinaryFormatter`** | Removed (throws in .NET 9) | `System.Text.Json`, `MessagePack`, Protobuf |
| **`AppDomain` isolation** | `AppDomain.CreateDomain()` removed | `AssemblyLoadContext` |
| **`Thread.Abort()`** | Throws `PlatformNotSupportedException` | `CancellationToken` cooperative cancellation |
| **GAC (Global Assembly Cache)** | No equivalent | NuGet package restore; side-by-side deploy |
| **Full-trust CAS (Code Access Security)** | Removed | OS-level process isolation |
| **`System.Web` namespace** | Removed entirely | `Microsoft.AspNetCore.Http` |

The distinction matters for effort estimation: the first group requires architectural redesign and cannot be automated. The second group requires code changes but follows predictable patterns.

### Capability Table: .NET Framework 4.8 vs .NET 10

| Capability | .NET Framework 4.8 | .NET 10 |
|---|---|---|
| Platforms | Windows only | Windows, Linux, macOS, WASM |
| Release cadence | Maintenance patches only | New major each November |
| C# version max | C# 7.3 | C# 14 |
| New BCL APIs | None | Continuous additions |
| JIT strategy | Single-tier RyuJIT | Tiered + Dynamic PGO |
| GC strategy | Segments-based | Regions-based (lower pause, faster OS return) |
| NativeAOT | No | Yes |
| `Span<T>` / `Memory<T>` | Via NuGet (limited BCL use) | Built-in; BCL-wide |
| `System.Text.Json` | No (Newtonsoft.Json only) | Built-in |
| `IAsyncEnumerable<T>` | No | Yes |
| Source generators | No | Yes |
| Nullable reference types | No | Yes (`<Nullable>enable</Nullable>`) |
| Hot Reload | No | Yes (IDE and CLI) |
| Side-by-side versioning | No | Yes |
| Linux containers | No | Yes |
| Open source | Partially (reference source) | Fully open source (dotnet/runtime) |

## 2. Migration Strategies — Lift-and-Shift vs Incremental

No single migration strategy fits every codebase. The right choice depends on the size of the solution, the depth of `System.Web` usage, the presence of WCF or COM dependencies, and how much risk the team can tolerate in a single release cycle.

### Strategy 1: Lift-and-Shift (Big Bang)

Retarget the entire solution to `net10.0` at once. All breaking changes are fixed in a single pass before any deployment to production.

**When it works well:**
- Small solutions (fewer than ~10 projects, ~50k LOC)
- No Web Forms or WCF server-side dependencies
- Most NuGet dependencies already have net10.0 TFMs
- A good test suite provides a safety net

**When it fails:**
- Large solutions — the list of breaking changes becomes unmanageable in a single pass
- Missing third-party packages with no modern TFM — the solution cannot compile until replacements are found
- Interdependent architectural changes (e.g., replacing Web Forms) block everything else

**Mechanics:** Change `<TargetFrameworkVersion>v4.8</TargetFrameworkVersion>` to `<TargetFramework>net10.0</TargetFramework>` in every project file, then resolve every compile error and behavioral difference.

### Strategy 2: Incremental Migration (Library-by-Library)

Migrate leaf-dependency libraries first, working up the dependency tree toward the application entry point. Libraries targeting `netstandard2.0` during the transition period can be consumed by both .NET Framework 4.7.2+ and net10.0 simultaneously, allowing the running application to remain on .NET Framework while its dependencies are progressively modernized.

```
Dependency order (migrate bottom-up):

  [App - stays on net48]
        |
  [Domain Library] --> migrate to netstandard2.0, then net10.0
        |
  [Infrastructure] --> migrate to netstandard2.0, then net10.0
        |
  [Data Access]    --> migrate to netstandard2.0, then net10.0
```

**`netstandard2.0` as the transition target:** `netstandard2.0` is a compatibility specification, not a runtime. A library targeting it compiles against a defined API surface that both .NET Framework 4.7.2+ and all Modern .NET versions implement. It is not the end state — `netstandard2.0` lacks access to Modern .NET-specific APIs — but it acts as a bridge that lets the library ship to both consumer types during the transition window.

**When to use incremental:**
- Large solutions with many layers
- Teams need to keep shipping features during migration
- Some projects have clear third-party blockers that take time to resolve

### Strategy 3: Strangler Fig Pattern

Named after the strangler fig vine that grows alongside an existing tree, this pattern runs .NET Framework and .NET 10 services in parallel, routing traffic gradually from the old service to the new one until the old service is decommissioned.

```
Phase 1: 100% traffic to .NET Framework service
         [Load Balancer] --> [.NET Framework App]

Phase 2: Traffic split — new routes go to .NET 10
         [Load Balancer] --> [.NET 10 App]       (new endpoints)
                        --> [.NET Framework App] (legacy endpoints)

Phase 3: All traffic to .NET 10
         [Load Balancer] --> [.NET 10 App]
                        (Framework app decommissioned)
```

**Key enabler — `Microsoft.AspNetCore.SystemWebAdapters`:** This NuGet package provides a `System.Web.HttpContext` compatibility surface on top of ASP.NET Core's `HttpContext`. Code in an existing MVC or Web Forms controller that references `System.Web.HttpContext.Current`, `HttpRequest.Form`, or `HttpResponse.Headers` can compile against ASP.NET Core equivalents without immediate rewriting. This is what makes page-by-page or controller-by-controller migration possible without a full-surface rewrite.

**When to use Strangler Fig:**
- Mission-critical services that cannot tolerate a full cutover
- Large Web Forms or MVC applications where feature-by-feature migration reduces risk
- Teams that can operate two deployments in parallel during the transition

### Decision Matrix

| Factor | Lift-and-Shift | Incremental | Strangler Fig |
|---|---|---|---|
| Codebase size | Small | Medium–Large | Large |
| `System.Web` usage | None or minimal | Moderate | Extensive |
| WCF server-side | None | None | Must redesign |
| Risk tolerance | Higher | Moderate | Lowest |
| Migration calendar | Shortest elapsed | Medium | Longest elapsed |
| Downtime risk | Single cutover | Rolling | Minimal |

## 3. .NET Upgrade Assistant

### What It Is

The .NET Upgrade Assistant is a Microsoft-maintained global `dotnet` tool that automates the mechanical parts of migration. It operates in two modes: **analyze** (read-only scan that produces a report) and **upgrade** (interactive wizard that modifies files). The tool reads project files, scans NuGet dependency graphs, invokes Roslyn analyzers to find removed APIs, and transforms configuration artifacts.

Install command: `dotnet tool install -g upgrade-assistant`

### Analyze Mode

`upgrade-assistant analyze <solution.sln>` scans the solution without modifying anything. It produces a compatibility report covering five categories:

1. **Project format issues** — old-style verbose `.csproj` vs SDK-style; presence of `packages.config`
2. **NuGet compatibility** — packages that lack a `net10.0` TFM in their package metadata; packages with known breaking changes
3. **Removed APIs** — calls to types or members absent from the target TFM, surfaced using the `Microsoft.DotNet.Analyzers.Compatibility` Roslyn analyzer
4. **Configuration system** — usage of `ConfigurationManager`, references to `web.config` or `app.config` that need migration to `IConfiguration`
5. **Legacy project types** — Web Forms (`.aspx`, `.ascx`), WCF (`.svc`, `ServiceModel` config), HTTP Modules/Handlers

The analyze pass is the most important input to migration effort estimation. Run it before writing a single line of migration code.

### Upgrade Mode

`upgrade-assistant upgrade <solution.sln>` walks projects in reverse dependency order (leaf dependencies first) and applies a series of upgrade steps interactively:

- Converts old-style `.csproj` to SDK-style format
- Replaces `<Reference>` with `<PackageReference>`; deletes `packages.config`
- Updates `<TargetFrameworkVersion>` to the target TFM
- Adds compatibility shim packages where applicable
- Transforms `web.config` / `app.config` entries
- Generates a `UpgradeAssistantSummary.json` report for the team

### What the Upgrade Assistant Does NOT Do

The tool handles mechanical transformations. It cannot:

- **Redesign Web Forms to Razor Pages/Blazor** — these are architectural changes requiring human judgment about component boundaries
- **Replace WCF server-side with gRPC** — service contracts, message types, and transport semantics all differ; no automated mapping exists
- **Rewrite COM interop** — COM-dependent code requires Windows-specific analysis and often runtime testing
- **Make business logic decisions** — deprecated API replacements that change semantics (e.g., `BinaryFormatter` → `System.Text.Json`) require validation that the new format is compatible with stored data

### API Analyzer as a Standalone Alternative

`Microsoft.DotNet.Analyzers.Compatibility` (the Roslyn analyzer the Upgrade Assistant embeds) can be added directly to any project as a NuGet package. It flags .NET Framework-only APIs with platform compatibility warnings (CA1416 and related codes) at compile time, without requiring the full Upgrade Assistant workflow. This is useful for targeted scanning of individual projects or when integrating compatibility analysis into a CI pipeline.

### APIs Most Commonly Flagged

| Flagged API | Reason | Action required |
|---|---|---|
| `System.Web.HttpContext.Current` | `System.Web` namespace removed | Replace with `IHttpContextAccessor` or use `SystemWebAdapters` |
| `ConfigurationManager.AppSettings` | Requires NuGet shim on net10.0 | Add `System.Configuration.ConfigurationManager` or migrate to `IConfiguration` |
| `BinaryFormatter` | Removed in .NET 9; security risk | Replace with `System.Text.Json`, `MessagePack`, or Protobuf |
| `Thread.Abort()` | Throws `PlatformNotSupportedException` | Replace with `CancellationToken` |
| `AppDomain.CreateDomain()` | Not supported | Replace with `AssemblyLoadContext` |
| `System.Runtime.Remoting.*` | Entire namespace removed | Replace with gRPC or SignalR |
| `System.Drawing.Bitmap` (Linux) | `libgdiplus` dependency; unreliable in containers | Replace with SkiaSharp or ImageSharp |

### Upgrade Assistant Command Reference

| Command | Purpose |
|---|---|
| `dotnet tool install -g upgrade-assistant` | Install globally |
| `upgrade-assistant analyze MySolution.sln` | Compatibility report — no files modified |
| `upgrade-assistant upgrade MySolution.sln` | Interactive upgrade wizard |
| `upgrade-assistant upgrade MyProject.csproj` | Upgrade a single project |
| `upgrade-assistant upgrade --non-interactive MyProject.csproj` | Apply all safe fixes without prompts (CI use) |

## 4. Project File Migration — packages.config → SDK-Style

### Two Generations of Project Files

**.NET Framework project files (old-style / non-SDK):** Generated by the Visual Studio project system built on MSBuild 14 and earlier. Characterized by:
- The root element `<Project ToolsVersion="..." xmlns="...">` (no `Sdk` attribute)
- Explicit `<Compile Include="...">` for every `.cs` file — files not listed are invisible to the build
- Assembly references as `<Reference>` elements with `<HintPath>` pointing into a `packages` folder
- A separate `packages.config` file listing every NuGet package including all transitive dependencies
- No automatic transitive dependency resolution — the developer manually maintains the full flat list
- Typical file length: 100–300+ lines of XML

**SDK-style project files (Modern .NET):** Introduced with .NET Core 1.0. Characterized by:
- The root element `<Project Sdk="Microsoft.NET.Sdk">` — the `Sdk` attribute imports common build targets implicitly
- No `<Compile Include>` — all `.cs` files in the project directory are included by default (wildcard glob)
- `<PackageReference>` inline in the project file; no `packages.config`
- Transitive dependencies resolved automatically by NuGet — only direct dependencies need to be declared
- Typical file length: 8–20 lines of XML

### The Migration Mechanics

The conversion from old-style to SDK-style involves:

1. Delete `packages.config`
2. Convert every `<Reference Include="..." HintPath="...">` for NuGet packages to `<PackageReference Include="PackageName" Version="x.y.z">`
3. Remove all `<Compile Include="...">` items (the SDK glob handles them)
4. Keep explicit `<Compile Remove="...">` for any files that should be excluded
5. Replace `<TargetFrameworkVersion>v4.8</TargetFrameworkVersion>` with `<TargetFramework>net10.0</TargetFramework>`
6. Add `<Nullable>enable</Nullable>` and `<ImplicitUsings>enable</ImplicitUsings>` as desired

**Critical pitfall on file inclusion:** Because old-style projects listed files explicitly, some were deliberately excluded. SDK-style projects include everything by default. Files excluded by omission in the old project become silently included after conversion. Audit for generated files, legacy stubs, and files excluded from compilation — they must be re-excluded with `<Compile Remove="...">`.

### Central Package Management (CPM)

In a monorepo with many projects, version drift becomes a problem: project A uses `Newtonsoft.Json 12.x` while project B uses `13.x`, leading to subtle runtime incompatibilities. Central Package Management (CPM) solves this by declaring all package versions in a single `Directory.Packages.props` file at the repository root.

`Directory.Packages.props` (repository root):
```xml
<Project>
  <PropertyGroup>
    <ManagePackageVersionsCentrally>true</ManagePackageVersionsCentrally>
  </PropertyGroup>
  <ItemGroup>
    <PackageVersion Include="Newtonsoft.Json" Version="13.0.3" />
    <PackageVersion Include="Microsoft.Extensions.Logging" Version="10.0.0" />
  </ItemGroup>
</Project>
```

With CPM active, individual project files reference packages without a `Version` attribute — `<PackageReference Include="Newtonsoft.Json" />`. If a `Version` attribute appears on a `PackageReference` in a project file while CPM is active, MSBuild emits a build error. This is intentional: the error enforces the invariant that the central file is the single source of truth.

**`Directory.Build.props` vs `Directory.Packages.props`:** These serve different purposes. `Directory.Build.props` sets MSBuild properties (like `<Nullable>enable</Nullable>`, `<TreatWarningsAsErrors>`) for all projects under the directory. `Directory.Packages.props` controls NuGet package versions. Both files are discovered by walking up the directory tree from the project file.

### Old-Style vs SDK-Style Side-by-Side

```
OLD (non-SDK):                          NEW (SDK-style):
---------------------------------       ---------------------------------
<Project ToolsVersion="15.0"            <Project Sdk="Microsoft.NET.Sdk">
  xmlns="...msbuild/2003">               <PropertyGroup>
  <PropertyGroup>                          <OutputType>Exe</OutputType>
    <OutputType>Exe</OutputType>           <TargetFramework>net10.0</TargetFramework>
    <TargetFrameworkVersion>v4.8           <Nullable>enable</Nullable>
      </TargetFrameworkVersion>          </PropertyGroup>
  </PropertyGroup>                       <ItemGroup>
  <ItemGroup>                              <PackageReference Include="Newtonsoft.Json"
    <Reference Include="Newtonsoft.Json      Version="13.0.3" />
      Version=13.0.0.0 ...">             </ItemGroup>
      <HintPath>..\packages\...\       </Project>
        Newtonsoft.Json.dll</HintPath>
    </Reference>
  </ItemGroup>
  <ItemGroup>
    <Compile Include="Program.cs" />
    <Compile Include="Helpers.cs" />
  </ItemGroup>
</Project>
+ packages.config (separate file)
```

## 5. API Compatibility Shims & Breaking Changes

### The Two Categories of Breaking Changes

**Removal with replacement:** The API was removed because it was unsafe, blocking, or cross-platform-incompatible. A different API achieves the same goal with better semantics. The work is a code change with a clear target.

**Removal without a compatible shim:** The API provided a Windows-specific behavior that has no cross-platform equivalent. If the application is Windows-only, `Microsoft.Windows.Compatibility` may restore the API. If cross-platform is required, the feature must be redesigned.

### Removed APIs and Their Replacements

| Removed / Changed API | Removed in | Category | Replacement | Notes |
|---|---|---|---|---|
| `BinaryFormatter` | .NET 9 (throws `NotSupportedException`) | Serialization | `System.Text.Json`, `MessagePack`, `Google.Protobuf` | Fundamental security risk: deserialization gadget chains allow arbitrary code execution; removal is intentional and permanent |
| `Thread.Abort()` | .NET Core 3.0 (`PlatformNotSupportedException`) | Threading | `CancellationToken` cooperative cancellation | Injected exceptions at unpredictable points; could corrupt shared state mid-write or inside `finally` blocks |
| `AppDomain.CreateDomain()` | .NET Core 1.0 | Isolation | `AssemblyLoadContext` | Process-level isolation is the correct replacement for true sandbox scenarios |
| `System.Web.*` | .NET Core 1.0 | Web | `Microsoft.AspNetCore.Http` | Entire namespace removed; no shim restores it fully — use `SystemWebAdapters` for incremental migration |
| `System.Runtime.Remoting.*` | .NET Core 1.0 | RPC | gRPC (`Grpc.AspNetCore`) or SignalR | Remoting used opaque binary channels; gRPC is the structured equivalent |
| `WebClient` | .NET 6 (marked obsolete) | HTTP | `HttpClient` | `WebClient` wraps `HttpClient` internally on .NET 6+; direct use is preferred for control |
| `System.Drawing.Common` on Linux | N/A — runtime fault | Graphics | SkiaSharp, `SixLabors.ImageSharp` | Depends on `libgdiplus` native library; unreliable in Linux containers; not available on macOS by default |

### Why `BinaryFormatter` Was Removed

`BinaryFormatter` deserializes the object graph described by the byte stream it receives. It calls constructors and property setters as dictated by the incoming data, with no validation that the resulting object graph is safe. A carefully crafted byte stream can cause `BinaryFormatter` to instantiate any type on the machine and call methods on it during deserialization — a **deserialization gadget chain**. This class of vulnerability has produced multiple critical CVEs. The removal is permanent and by design.

The replacement choice depends on the use case:
- **Human-readable, schema-flexible:** `System.Text.Json` (built-in) or `Newtonsoft.Json`
- **Compact binary, cross-language:** `Google.Protobuf` or `MessagePack-CSharp`
- **Compact binary, .NET-only:** `MessagePack-CSharp` with `[MessagePackObject]` attributes

When migrating stored `BinaryFormatter` data, there is no automatic converter. The migration strategy is to deserialize the legacy data using the old `BinaryFormatter` code on .NET Framework, then re-serialize it in the new format, then deploy the new format reader.

### Why `Thread.Abort()` Was Removed

`Thread.Abort()` injects a `ThreadAbortException` into the target thread at whatever instruction pointer the thread happens to be executing at the moment the OS delivers the signal. This can occur:
- Inside a `lock` body, leaving the lock acquired and the protected resource in an inconsistent state
- Between a null check and a dereference, producing a `NullReferenceException` on the next line
- Inside a `finally` block that was cleaning up resources

The fundamental problem is that no code can be written to be safe against asynchronous exception injection without wrapping every statement in a `try/catch`. Cooperative cancellation via `CancellationToken` is safe because the worker decides when to check the token — always at a point where it is in a consistent state and can exit cleanly.

### Compatibility NuGet Packages

Microsoft ships several packages that restore .NET Framework APIs on net10.0 without requiring immediate redesign:

| Package | What it provides | Scope |
|---|---|---|
| `Microsoft.Windows.Compatibility` | 20,000+ Windows-only APIs: Registry, EventLog, WMI, Windows Cryptography | Windows-deployed apps only; throws `PlatformNotSupportedException` on Linux/macOS |
| `System.Configuration.ConfigurationManager` | `ConfigurationManager.AppSettings`, `ConnectionStrings`, `ConfigurationSection` | Any OS; reads `app.config` / `app.exe.config` |
| `Microsoft.AspNetCore.SystemWebAdapters` | `System.Web.HttpContext` compatibility surface on ASP.NET Core | Incremental Web Forms / ASP.NET MVC → ASP.NET Core migration |
| `System.Drawing.Common` | `System.Drawing` types on net10.0 | Short-term bridge; requires `libgdiplus` on Linux — unreliable in containers |
| `Microsoft.Bcl.AsyncInterfaces` | `IAsyncEnumerable<T>` backport for net48 | net48 library consumers of async streams |

**These are bridges, not destinations.** The long-term migration goal is to remove each shim package once the corresponding API has been replaced natively. Leaving shim packages in place indefinitely accumulates technical debt and — in the case of `Microsoft.Windows.Compatibility` — ties deployment to Windows.

**`System.Configuration.ConfigurationManager` vs `IConfiguration`:** The shim restores the old static API (`ConfigurationManager.AppSettings["key"]`). The `IConfiguration` system from `Microsoft.Extensions.Configuration` is the idiomatic Modern .NET approach: it supports multiple providers (JSON files, environment variables, Azure Key Vault, command-line args), is injected via DI, and has no static state. Migrating to `IConfiguration` is the correct long-term path; the shim buys time.

### Windows-Only API Guard Pattern

When using `Microsoft.Windows.Compatibility` on a cross-platform target, guard calls to Windows-only APIs with a runtime OS check:

`RuntimeInformation.IsOSPlatform(OSPlatform.Windows)` — evaluates at runtime, always safe to call on any OS.

For Roslyn-level enforcement, annotate methods that call Windows-only APIs with `[SupportedOSPlatform("windows")]`. The analyzer then warns callers on non-Windows targets — catching the mistake at compile time rather than at runtime.

## 6. Nullable Reference Types — Opt-In Safety Net

### The .NET Framework Problem

In .NET Framework, every reference type is implicitly nullable. The compiler has no way to distinguish a variable that intentionally holds `null` from one that should never be `null`. The only signal that a null was dereference is a `NullReferenceException` at runtime — historically the most common production exception in .NET applications. The compiler emitted no warnings; the developer had no static aid.

### What Nullable Reference Types (NRTs) Provide

NRTs (introduced in C# 8, enabled per-project) add a nullability layer to the type system:

- `string` (non-nullable): the compiler tracks null flow and warns if a value that could be null is assigned to this type or if a method is called on a value that could be null
- `string?` (nullable): explicitly signals that null is expected and permitted here; the compiler requires a null check before dereferencing

This is **compile-time static analysis only** — the CLR does not enforce nullability at runtime. A `string` annotated as non-nullable can still receive `null` from reflection, `JsonSerializer`, or interop with code that predates NRT annotations. NRTs catch mistakes in code you write; they do not catch surprises from external inputs.

### Enabling NRTs Safely in Brownfield Code

Enabling NRTs in a large existing codebase typically surfaces hundreds or thousands of warnings immediately. The recommended migration path has three stages:

**Stage 1 — Warnings mode:**
```xml
<Nullable>warnings</Nullable>
```
Produces the same diagnostics as `enable` but as warnings, not errors. Compilation succeeds. This stage lets the team assess the scope without blocking the build.

**Stage 2 — File-level opt-in with `#nullable enable`:**
Individual files most in need of null safety can be opted in selectively. Files not yet addressed use `#nullable disable` or the project default. The `#nullable restore` pragma reverts to the project-level setting.

**Stage 3 — Project-wide enforcement:**
```xml
<Nullable>enable</Nullable>
```
`string` is non-nullable everywhere. All null violations are warnings. Adding `<WarningsAsErrors>Nullable</WarningsAsErrors>` or `<TreatWarningsAsErrors>true</TreatWarningsAsErrors>` promotes them to errors, making null violations a build blocker.

### The Null-Forgiving Operator (`!`)

`name!` suppresses the nullable warning on `name` for that expression. It is an escape hatch — it tells the compiler "I assert this is non-null; trust me." The compiler accepts the assertion without verifying it.

Every `!` is a suppression, not a proof of safety. If the assertion is wrong, the runtime `NullReferenceException` still occurs. Rules for responsible use:

- Accompany every `!` with a comment explaining the invariant that makes it safe
- Audit `!` usage in code reviews — a high density of `!` operators means NRTs are enabled in name only
- Prefer explicit null checks or guard clauses over `!` wherever the assertion is not immediately obvious from context

### Nullability Annotations in APIs

When migrating a library's public API, adding NRT annotations is a technically non-breaking change (the annotations are metadata; the runtime behavior is unchanged). However, **consumers** who have NRTs enabled will receive new warnings when they call your API — previously silent `null` returns from your methods now carry a `?` annotation that requires handling. Treat this as a minor breaking change in practice; announce it in release notes.

### Boundary Validation Remains Required

NRTs do not eliminate the need for null validation at trust boundaries:

- `JsonSerializer.Deserialize<T>()` can return `null` if the JSON is `"null"` — even if `T` is declared as a non-nullable reference type
- Reflection-based construction bypasses the compiler's null tracking
- Interop with `COM`, `P/Invoke`, or pre-NRT libraries returns unannotated values

At external boundaries (HTTP request deserialization, database result mapping, file parsing), validate for null explicitly regardless of what the type annotation says.

## 7. Multi-Targeting and Preprocessor Guards

### When Multi-Targeting Applies

Multi-targeting — building a single project for multiple Target Framework Monikers (TFMs) in one `dotnet build` invocation — is a **library concern**, not an application concern. Applications should target one TFM: the runtime they deploy to. Libraries have consumers on different runtimes and need to serve them all.

The key use case: a shared utility library that serves enterprise consumers still on .NET Framework 4.8 and new consumers on net10.0. Multi-targeting lets the same library ship both an optimized net10.0 implementation and a compatible net48 fallback in a single NuGet package.

### Multi-Target Project Declaration

`<TargetFrameworks>` (plural) triggers multi-targeting. Each semicolon-separated TFM produces a separate output directory and a separate NuGet asset:

```xml
<TargetFrameworks>net10.0;net48</TargetFrameworks>
```

This builds `bin\Debug\net10.0\` and `bin\Debug\net48\`. When packed as a NuGet package, consumers on net10.0 get the net10.0 output; consumers on net48 get the net48 output — NuGet's TFM compatibility matching resolves this automatically.

### Preprocessor Symbols Defined by the SDK

The SDK defines compile-time preprocessor symbols for the current TFM being compiled. These drive `#if` guards in source code:

| Symbol | When defined | Precision |
|---|---|---|
| `NET10_0_OR_GREATER` | net10.0, net11.0, net12.0, … | Family — survives future versions |
| `NET10_0` | Exactly net10.0 | Exact — must be updated when new version ships |
| `NETFRAMEWORK` | net48, net472, net461, net45, … (any Framework) | Family — all Framework TFMs |
| `NET48` | Exactly net48 | Exact — does not match net472 or net461 |
| `NETSTANDARD2_0` | Exactly netstandard2.0 | Exact |
| `NETCOREAPP` | Any .NET Core 1.0–3.1 TFM | Legacy — does not cover net5+ |

**Critical precision distinction:**
- Use `NETFRAMEWORK` (not `NET48`) when you mean "any .NET Framework target" — it stays correct as you add `net472` or `net461` to the TFM list
- Use `NET10_0_OR_GREATER` (not `NET10_0`) when you mean "net10.0 and everything after" — prevents needing an update when .NET 11 ships
- Use exact symbols (`NET48`, `NET10_0`) only when the code path is specific to that exact version

### `#if` vs `[SupportedOSPlatform]` — Choosing the Right Tool

`#if WINDOWS` with preprocessor guards removes code at compile time — the non-Windows code path simply does not exist in the non-Windows binary. This is appropriate when the API itself is unavailable on other platforms (P/Invoke signatures, COM calls).

`[SupportedOSPlatform("windows")]` and `[UnsupportedOSPlatform("linux")]` are runtime annotations that inform the Roslyn platform compatibility analyzer. The code exists in all compiled outputs, but the analyzer warns callers on unsupported platforms. This is appropriate when the API is available on all platforms but the behavior differs, or when the call is behind a runtime OS check and the developer needs to document that explicitly.

Prefer annotations over `#if` for platform-specific behavior differences; reserve `#if` for compile-time elimination of genuinely unavailable APIs.

### `netstandard2.0` as a Multi-Target Option

Adding `netstandard2.0` to the TFM list makes the library consumable by the widest possible set of runtimes (net461+, netcoreapp2.0+, net5+). The tradeoff: the netstandard2.0 implementation cannot use any Modern .NET-specific APIs (no `Span<T>` in BCL, no `System.Text.Json`, no `IAsyncEnumerable<T>`). It is a compatibility target, not a performance target.

A common multi-target triple for broad compatibility:
```xml
<TargetFrameworks>net10.0;netstandard2.0;net48</TargetFrameworks>
```

`net10.0` consumers get the optimized implementation. `net48` consumers get the Framework implementation. `netstandard2.0` covers anything in between that matches neither.

### When NOT to Multi-Target

- **Applications:** apps deploy to one runtime — no need for multiple TFMs
- **Libraries with no .NET Framework consumers:** target `net10.0` only; don't add `net48` out of habit
- **Proof-of-concept / prototype code:** multi-targeting adds build complexity that is not worth the cost for exploratory work
- **After `net48` consumers have migrated:** drop the `net48` TFM; the build simplifies

## 8. Quick Reference

### Migration Step Checklist (Ordered)

1. Run `upgrade-assistant analyze MySolution.sln` — read the full compatibility report before touching any code
2. Identify architectural blockers: Web Forms → Razor Pages / Blazor; WCF server → gRPC; Remoting → gRPC / SignalR — budget these as separate workstreams
3. Choose migration strategy: lift-and-shift for small solutions; incremental (library-first) or Strangler Fig for large solutions
4. Convert project files to SDK-style: delete `packages.config`, convert `<Reference>` to `<PackageReference>`, remove `<Compile Include>` items
5. Change `<TargetFrameworkVersion>v4.8</TargetFrameworkVersion>` to `<TargetFramework>net10.0</TargetFramework>`
6. Add compatibility shim packages as temporary bridges: `System.Configuration.ConfigurationManager`, `Microsoft.Windows.Compatibility`, `Microsoft.AspNetCore.SystemWebAdapters` as needed
7. Replace removed APIs: `BinaryFormatter` → `System.Text.Json`; `Thread.Abort()` → `CancellationToken`; `AppDomain.CreateDomain()` → `AssemblyLoadContext`
8. Enable `<Nullable>warnings</Nullable>` — assess scope; fix null warnings; promote to `<Nullable>enable</Nullable>`
9. Run the full test suite on net10.0; compare behavior against the net48 baseline
10. Profile with `dotnet-trace` and `dotnet-counters` to confirm the expected performance improvement
11. Plan removal of compatibility shim packages — each shim removal is a discrete future task
12. Set `<TreatWarningsAsErrors>true</TreatWarningsAsErrors>` to enforce code quality going forward
