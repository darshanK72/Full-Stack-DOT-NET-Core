# CLI, Architecture & Components

## Why It Matters

Every .NET developer runs `dotnet build` and `dotnet run` daily, but few understand what each command does under the hood, what separates an SDK from a Runtime, or why a published app behaves differently from a locally-built one. Understanding the CLI architecture and its surrounding components lets you reason about build failures, deployment packages, cross-platform behavior, and tool installation without guessing. These topics surface directly in technical interviews: SDK vs Runtime, BCL layering, and AppDomain isolation consistently distinguish candidates who understand the platform from those who only use it.

## Section 1: dotnet CLI — The Build Orchestrator

The `dotnet` CLI is the single entry point for the entire .NET development lifecycle. It is not a compiler itself — it is an orchestrator that delegates to specialised sub-systems depending on which command you run: MSBuild coordinates the build graph, Roslyn compiles C# to IL, NuGet resolves and downloads packages, and the publish pipeline applies post-compilation transforms such as trimming, ReadyToRun pre-compilation, and single-file bundling.

Understanding which sub-system each command invokes explains why some operations are slow, why some produce artifacts suitable for deployment and others do not, and why the same source can produce very different binaries depending on the flags used.

### The Pipeline Behind Each Command

When you run `dotnet build`, the CLI invokes MSBuild with the project file. MSBuild reads the `.csproj`, evaluates property and item groups, triggers an implicit `dotnet restore` if needed, calls the Roslyn compiler to produce IL in `obj/`, then copies the results to `bin/`. The output is optimised for a local development loop — unstripped, with PDB symbol files, and referencing the shared framework by name rather than embedding it.

When you run `dotnet publish`, MSBuild runs an extended pipeline that includes post-build targets: the IL linker (trimmer) removes unused code, ReadyToRun cross-compilation can pre-JIT hot paths, and single-file bundling wraps everything into one executable. The output is self-contained or framework-dependent depending on flags, but in either case it is the artifact that belongs on a server — never the `bin/` output of a plain build.

`dotnet run` is deliberately a development shortcut: it rebuilds the app from source on every invocation and then launches it in-process. It is not a production launcher. For production you always run the published executable directly or via `dotnet exec`.

`dotnet watch run` wraps `dotnet run` with a file-system watcher. When any tracked file changes, it terminates the running process, rebuilds, and restarts — or applies hot-reload if the change is compatible. Hot-reload can apply method body changes without a full restart, but structural changes (adding fields, changing signatures) always trigger a full rebuild.

### dotnet CLI Command Reference

| Command | What it does | Key flags | When to use |
|---|---|---|---|
| `dotnet new <template>` | Scaffold a project from a built-in or installed template | `--name`, `--output`, `--framework net10.0` | Starting any new project or item |
| `dotnet restore` | Download NuGet packages listed in `.csproj` / `packages.lock.json` | `--locked-mode`, `--no-cache` | Explicitly before a build in CI; implicitly called by `build` |
| `dotnet build` | Compile source to IL (implies restore) | `-c Release`, `--no-restore`, `--no-incremental` | Local compile-check and test runs |
| `dotnet run` | Build then execute the app in one step | `--no-build`, `--project <path>`, `-- <app-args>` | Inner dev loop only |
| `dotnet watch run` | Rebuild and hot-reload on file save | `--no-hot-reload` | Active development where you want instant feedback |
| `dotnet publish` | Produce deployment-ready output | `-r <RID>`, `--self-contained`, `-c Release` | Producing any artifact for a server or container |
| `dotnet test` | Discover and run unit tests via a test adapter | `--filter <expr>`, `--collect "Code Coverage"` | Running tests locally or in CI |
| `dotnet pack` | Create a NuGet `.nupkg` from a library project | `--no-build`, `-o <outDir>` | Releasing a NuGet package |
| `dotnet clean` | Delete `bin/` and `obj/` directories | `-c Release` | Forcing a full rebuild; clearing stale assets |
| `dotnet tool install` | Install a dotnet CLI tool package | `-g` (global), `--version` | Adding code generators, formatters, linters |
| `dotnet tool restore` | Install local tools from the manifest | — | CI pipeline setup; first clone of a repo |
| `dotnet --info` | Print SDK version, runtime, host path, installed RIDs | — | Diagnosing version or path mismatches |
| `dotnet --list-sdks` | Enumerate installed SDK versions | — | Checking what is installed on a machine |
| `dotnet --list-runtimes` | Enumerate installed runtime versions | — | Confirming a server has the right runtime |

### dotnet build vs dotnet publish

This distinction is the most common interview question in this space. The differences are not cosmetic:

- `dotnet build` targets the local development feedback loop. Output lives in `bin/<config>/<tfm>/`. Symbol files are present. The app references the shared framework by name, so the shared framework must be installed on the machine that runs it.
- `dotnet publish` targets deployment. Output lives in `bin/<config>/<tfm>/publish/`. It can be self-contained (runtime bundled, no .NET installation needed) or framework-dependent (smaller, but requires a matching runtime on the target). Publish also triggers trimming, ReadyToRun, and single-file bundling if configured.

Never deploy the output of `dotnet build`. Always deploy the output of `dotnet publish`.

### dotnet run vs dotnet watch run

- `dotnet run` triggers a full restore + build on every invocation, then launches the process. Use `--no-build` to skip the build when you know nothing changed.
- `dotnet watch run` adds a file-system watcher around `dotnet run`. It monitors tracked files (controlled by `<Watch>` MSBuild items) and either hot-reloads compatible changes or restarts from scratch. Use this during active development to eliminate the manual re-run cycle.

## Section 2: SDK vs Runtime vs ASP.NET Core Runtime

The three .NET distribution packages are frequently confused because they sound similar and the SDK ships with everything the others contain. The key insight is that they are a strict superset chain: SDK ⊃ ASP.NET Core Runtime ⊃ .NET Runtime.

### What Each Package Contains

The **.NET SDK** is the developer package. It bundles the Roslyn compiler, the `dotnet` CLI, MSBuild and its target files, NuGet tooling, BCL reference assemblies, source generators, and a full .NET Runtime. Everything you need to write, build, test, and publish an app. Install the SDK on developer machines and CI build agents.

The **.NET Runtime** (also called the CoreCLR runtime package) is the minimum required to *execute* a compiled .NET app. It contains the JIT compiler, the garbage collector, the thread pool, and the Base Class Library. It does not include Roslyn, the CLI, or MSBuild. Production servers that host pre-published apps need only this package — installing the full SDK on a server wastes disk space and expands the attack surface.

The **ASP.NET Core Runtime** is the .NET Runtime plus the ASP.NET Core framework assemblies: Kestrel, the middleware pipeline, MVC, Razor, SignalR, and the `Microsoft.AspNetCore.*` namespaces. It is the smallest installation that can host a web application or REST API. It still does not include the compiler or CLI.

### Package Comparison Table

| Package | Contains | Install for... | Approx. size |
|---|---|---|---|
| .NET SDK | Compiler (Roslyn) + CLI + MSBuild + ASP.NET Core Runtime + .NET Runtime | Dev machines, CI build agents | ~700 MB |
| ASP.NET Core Runtime | .NET Runtime + Kestrel + ASP.NET Core middleware | Prod servers: web apps, APIs | ~35 MB |
| .NET Runtime | CLR (JIT + GC) + BCL | Prod servers: console apps, workers | ~25 MB |

On a developer machine install the **SDK only** — it already contains both runtimes. On a production server install only the smallest runtime that covers your app type. If a server only runs published apps, it never needs the compiler.

### global.json — Pinning the SDK Version

`global.json` pins the SDK version used in a directory tree. Place it at the repository root so every developer and CI agent resolves the same SDK version regardless of how many SDK versions are installed on the machine.

```json
{
  "sdk": {
    "version": "10.0.100",
    "rollForward": "latestPatch"
  }
}
```

The `rollForward` property controls how version mismatches are handled when the pinned version is not installed:

| rollForward value | Behaviour |
|---|---|
| `disable` | Fail if the exact version is not installed |
| `patch` | Allow higher patch within the same feature band |
| `latestPatch` | Use the highest patch within the same feature band |
| `minor` | Allow higher minor within the same major |
| `latestMinor` | Use the highest minor within the same major |
| `major` | Allow any higher version |
| `latestMajor` | Use the highest installed version |

`latestPatch` is the recommended default for teams: it tolerates security-patch updates without breaking the build, but it will not silently upgrade to a new feature band with potentially breaking changes.

### Self-Contained vs Framework-Dependent Publish

These two publish modes represent a trade-off between portability and binary size.

**Framework-dependent** (the default): the published output does not include the .NET runtime. The target machine must have a compatible runtime installed. Binaries are small — typically a few hundred kilobytes for the app DLLs — because all framework code comes from the shared installation.

**Self-contained**: the published output bundles the entire .NET runtime alongside the app DLLs. No .NET installation is needed on the target. The downside is size (50–200 MB depending on trimming settings) and the fact that runtime security patches are not automatically picked up — you must rebuild and redeploy.

Enable self-contained with `-r <RID> --self-contained true` on `dotnet publish`. Trimming can reduce binary size significantly but requires testing, as it removes code paths the analyzer cannot prove are reachable.

## Section 3: Base Class Library (BCL) Architecture

The BCL is the set of APIs shipped as part of the .NET platform itself — not as separate NuGet packages you opt into. It is not a flat collection of assemblies; it is a deliberate layer cake. Understanding the layers lets you predict which types are always available in any .NET app and which require a `<PackageReference>`.

### The Layer Model

```
┌─────────────────────────────────────────────────────────────┐
│  Layer 5: App model assemblies                              │
│  ASP.NET Core · MAUI · Blazor · WPF · WinForms             │
│  (SDK-variant-specific; not available in all project types) │
├─────────────────────────────────────────────────────────────┤
│  Layer 4: Microsoft.Extensions.*                            │
│  DI · Configuration · Logging · Hosting                     │
│  (ship with SDK on net10.0; also available as NuGet pkgs)   │
├─────────────────────────────────────────────────────────────┤
│  Layer 3: BCL subsystem assemblies                          │
│  System.Net.Http · System.Text.Json · System.IO.FileSystem  │
│  System.Collections.Immutable · System.Linq · …            │
│  (ship with every .NET runtime; no PackageReference needed) │
├─────────────────────────────────────────────────────────────┤
│  Layer 2: System.Runtime (public facade)                    │
│  Re-exports the public surface of System.Private.CoreLib    │
│  (stable public API contract)                               │
├─────────────────────────────────────────────────────────────┤
│  Layer 1: System.Private.CoreLib                            │
│  object · string · int · Span<T> · GC · Thread              │
│  (compiled into the runtime itself; not directly referenced)│
└─────────────────────────────────────────────────────────────┘
```

### Layer-by-Layer Explanation

**Layer 1 — `System.Private.CoreLib`**: The lowest-level layer, compiled directly into the CoreCLR runtime binary. It defines `object`, `string`, all primitive value types, `Span<T>`, `Memory<T>`, and the core threading primitives. You cannot reference this assembly by name in a project file — the runtime injects it automatically. It is the layer that cannot be substituted or mocked.

**Layer 2 — `System.Runtime` (facade)**: A thin reference assembly that re-exports the public surface of `System.Private.CoreLib`. When you write `using System;` in a project, the compiler resolves types against this facade. The split exists so the public API contract remains stable even as the internal implementation moves between runtime versions. This is the "public face" of the BCL.

**Layer 3 — Subsystem assemblies**: Each functional area ships in its own assembly. `System.Net.Http` contains `HttpClient`, `System.Text.Json` contains `JsonSerializer`, `System.IO.FileSystem` handles file I/O, `System.Linq` provides LINQ operators. These ship with every .NET runtime and require no `<PackageReference>` when targeting `net10.0`.

**Layer 4 — `Microsoft.Extensions.*`**: The hosting, dependency injection, configuration, and logging abstractions that power ASP.NET Core and the Generic Host. On `net10.0` these ship with the SDK, but they are versioned and released separately and can also be installed as NuGet packages into older TFM projects. The key point: they are *not* strictly part of the BCL, even though they feel like platform code.

**Layer 5 — App model assemblies**: ASP.NET Core, MAUI, Blazor, WPF, WinForms. These are activated by choosing the correct SDK variant in the `.csproj` (`Microsoft.NET.Sdk.Web`, `Microsoft.NET.Sdk.Maui`, etc.) and are not available outside their target project types.

### System.* vs Microsoft.Extensions.* vs NuGet-only

A practical rule of thumb for deciding whether a type needs a `<PackageReference>`:

- `System.*` namespace → part of the BCL (Layer 2 or 3); no `PackageReference` needed on `net10.0`
- `Microsoft.Extensions.*` namespace → ships with the SDK on `net10.0`, but technically a NuGet package; add a `PackageReference` when targeting older TFMs
- `Newtonsoft.Json`, `AutoMapper`, `Dapper`, etc. → third-party NuGet; always requires an explicit `PackageReference`

### Pitfalls

**`Microsoft.Extensions.Logging` is not in the BCL.** It ships with the SDK on `net10.0`, so you often do not need an explicit package reference in a new project, but it is not guaranteed available the way `System.Console` is. In a class library targeting `net10.0` without the web SDK, you must add `<PackageReference Include="Microsoft.Extensions.Logging.Abstractions" />` explicitly.

**Adding a redundant `PackageReference` for BCL types.** Adding `<PackageReference Include="System.Text.Json" />` on `net10.0` is harmless but redundant. The compiler resolves the type from the SDK reference assembly first. However, pinning a specific NuGet version can cause subtle mismatches if it conflicts with what the runtime loads — avoid it unless you need an API not yet in your SDK version.

## Section 4: AppContext and AppDomain

`AppContext` and `AppDomain` both expose metadata about the execution environment, but they serve different purposes and have very different lifetimes in .NET Core vs .NET Framework.

### AppContext — Ambient Application Data

`AppContext` is a static class that provides stable, ambient information about the executing application context. Its data is fixed at startup and is safe to read from any thread without synchronization.

**`AppContext.BaseDirectory`** returns the directory containing the executing assembly's `.dll` or `.exe`. This is the correct anchor for constructing paths to files that ship alongside your app — configuration files, templates, embedded resources. Do not use `Directory.GetCurrentDirectory()` for this purpose: the working directory is a process-level mutable property that can be changed by any code at any time and does not necessarily point to the app's installation folder.

```csharp
string configPath = Path.Combine(AppContext.BaseDirectory, "appsettings.json");
```

**`AppContext.TargetFrameworkName`** returns the TFM the assembly was compiled for, such as `.NETCoreApp,Version=v10.0`. This matches the `<TargetFramework>net10.0</TargetFramework>` in your `.csproj` and is useful in diagnostic output and multi-targeting code.

**`AppContext.GetData(key)` / `SetData(key, value)`** provide a process-wide key-value store for ambient configuration. Frameworks use this channel to communicate settings without tight coupling — for example, `System.Net.Http` reads switch keys to opt in or out of behaviors. Application code rarely writes to this store directly.

### AppDomain — From Isolation to Single Domain

In .NET Framework, `AppDomain` was the isolation unit below the process. You could create multiple domains, load assemblies into them, and then unload those domains to release the assemblies — without restarting the process. This was used by plugin hosts, ASP.NET (one AppDomain per web application), and test runners.

.NET Core removed multi-domain isolation entirely. There is exactly **one** `AppDomain` per process in .NET Core/.NET 5+. The reasons were performance (domain transitions were expensive), portability (the model did not map cleanly to non-Windows platforms), and architectural cleanliness (the isolation was leaky in practice). `AppDomain.CreateDomain()` throws `PlatformNotSupportedException` at runtime.

The replacement for assembly isolation in .NET Core is `System.Runtime.Loader.AssemblyLoadContext`. A custom `AssemblyLoadContext` can load assemblies in a private context and be unloaded when all references to it are released. This covers the plugin and hot-reload use cases without the overhead of a full domain boundary.

**What `AppDomain.CurrentDomain` still provides:**

- `FriendlyName`: the friendly name of the single domain (matches the entry assembly name)
- `Id`: always `1` in .NET Core — there is only ever one domain
- `GetAssemblies()`: returns a snapshot of all assemblies currently loaded into the process; useful for diagnostics, plugin enumeration, and reflection-based frameworks
- `UnhandledException` event: a last-chance handler for unhandled exceptions on any thread
- `BaseDirectory`: equivalent to `AppContext.BaseDirectory` — inherited for compatibility

```csharp
// Id is always 1 in .NET Core.
int domainId = AppDomain.CurrentDomain.Id;

// Snapshot of loaded assemblies grows as the JIT touches new code.
Assembly[] loaded = AppDomain.CurrentDomain.GetAssemblies();
```

### Pitfalls

**`AppContext.BaseDirectory` is not the working directory.** `AppContext.BaseDirectory` points to where the app's binaries live. `Directory.GetCurrentDirectory()` (or `Environment.CurrentDirectory`) points to the directory from which the process was launched, which the user or a script can set arbitrarily. For paths to app assets, always use `AppContext.BaseDirectory`. For user-facing relative paths in CLI tools, `Directory.GetCurrentDirectory()` is correct.

**`AppDomain.CreateDomain()` throws on .NET Core.** Code ported from .NET Framework that creates domains will compile successfully (the method signature still exists) but will throw `PlatformNotSupportedException` at runtime. The migration path is `AssemblyLoadContext`.

## Section 5: Process, Environment & Platform Detection

The `Environment` class and `RuntimeInformation` together cover all the process-level and OS-level metadata an application typically needs. They address different concerns: `Environment` is about the running process and operating system state; `RuntimeInformation` is about the .NET runtime's identity and the hardware architecture.

### Environment — Process and OS State

`Environment` is a static class in `System` that exposes:

| Property | What it returns | Example value |
|---|---|---|
| `Environment.Version` | CLR version as `System.Version` | `10.0.1` |
| `Environment.ProcessPath` | Full path to the process executable | `C:\app\myapp.exe` |
| `Environment.CurrentDirectory` | Working directory (mutable) | `C:\Users\dev\projects` |
| `Environment.MachineName` | Hostname of the machine | `PROD-SERVER-01` |
| `Environment.Is64BitProcess` | Whether the current process is 64-bit | `true` |
| `Environment.Is64BitOperatingSystem` | Whether the OS kernel is 64-bit | `true` |
| `Environment.ProcessorCount` | Logical CPU count visible to the process | `8` |
| `Environment.OSVersion` | OS platform and version | `Microsoft Windows NT 10.0.26100.0` |

`Is64BitProcess` and `Is64BitOperatingSystem` can differ: a 32-bit process can run on a 64-bit OS (WOW64 on Windows). `ProcessorCount` reflects the CPUs allocated to the process, which in containers may be fewer than the physical machine has.

### RuntimeInformation — Runtime and Architecture Identity

`RuntimeInformation` lives in `System.Runtime.InteropServices` and focuses on the .NET runtime's identity and the hardware it is running on:

| Property | What it returns | Example value |
|---|---|---|
| `RuntimeInformation.FrameworkDescription` | Runtime name and version string | `.NET 10.0.1` |
| `RuntimeInformation.OSDescription` | OS name and version | `Microsoft Windows 10.0.26100` |
| `RuntimeInformation.OSArchitecture` | Architecture of the OS kernel | `X64` |
| `RuntimeInformation.ProcessArchitecture` | Architecture of the current process | `X64` |
| `RuntimeInformation.RuntimeIdentifier` | RID of the running process | `win-x64` |

`OSArchitecture` and `ProcessArchitecture` can differ: on Apple Silicon Macs running Rosetta 2, `OSArchitecture` is `Arm64` but `ProcessArchitecture` may be `X64` if the process is a x64 binary being translated.

### Platform Detection: Runtime vs Compile-Time

Two mechanisms exist for platform-conditional logic, and they operate at entirely different stages:

**`RuntimeInformation.IsOSPlatform(OSPlatform.X)`** is a **runtime** check. It interrogates what the host process reports about the current OS and evaluates to `true` or `false` at the moment the line executes. This is the correct mechanism to guard platform-specific code paths inside a single cross-platform binary:

```csharp
if (RuntimeInformation.IsOSPlatform(OSPlatform.Windows))
    // call a Windows-only API
```

**TFM suffix `-windows`** and **`[SupportedOSPlatform("windows")]`** are **compile-time** constraints enforced by the Roslyn platform compatibility analyzer. The TFM suffix (`net10.0-windows`) tells the compiler that this whole project targets Windows and unlocks Windows-specific APIs like `System.Windows.Forms`. The `[SupportedOSPlatform]` attribute marks individual APIs as platform-specific and causes the analyzer to emit a warning if a cross-platform caller uses them without a runtime guard.

Use both: the TFM suffix to restrict the entire project, the `[SupportedOSPlatform]` attribute to annotate individual APIs in a multi-target library, and `IsOSPlatform` to write the actual runtime branch in shared code. The analyzer and the runtime check are complementary — the analyzer catches the mistake at build time; `IsOSPlatform` executes the correct branch at runtime.

### Runtime Identifiers (RIDs)

A Runtime Identifier is a string code that identifies a specific OS + CPU architecture combination. RIDs are used by `dotnet publish -r <RID>` to select native assets, resolve native NuGet dependencies, and name the output folder. They follow the pattern `<os>-<arch>` or `<os>.<version>-<arch>` for more specific targeting:

| RID | Meaning |
|---|---|
| `win-x64` | Windows, 64-bit x86 |
| `win-arm64` | Windows, ARM64 |
| `linux-x64` | Linux, 64-bit x86 |
| `linux-arm64` | Linux, ARM64 (Raspberry Pi 4, server ARM) |
| `osx-x64` | macOS, Intel x86 |
| `osx-arm64` | macOS, Apple Silicon (M1/M2/M3) |
| `linux-musl-x64` | Linux with musl libc (Alpine containers) |

`RuntimeInformation.RuntimeIdentifier` returns the RID the current process was published for. For a framework-dependent app this may be a generic RID; for a self-contained app it matches the `-r` flag used at publish time.

## Section 6: Global Tools & Local Tools

The `dotnet tool` subsystem lets you install .NET-based command-line utilities distributed as NuGet packages. There are two installation scopes with fundamentally different behavior, and confusing them is a common source of CI failures.

### Global Tools

`dotnet tool install -g <package-id>` installs a tool globally for the **current user**. The binaries are written to `~/.dotnet/tools` on all platforms, and that directory is expected to be on the system `PATH`.

Because the installation lives in the user's home directory, global tools are **user-specific**. A tool installed under one user account is not available to another user on the same machine. This catches teams out in CI when a developer installed a tool manually under an administrator account but the CI agent runs as a restricted service account — the tool is "installed" on the machine but not on the `PATH` of the CI user.

### Local Tools

`dotnet tool install <package-id>` without `-g` installs a tool into a project or repository scope, governed by a manifest file.

The workflow:
1. Create the manifest once: `dotnet new tool-manifest` — writes `.config/dotnet-tools.json` at the current directory.
2. Add tools: `dotnet tool install <package-id>` — adds an entry to the manifest but does **not** install the binary.
3. Install from manifest: `dotnet tool restore` — reads the manifest and downloads + installs the binaries.

The manifest file must be committed to source control. The binary directories should not be. Anyone who clones the repository (or a CI agent checking out the code) must run `dotnet tool restore` before invoking any local tool.

### Tool Resolution Order

When you invoke a tool name on the command line, .NET resolves it in this order:

1. Local manifest (`.config/dotnet-tools.json` in the current directory or any ancestor)
2. Global PATH (`~/.dotnet/tools`)

If the same tool is installed both locally and globally, the local version wins. This allows a project to pin a specific tool version without affecting other projects on the same machine.

### Tool Management Commands

| Command | What it does |
|---|---|
| `dotnet tool install -g <id>` | Install a tool globally for the current user |
| `dotnet tool install <id>` | Add a tool to the local manifest |
| `dotnet tool restore` | Install all tools listed in the local manifest |
| `dotnet tool update -g <id>` | Update a global tool to the latest version |
| `dotnet tool list -g` | List all globally installed tools |
| `dotnet tool list --local` | List tools in the local manifest |
| `dotnet tool uninstall -g <id>` | Remove a global tool |

### Pitfalls

**Forgetting `dotnet tool restore` in CI** is the most common cause of "command not found" errors for local tools. The manifest records the *intent* to use a tool; `dotnet tool restore` is what actually downloads and installs it. Add `dotnet tool restore` as an explicit step in your CI pipeline, typically right after `dotnet restore`.

**Global tools are not machine-wide.** A tool installed globally by one user is not visible to other users. In multi-user CI environments (or containers that change users between build steps), install tools globally in the same user context that will invoke them, or use local tools with a committed manifest instead.

**Global tool versions are user-pinned.** Running `dotnet tool update -g <id>` updates to the latest version for your user, which may differ from what a teammate has. For reproducible builds, prefer local tools with an explicit version pinned in the manifest.
