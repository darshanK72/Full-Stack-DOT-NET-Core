# Garbage Collection & Memory

## Why This Matters

Memory management is one of the most probed areas in .NET interviews because it separates developers who understand the runtime from those who merely use it. The GC is not invisible: every allocation decision affects collection frequency, pause duration, and heap fragmentation. Understanding the GC's internal model lets you write code that cooperates with the collector — lower latency, higher throughput, fewer out-of-memory incidents under load.

## Section 1: Generational GC — Core Model

### The Generational Hypothesis

The .NET GC is a **tracing, compacting, generational** collector. Its design rests on a single empirical observation called the **generational hypothesis**: most objects die young. Profiling across thousands of programs shows that the vast majority of allocations — temporaries, LINQ intermediates, loop variables, method-local objects — become unreachable within milliseconds of creation. By dividing the heap into generations and collecting young objects far more frequently than old ones, the GC avoids scanning the entire heap on every cycle. This delivers high throughput without the cost of a full collection on every pass.

### Generation 0 — The Allocation Nursery

All new small objects are allocated in **Gen 0**. Its budget is deliberately tiny (a few hundred kilobytes to a few megabytes depending on machine and GC mode). When Gen 0 fills, the GC triggers a Gen 0 collection: it identifies which objects in that small region are still reachable, promotes survivors to Gen 1, and reclaims the rest. Because it only scans a tiny fraction of the heap, a Gen 0 collection completes in under a millisecond. In a busy server application, Gen 0 can be collected hundreds of times per second with negligible pause impact.

### Generation 1 — The Buffer

**Gen 1** acts as a buffer zone between the short-lived Gen 0 and the expensive Gen 2. It holds objects that survived one Gen 0 collection but have not yet lived long enough to be considered long-lived. Collecting Gen 1 requires scanning both Gen 0 and Gen 1 regions. Survivors are promoted to Gen 2. The intent is to give the GC a second chance to collect medium-lived objects (objects that were still in use during one Gen 0 sweep but die shortly after) before they reach the costly Gen 2.

### Generation 2 — Long-Lived Objects

**Gen 2** holds objects that have survived at least one Gen 1 collection: singletons, static-field-referenced objects, long-running caches, and the managed wrappers around connection pools. A Gen 2 (full) collection pauses all managed threads and scans the entire heap. It is the most expensive GC event in normal operation. Minimizing promotions to Gen 2 — by eliminating mid-lived objects that outlive their Gen 0 collection but are not truly long-lived — is one of the most impactful GC tuning moves available.

### Large Object Heap (LOH)

Objects at or above **85,000 bytes** bypass the generational heaps entirely and land on the **Large Object Heap**. The LOH is collected only during Gen 2 collections. Crucially, it is **not compacted by default** — moving a 10 MB object would require copying all its bytes and updating every reference to it, which is too expensive in the general case. The absence of compaction leads to fragmentation over time: as large objects are allocated and freed, the heap becomes a patchwork of used and free spans. You can request a one-time compaction of the LOH before the next Gen 2 collection by setting `GCSettings.LargeObjectHeapCompactionMode = GCLargeObjectHeapCompactionMode.CompactOnce`. After that collection, the mode resets to `Default` (no compaction).

### Pinned Object Heap (POH) — .NET 5+

Before .NET 5, pinning an object (making it immovable so a native pointer into it stays valid) in Gen 0 caused fragmentation: the pinned object acted as an immovable island in an otherwise compactable region, leaving gaps that could never be filled. The **Pinned Object Heap** (POH) solves this by giving pinned objects their own isolated heap that is never compacted by design. Network I/O buffers and interop scenarios that require a stable memory address should use `GC.AllocateArray<T>(length, pinned: true)` to place them on the POH, completely isolating their fragmentation from the generational heaps.

### Promotion Mechanics

When a Gen 0 collection runs, any live object in Gen 0 is **promoted** to Gen 1 — its memory is copied into the Gen 1 region and all references to it are updated. When a Gen 1 collection runs, survivors of Gen 1 are promoted to Gen 2. An object never skips a generation in normal flow. The cost of promotion is not zero: every promoted object occupies Gen 1 or Gen 2 budget, contributes to triggering deeper (more expensive) collections sooner, and may eventually trigger a full Gen 2 collection.

### Heap Layout — ASCII Diagram

```
  Managed Heap
  ┌──────────────────────────────────────────────────────────────────┐
  │  Gen 0                │  Gen 1          │  Gen 2                 │
  │  (nursery)            │  (buffer)       │  (long-lived)          │
  │  ~KB–few MB           │  ~2–8 MB        │  unbounded             │
  │  collected very often │  collected less │  full GC, expensive    │
  │  new allocations→here │  survivors←Gen0 │  survivors←Gen1        │
  └──────────────────────────────────────────────────────────────────┘
  
  Large Object Heap (LOH)  — objects ≥ 85,000 bytes; NOT compacted by default
  ┌──────────────────────────────────────────────────────────────────┐
  │  [obj 1: 200 KB] [free] [obj 2: 1 MB] [free] [obj 3: 512 KB]    │
  │         ↑ fragmentation gap        ↑ fragmentation gap           │
  └──────────────────────────────────────────────────────────────────┘
  
  Pinned Object Heap (POH) — .NET 5+; pinned interop/I/O buffers; never compacted
  ┌──────────────────────────────────────────────────────────────────┐
  │  [pin buf 1] [pin buf 2] [pin buf 3]  ...                        │
  └──────────────────────────────────────────────────────────────────┘
```

| Heap / Gen | Typical budget | Collection frequency | Compacted? | Notes |
|---|---|---|---|---|
| Generation 0 | ~256 KB – few MB | Very frequent (milliseconds) | Yes | All new small allocations land here |

## Section 2: GC Phases — Mark, Plan, Relocate, Update

A GC collection is not a single atomic event. It proceeds through four conceptual phases. Understanding these phases explains what causes pauses, why references are never dangling after a GC, and how background GC can overlap with application execution.

### Phase 1 — Mark

The GC starts from a set of **GC roots** and traverses every reachable object reference, marking each live object. Any object not reached by this traversal is dead — its memory can be reclaimed.

GC roots are:
- **Static fields** — class-level fields referenced through the loader's type data
- **Local variables on active thread stacks** — the JIT reports live local reference variables at every safe-point (GC safe-points are positions in code where the stack layout is known to the runtime)
- **CPU registers** — the JIT tracks which registers hold live references at each safe-point
- **GC handles** — explicit handles created via `GCHandle.Alloc()` (strong, pinned, weak, or weak-tracking-resurrection)

The mark phase must be complete and consistent before any memory is reclaimed. For Gen 0 and Gen 1 collections, all managed threads are suspended during marking. For Gen 2 background GC, marking runs concurrently with application threads, with occasional short pauses to handle reference writes that occurred during the concurrent scan (the **write barrier** mechanism records these).

### Phase 2 — Plan

After marking, the GC assesses whether compaction is cost-effective. If the live objects are densely packed with little fragmentation, a **sweep-only** collection may suffice: the GC simply zeros out the dead spans and records them as free space, without moving any live object. Sweeping is far cheaper than compacting because no object copies are made and no references need updating. If fragmentation is high, the GC decides to compact.

### Phase 3 — Relocate / Compact

In a compacting collection, live objects are slid toward the low end of the heap to eliminate gaps. Each object is physically copied to its new address. The GC computes the new address for every live object during this phase. Object headers and the GC's internal data structures are updated.

### Phase 4 — Update References

After relocation, every managed reference in every live object, on every thread stack, and in every CPU register must be updated to point to the new addresses computed in Phase 3. This is the step that makes the heap fully consistent after compaction — no dangling pointer is possible because the GC controls all managed references and updates them atomically before resuming threads.

### Stop-the-World vs Background

- **Gen 0 and Gen 1** collections: all managed threads are suspended for the entire duration — mark, plan, relocate, update. Because these regions are small, pauses are short (sub-millisecond to low milliseconds).
- **Gen 2 (full) foreground collection**: all threads suspended for the entire duration — can cause multi-hundred-millisecond pauses on large heaps.
- **Gen 2 background GC** (default): the mark phase runs on a dedicated background thread concurrently with application execution. Gen 0 and Gen 1 collections can proceed normally during background Gen 2 marking. The final phases that must be stop-the-world are shorter because most marking work is already done.

### Write Barrier

The write barrier is a small piece of code the JIT inserts around every managed reference store. It records that a reference in a long-lived object now points to a younger object. The GC uses this **card table** to avoid re-scanning all of Gen 2 to find references into Gen 0 during a Gen 0 collection — it only re-scans the "cards" (fixed-size heap regions) that the write barrier flagged as dirty. The write barrier is a key reason that generational collection is efficient even when Gen 2 is large.

## Section 3: GC Modes — Workstation vs Server

### Workstation GC

**Workstation GC** uses a single GC thread. When a collection triggers, all application threads are paused, the single GC thread performs the collection, then all threads resume. It is designed for desktop, console, and GUI applications where low memory footprint and responsiveness to the user matter more than raw throughput. Heap segments are small, individual GC pauses are short, and memory is returned to the OS more aggressively.

### Server GC

**Server GC** creates one GC heap and one GC thread per logical CPU core. Each core allocates into its own Gen 0 segment and collects its segment independently. Collections across all heaps are coordinated so that a Gen 0 collection on core 0 and core 1 happen together. This parallelism multiplies throughput dramatically — the heap is effectively N times larger and collected N times faster — but baseline memory usage is significantly higher. ASP.NET Core enables Server GC by default, detected via the presence of a server hosting environment.

Configure it in `runtimeconfig.json`:
```json
{ "configProperties": { "System.GC.Server": true, "System.GC.Concurrent": true } }
```

### Background GC

Background GC is orthogonal to the Workstation/Server split. It controls how Gen 2 (full) collections behave. In **background GC** mode (default since .NET 4), the mark phase of a Gen 2 collection runs on a dedicated background thread. Application threads continue running during this phase. Gen 0 and Gen 1 foreground collections can still occur during the background Gen 2 mark. Only the brief final phases (relocate and update references) require a full stop-the-world. This dramatically reduces the maximum pause time caused by full GC on large heaps. In **non-concurrent (blocking) GC** mode, every Gen 2 collection fully stops all threads.

### GCSettings.LatencyMode

`GCSettings.LatencyMode` provides runtime control over how aggressively the GC suppresses Gen 2 collections. Changing the latency mode is a temporary measure for latency-sensitive sections; the mode should always be restored in a `finally` block.

| LatencyMode | Gen 2 behaviour | Typical use case |
|---|---|---|
| `Interactive` | Normal — full GC allowed | Default for most applications |
| `Batch` | Maximum frequency allowed | Offline ETL, batch processing, benchmarks |
| `LowLatency` | Gen 2 suppressed during short burst | Brief trading spikes, game frame boundaries |
| `SustainedLowLatency` | Gen 2 mostly avoided for extended period | Ongoing real-time audio/video processing |
| `NoGCRegion` | GC paused until reserved budget exceeded | Ultra-short critical sections (must call `EndNoGCRegion()`) |

### GC Mode Comparison Table

| GC Mode | GC Threads | Max Pause | Throughput | Memory | Best for |
|---|---|---|---|---|---|
| Workstation + Background | 1 | Low (concurrent Gen 2) | Moderate | Low | Desktop, console, CLI |
| Server + Background | 1 per core | Very low | High | High | ASP.NET Core, microservices |
| Workstation, no Background | 1 | High (blocking Gen 2) | Low | Low | Rarely desired |
| `Batch` LatencyMode | — | High (GC unrestricted) | Maximum | Varies | Offline batch workloads |
| `SustainedLowLatency` | — | Minimal | Reduced | Grows over time | Real-time streaming |

## Section 4: Finalizers — The Safety Net

### What a Finalizer Is

A finalizer is declared with the `~ClassName()` destructor syntax. The C# compiler compiles it into an override of `Object.Finalize()`. It is the last-chance hook to release unmanaged resources — native handles, COM objects, manually allocated native memory — in the event that the caller forgot to call `Dispose()`. The critical word is **last-chance**: the finalizer is a safety net, not a primary cleanup mechanism.

### The Two-Pass Finalization Protocol

When the GC identifies an object as unreachable, if that object has a registered finalizer it does **not** immediately reclaim the memory. Instead:

1. **First GC — finalization queue**: the GC moves a reference to the object onto the **finalization queue** and marks the object as "not yet collected." The object is effectively resurrected for the purpose of running its finalizer. If the object was in Gen 0, it is now promoted to Gen 1 (or Gen 2) — it has survived a GC cycle purely because it has a finalizer.
2. **Finalizer thread**: a dedicated system thread runs continuously, draining the finalization queue by calling each object's `Finalize()` method. This is asynchronous and non-deterministic — you have no control over when the finalizer thread runs.
3. **Freachable queue**: after `Finalize()` completes, the reference moves to the "freachable queue." The object is now truly unreachable again.
4. **Second GC**: on the next collection, the GC reclaims the memory. The object has survived at least one and sometimes two extra GC cycles.

### The Cost of Finalizers

Every class with a finalizer contributes to GC pressure in two ways. First, the object itself survives at least one extra collection cycle, occupying heap memory longer than necessary and potentially being promoted to an older (more expensive) generation. Second, the finalizer thread is a single-threaded bottleneck — if finalizers are slow or numerous, they create a queue backlog that delays memory reclamation and may eventually cause an `OutOfMemoryException` even though objects are logically unreachable.

### GC.SuppressFinalize and GC.ReRegisterForFinalize

`GC.SuppressFinalize(this)` removes an object from the finalization queue. When called inside `Dispose()`, it tells the GC "this object was properly cleaned up; skip the finalizer." This is the standard practice in the dispose pattern: a properly disposed object avoids the entire two-pass overhead. `GC.ReRegisterForFinalize(this)` re-adds an object to the finalization queue after it has been suppressed or after its finalizer has already run. This enables **object resurrection** — a rare pattern where a finalizer deliberately makes the object reachable again (by, for example, storing `this` in a static field) and then re-registers so the finalizer can run again later. Resurrection should be avoided in almost all application code.

### Hard Rules

- Never rely on finalizer timing for correctness. A database connection closed in a finalizer may not be closed for seconds, minutes, or never (if the process exits with threads aborted).
- Never throw an exception inside a finalizer. In .NET, an unhandled exception in a finalizer terminates the process.
- Never access other managed objects inside a finalizer with `disposing = false`. Those objects may have already been finalized. Only unmanaged resource handles are safe to access from a finalizer.
- Always call `GC.SuppressFinalize(this)` at the end of `Dispose()`.

### Finalization Queue Diagram

```
Normal object (no finalizer):
  Object unreachable → GC reclaims on same cycle ✓

Object with finalizer:
  Object unreachable
       │
       ▼
  [Finalization Queue]  ← GC places reference here instead of collecting
       │
       ▼  (finalizer thread runs asynchronously)
  Finalizer() runs
       │
       ▼
  [Freachable Queue]
       │
       ▼  (next GC cycle)
  Memory reclaimed  ← costs 1+ extra GC cycles

With GC.SuppressFinalize(this) called in Dispose():
  Dispose() called → object removed from finalization queue → GC reclaims on next cycle ✓
```

## Section 5: IDisposable — Deterministic Resource Cleanup

### The Problem Finalizers Cannot Solve

Finalizers are non-deterministic: you cannot know when they run. For resources that carry cost while held — database connections, file handles, network sockets, unmanaged memory — "eventually cleaned up" is not acceptable. `IDisposable` provides a deterministic, synchronous cleanup contract that the caller controls.

### The using Statement

The `using` statement is syntactic sugar for a `try/finally` block. The compiler guarantees that `Dispose()` is called in the `finally` clause regardless of whether the body exits normally, throws an exception, or hits a `return`. The modern `using var x = ...;` declaration form scopes the disposal to the enclosing block rather than requiring braces.

### IAsyncDisposable and await using

For resources that require asynchronous cleanup — flushing an async stream to a remote endpoint, closing a database connection that issues a `RESET` over the network — `IAsyncDisposable` exposes `DisposeAsync()` which returns a `ValueTask`. Consumed via `await using`, it composes naturally with async code without blocking a thread during cleanup.

### The Full Dispose Pattern

The full dispose pattern applies to classes that hold **unmanaged resources directly** (via `SafeHandle` or raw `IntPtr`) or that inherit from a base class that might be extended. It combines three components:

**Public `Dispose()` entry point:**
```csharp
Dispose(disposing: true); GC.SuppressFinalize(this);
```

**Protected virtual `Dispose(bool disposing)` — the real cleanup method:**
- If `disposing` is `true`: the call came from `Dispose()` — it is safe to access and dispose child `IDisposable` members because they have not been finalized.
- Whether or not `disposing` is `true`: release unmanaged handles. Unmanaged handles are always safe to release from any context.
- The `bool _disposed` guard makes the method idempotent: calling `Dispose()` a second time is a no-op.

**Finalizer `~ClassName()`:**
- Calls `Dispose(false)` — the safety net path.
- Only reached if the caller forgot to call `Dispose()`.
- With `GC.SuppressFinalize` in `Dispose()`, the finalizer is never called for properly-disposed objects.

### Why the Dispose(bool) Split Exists

The `disposing` flag solves a problem unique to the finalizer path. When the finalizer runs, other managed objects on the heap may have already been finalized by the same GC cycle. Calling `someOtherDisposable.Dispose()` from a finalizer could call a method on an already-finalized object, causing corruption or exceptions. The `disposing = false` path therefore touches only unmanaged handles (which are always safe to close directly) and never calls methods on other managed objects.

### Dispose Pattern Structure

```
IDisposable (public contract)
    │
    └── Dispose()
            │
            ├── Dispose(disposing: true)   ← from user code / using statement
            │       ├── if (disposing): release IDisposable children
            │       ├── always: release unmanaged handles
            │       └── _disposed = true
            │
            └── GC.SuppressFinalize(this)  ← prevents finalizer from running

Finalizer ~T()
    │
    └── Dispose(disposing: false)          ← safety net path
            ├── (skip managed children — they may be finalized already)
            ├── release unmanaged handles
            └── _disposed = true
```

### IDisposable for Pure Managed Resources

If a class holds only managed `IDisposable` children (streams, DbConnection, HttpClient) and no unmanaged handles directly, the simpler pattern applies: implement `Dispose()` directly, dispose the children, optionally add a finalizer only if there is genuinely a reason to need one (there usually isn't). Do not add a finalizer "just in case" — it adds GC overhead for no benefit.

### Rules

- `Dispose()` must be **idempotent**: calling it multiple times must not throw.
- `Dispose()` must not throw under normal conditions.
- After `Dispose()` is called, all other methods should throw `ObjectDisposedException` if they require the resource to be open.
- Never access `Dispose()`-managed state from a finalizer — use `SafeHandle` subclasses instead of raw `IntPtr` wherever possible; `SafeHandle` has its own finalizer and critical finalizer infrastructure built in.

## Section 6: Weak References & Memory Caches

### Strong References and the GC

Every normal field, local variable, or parameter that holds an object is a **strong reference**. As long as any strong reference to an object exists and is reachable from a GC root, the GC will never collect it. This is what you want for most objects. But for caches and event subscriptions, it is sometimes desirable to hold an object without preventing the GC from reclaiming it when memory pressure rises.

### WeakReference\<T\>

`WeakReference<T>` holds a reference to an object but tells the GC "you may collect this object even though I hold this reference." To access the target, call `TryGetTarget(out T target)`. If the object is still alive it returns `true` and sets `target` to the object. If the object was collected it returns `false` and sets `target` to `default`. You must always check the return value; the pattern is:

```csharp
if (weak.TryGetTarget(out var obj)) { /* use obj — it is alive here */ }
```

Once `TryGetTarget` returns `true`, the local variable `obj` is a strong reference, so the GC cannot collect the object for as long as `obj` is in scope. Work through the local variable, not through a second `TryGetTarget` call.

### Short vs Long Weak References

The default `WeakReference<T>` constructor creates a **short weak reference**: the object is eligible for collection at any normal GC, before its finalizer runs. Passing `trackResurrection: true` creates a **long weak reference**: the object can survive until after its finalizer has run (it tracks through the finalization queue). Long weak references are needed in rare resurrection patterns. For ordinary caches, use short weak references.

### ConditionalWeakTable\<TKey, TValue\>

`ConditionalWeakTable<TKey, TValue>` is a dictionary whose keys are held by weak reference. An entry automatically disappears when the GC collects the key object — no manual cleanup required. It is used by the runtime itself extensively, and it is the correct mechanism for attaching per-object metadata without leaking memory. A regular `Dictionary<object, TValue>` would prevent the key object from ever being collected.

`ConditionalWeakTable` uses reference equality for key comparison (not `Equals`/`GetHashCode`), making it safe to use even when the key type has no sensible equality semantics. It is thread-safe for individual operations.

### Use Cases

- **Caches**: store computed results keyed by input objects; entries are evicted automatically when input objects are collected, preventing the cache from growing without bound.
- **Event aggregators**: a mediator or event bus can hold subscriber references as weak references so that subscribers are not kept alive purely by their event subscription.
- **Per-object extension data**: the runtime uses `ConditionalWeakTable` to attach async state machine state to objects without the framework retaining the object.

### Pitfall: TOCTOU Between TryGetTarget and Use

There is a conceptual time-of-check/time-of-use gap if you call `TryGetTarget`, check that it returned `true`, then call it again before using the object. Between the first and second call another thread could trigger a GC that collects the object (since your code held no strong reference between the two calls). Always capture the result of `TryGetTarget` in a local variable and work with that variable exclusively within the same stack frame.

## Section 7: Allocation-Free Patterns

### Why Allocation Rate Matters

The Gen 0 collection frequency is roughly proportional to the rate at which Gen 0 fills with new allocations. Every reduction in allocation rate on hot paths directly reduces GC collection frequency, reduces total pause time, and reduces CPU time spent in GC. For high-throughput services — protocol parsers, serializers, request handlers, tight loops — eliminating heap allocations on the critical path is one of the highest-leverage optimizations available.

### stackalloc — Stack-Allocated Buffers

`stackalloc T[N]` allocates a fixed-size block directly on the current thread's call stack. There is no heap involvement, no GC tracking, and no allocation overhead beyond the stack pointer decrement. The memory is automatically reclaimed when the method returns. In safe code, `stackalloc` must be used via `Span<T>`: `Span<byte> buf = stackalloc byte[64];`. The `Span<T>` is stack-only (it is a `ref struct`) so it cannot escape the declaring method — you cannot store it in a class field or pass it across an `await`.

The critical constraint is **stack size**. Each thread has approximately 1 MB of stack by default. Allocating more than a few kilobytes with `stackalloc` risks `StackOverflowException`. For buffers larger than a few hundred bytes, prefer `ArrayPool<T>`.

### ArrayPool\<T\>.Shared — Pooled Arrays

`ArrayPool<T>.Shared` is a thread-safe, shared pool of reusable arrays. `Rent(minimumLength)` returns an array from the pool (guaranteed to have at least `minimumLength` elements, but may be larger). `Return(array)` returns the array to the pool for the next caller. The array objects themselves are allocated once and reused thousands of times — the amortized per-use allocation cost approaches zero.

Two pitfalls:
- The returned buffer is **larger than requested** more often than not. Never use `buffer.Length` as your data length — use the `minimumLength` you passed to `Rent()`.
- The returned buffer may contain **stale data** from a previous use. Always initialize the portion you intend to read before processing it.

Always `Return()` in a `finally` block. A rental that is never returned causes the array to be garbage collected as a normal Gen 2 object, defeating the purpose of the pool.

### MemoryPool\<T\> — Async-Safe Pooled Buffers

`MemoryPool<T>.Shared.Rent(minimumLength)` returns an `IMemoryOwner<T>`, which is `IDisposable`. The owned memory is exposed as `Memory<T>`. Because `Memory<T>` is a regular struct (not a `ref struct` like `Span<T>`), it can be stored in fields and passed across `await` boundaries — making it suitable for async code that hands a buffer off between methods. Dispose the `IMemoryOwner<T>` when done to return the buffer to the pool.

### RecyclableMemoryStream — LOH-Free MemoryStream

`Microsoft.IO.RecyclableMemoryStream` (NuGet: `Microsoft.IO.RecyclableMemoryStream`) replaces the standard `MemoryStream` for large payloads. The standard `MemoryStream` grows its internal buffer exponentially; once the buffer crosses 85 KB it moves to the LOH, causing LOH fragmentation. `RecyclableMemoryStream` uses a pool of small fixed-size blocks instead, keeping all allocations below the LOH threshold and eliminating LOH pressure entirely. It is drop-in compatible with `MemoryStream` via base-class inheritance.

### Why Not Just Trust the GC?

The GC is highly optimized and Gen 0 collections are fast. For most application code, normal allocation patterns are fine. But there is a threshold where allocation rate genuinely dominates application behavior: high-frequency request handling, binary serialization, real-time signal processing. In those domains, reducing allocation rate from "many Gen 0 collections per second" to "virtually none" is the difference between 50 ms P99 latency and 2 ms P99 latency.

### Allocation-Free Pattern Comparison

| Pattern | GC pressure | Thread-safe | Async-safe | Max size | Primary pitfall |
|---|---|---|---|---|---|
| `stackalloc` + `Span<T>` | None | N/A (stack-local) | No (`ref struct`) | ~few KB | Stack overflow if oversized |
| `ArrayPool<T>.Shared` | Near-zero (amortized) | Yes | Yes (array) | Unlimited | Buffer larger than requested; stale data; must `Return()` |
| `MemoryPool<T>.Shared` | Near-zero (amortized) | Yes | Yes (`Memory<T>`) | Unlimited | Must dispose `IMemoryOwner<T>`; same stale-data risk |
| `RecyclableMemoryStream` | Near-zero (no LOH) | No (per-instance) | Yes | Effectively unlimited | Requires NuGet package; must dispose |
| `Span<T>` (over existing buf) | None | N/A | No | Existing buffer | Cannot cross `await`; cannot store on heap |
| `Memory<T>` (over existing buf) | None | N/A | Yes | Existing buffer | No bounds enforcement at the `Memory<T>` level |

## Quick Reference

### GC Generation Thresholds and Collection Cost

| Generation | Typical budget | Objects it holds | Promotion target | Relative cost |
|---|---|---|---|---|
| 0 | ~256 KB – few MB | All new small allocations | Gen 1 (survivors) | Very low |
| 1 | ~2–8 MB | Survivors of one Gen 0 | Gen 2 (survivors) | Low |
| 2 (full GC) | Unbounded | Long-lived objects, statics, caches | Stays in Gen 2 | High |
| LOH | Unbounded | Objects ≥ 85 KB | None (no promotion) | High (Gen 2 only) |
| POH | Unbounded | Pinned I/O / interop buffers | None | High (Gen 2 only) |

| Value | Gen 2 behaviour | Restore needed? | Use case |
|---|---|---|---|
| `Interactive` | Normal — full GC allowed | Default | General-purpose applications |
| `Batch` | Unrestricted — maximum allowed | Yes | Offline batch, ETL, benchmarks |
| `LowLatency` | Suppressed — short bursts only | Yes | Brief latency-critical windows |

### Full Dispose Pattern Template

```csharp
class MyResource : IDisposable
{
    private bool _disposed;

    public void Dispose()
    {
        Dispose(disposing: true);
        GC.SuppressFinalize(this);
    }

    protected virtual void Dispose(bool disposing)
    {
        if (_disposed) return;
        if (disposing)
        {
            // Safe: release managed IDisposable children here
        }
        // Always: release unmanaged handles (SafeHandle, IntPtr, etc.)
        _disposed = true;
    }

    ~MyResource() => Dispose(disposing: false); // Safety net only
}
```

Key rules:
- Call `GC.SuppressFinalize(this)` in `Dispose()` to skip the two-pass finalization cost
- `Dispose()` must be idempotent — `_disposed` guard prevents double-release
- `Dispose(false)` from finalizer: skip managed children, only release unmanaged handles
- `Dispose()` must not throw under normal conditions
- All other public methods should check `_disposed` and throw `ObjectDisposedException`

### Finalization Lifecycle

| Event | What happens | GC cost |
|---|---|---|
| Object becomes unreachable (has finalizer) | Moved to finalization queue — NOT collected | Object survives; may promote to Gen 1/2 |
| Finalizer thread processes queue | `Finalize()` called asynchronously | Delay: non-deterministic |
| Post-finalization | Object moved to freachable queue | Now truly unreachable again |
| Next GC | Memory reclaimed | Object costs 1+ extra GC cycles |
| `GC.SuppressFinalize(this)` called | Removed from finalization queue | Collected on next normal GC — no extra cycles |

### Allocation-Free API Quick Comparison

| API | Allocates? | Async? | Notes |
|---|---|---|---|
| `stackalloc T[N]` + `Span<T>` | No (stack) | No | Scope-limited; ≤ few KB |
| `ArrayPool<T>.Shared.Rent()` | Once, then pooled | Yes | Must `Return()` in `finally`; buffer may be oversized |
| `MemoryPool<T>.Shared.Rent()` | Once, then pooled | Yes | Returns `IMemoryOwner<T>`; dispose to return |
| `RecyclableMemoryStream` | No LOH | Yes | Replaces `MemoryStream` for large payloads |

### Common Finalization Pitfalls

- Finalizers run asynchronously — never use them for deterministic resource release
- Throwing in a finalizer terminates the process
- Accessing other managed objects from a finalizer — they may already be finalized
- Not calling `GC.SuppressFinalize(this)` in `Dispose()` — object pays two-pass overhead for no reason
- Long-running finalizers creating a backlog on the single finalizer thread — can cause `OutOfMemoryException`
- Not pairing `GC.AddMemoryPressure` with `GC.RemoveMemoryPressure` — GC sees artificially inflated pressure permanently

### Key GC APIs at a Glance

| API | Purpose | When to use |
|---|---|---|
| `GC.CollectionCount(gen)` | Collection count per generation since start | Benchmarks, diagnostics |
| `GC.GetTotalMemory(false)` | Approximate managed heap bytes | Rough memory snapshots |
| `GC.GetTotalAllocatedBytes()` | Cumulative bytes allocated | Allocation-rate profiling |
| `GC.GetGCMemoryInfo()` | Full GC stats: heap size, fragmentation, pause | Health checks, diagnostics |
| `GCSettings.IsServerGC` | Whether Server GC is active | Read-only at runtime |
| `GCSettings.LatencyMode` | Get/set GC aggressiveness | Latency-critical sections |
| `GC.TryStartNoGCRegion(size)` | Suppress GC for reserved budget | Ultra-short critical sections |
| `GC.EndNoGCRegion()` | End NoGCRegion | Always call after `TryStartNoGCRegion` |
| `GC.AddMemoryPressure(n)` | Signal large unmanaged allocation | When holding unobserved native memory |
| `GC.RemoveMemoryPressure(n)` | Signal unmanaged memory freed | In `Dispose`/finalizer |
| `GC.AllocateArray<T>(n, pinned:true)` | Allocate to Pinned Object Heap | I/O buffers, interop |
| `GC.SuppressFinalize(this)` | Remove from finalization queue | Always in `Dispose()` |
| `GC.ReRegisterForFinalize(this)` | Re-add to finalization queue | Resurrection patterns only |
