## 1. CLR Lifecycle — From Source to Execution

### The Full Pipeline

Every C# program moves through four distinct phases before a single CPU instruction executes. Understanding each phase is the foundation for reasoning about startup latency, memory layout, deployment choices, and runtime constraints.

```
  C# Source (.cs files)
         |
         |  Roslyn compiler  (csc / dotnet build)
         v
  IL Assembly  (.dll or .exe  — a PE file)
  +------------------------------------------+
  |  IL bytecode  |  Metadata  |  Manifest   |
  +------------------------------------------+
         |
         |  CLR loader — validates IL, resolves referenced assemblies,
         |               enforces type safety, builds vtables,
         |               registers GC roots
         v
  Loaded Assembly in memory
  (types resolved, method stubs installed)
         |
         |  RyuJIT — fires on the FIRST call to each method
         |           (lazy, per-method, not per-assembly)
         v
  Native machine code  (x64 / ARM64 / x86)
  (cached in memory for the lifetime of the process)
         |
         v
  CPU executes directly
  (GC, SEH, ThreadPool, SynchronizationContext active throughout)
```

### Phase Details

**Phase 1 — Roslyn compilation.** The C# compiler (`csc`, or `dotnet build` which invokes it) reads source, performs semantic analysis, and emits **Intermediate Language (IL)**, also called MSIL or CIL. IL is a stack-based, CPU-neutral bytecode — it describes *what* the program does without committing to any hardware instruction set. The compiler also emits **metadata**: a structured description of every type, method, field, parameter, generic constraint, and custom attribute. Both IL and metadata are embedded in the same PE file (portable executable — the `.dll` or `.exe`). The PE file also contains a **manifest** listing the assembly's identity, version, culture, and its references to other assemblies.

**Phase 2 — CLR loading.** When the host (`dotnet.exe`, `corerun.exe`, or a custom host using the hosting API) starts a process, it bootstraps the CLR inside that process. The CLR is **not a process** — it is a runtime engine embedded inside the host process. The CLR loader then reads the PE assembly, validates the IL for structural soundness (correct stack usage, no invalid jumps), resolves all referenced assemblies, and builds the in-memory type system: vtables for virtual dispatch, interface dispatch tables, and GC root registration for static fields.

**Phase 3 — JIT compilation.** Methods are compiled lazily. The loader initially installs a stub pointer for each method. On the first call, the stub traps into the JIT compiler (`RyuJIT`), which translates that method's IL into native machine code for the current CPU. The stub pointer is then replaced with the address of the native code. All subsequent calls bypass the JIT entirely.

**Phase 4 — Native execution under CLR supervision.** The native code runs directly on the CPU, but the CLR continues to operate alongside it: the garbage collector manages heap memory, structured exception handling intercepts hardware faults and software throws, the thread pool manages worker threads, and the synchronization context controls continuation scheduling.

### CLR Responsibilities

The CLR is responsible for six cross-cutting concerns that run continuously after the process starts:

- **Memory management** — generational garbage collector tracks all managed heap objects; frees unreachable objects; compacts the heap to eliminate fragmentation
- **Type safety enforcement** — prevents invalid casts, out-of-bounds array accesses, and null dereferences from corrupting memory; validated at both IL load time and JIT time
- **Exception handling** — maps OS Structured Exception Handling (SEH) to C# `try/catch/finally/when` constructs; manages the stack unwind protocol
- **JIT compilation** — per-method lazy translation of IL to native code via RyuJIT; tiered re-compilation for hot methods
- **Thread management** — the `ThreadPool` schedules work items and async continuations; `SynchronizationContext` controls on which thread continuations are dispatched
- **Metadata resolution** — powers reflection (`Type`, `MethodInfo`, `FieldInfo`), attribute inspection, generic instantiation, and assembly binding

### Key Structural Facts

- Metadata and IL **co-exist in the same PE file**. When the CLR loads an assembly, it maps both into memory simultaneously. Reflection APIs read metadata; the JIT reads IL.
- The CLR is **hosted inside a process** — it does not create a new OS process. `dotnet.exe` is merely a thin native launcher that loads the CLR DLL (`coreclr.dll`) and delegates execution to it.
- The managed heap, GC roots, and JIT code cache all live in the same OS virtual address space as unmanaged code in the same process.

## 2. JIT Compilation — How It Works

### What JIT Means

JIT = Just-In-Time. Methods are compiled from IL to native code **on their first call**, then the native code is cached in memory for the lifetime of the process. Every subsequent call to the same method executes the cached native code directly — zero JIT overhead for warm calls.

RyuJIT is the current JIT compiler in CoreCLR. It replaced the older JIT64 (used in .NET Framework 4.x) and is written in C++. RyuJIT targets x64, x86, ARM64, and ARM32 and is the JIT compiler for all modern .NET versions (.NET Core 1.0+, .NET 5+, .NET 10).

### Two-Tier JIT (Tiered Compilation)

Tiered Compilation, enabled by default since .NET Core 3.0, gives RyuJIT two modes of operation for each method:

**Tier 0 — quick, unoptimized JIT**
- Fires on the first call to a method
- Optimizations are minimal: no inlining, no loop unrolling, simple register allocation
- The goal is to minimize JIT latency — generating *any* working native code fast so the program starts quickly
- Tier 0 code also instruments the method with a **call-count probe**: a tiny counter that increments on each method entry

**Tier 1 — full optimization JIT**
- Fires when a method's call count crosses the "hot" threshold (~30 calls by default)
- RyuJIT applies its full optimization suite: aggressive inlining, loop unrolling, escape analysis, strength reduction, dead-code elimination, register allocation
- The Tier 1 native code is compiled on a background thread, then **swapped in atomically** to replace the Tier 0 code
- From that point forward, all calls execute the fully-optimized Tier 1 code

**Why two tiers?**
- Methods called once (startup path, configuration code) benefit from fast Tier 0 — spending 3ms optimizing a method called once is wasteful
- Methods called thousands of times (hot loops, serializers, request handlers) benefit from Tier 1 — the up-front optimization cost is quickly recovered from the faster steady-state execution

```
First call
    |
    v
  Tier 0 compiles (fast, unoptimized)
  Installs call-count probe
    |
    v
  Executes Tier 0 native code
  Probe increments on each call
    |
    | call count >= threshold (~30)
    v
  Tier 1 compiles in background (slow, fully-optimized)
  Swaps Tier 0 code out atomically
    |
    v
  All future calls execute Tier 1 native code
```

### MethodImplOptions — Controlling JIT Behavior

The `[MethodImpl]` attribute lets you override the JIT's per-method decisions:

| `MethodImplOptions` | Effect | Typical use case |
|---|---|---|
| `NoInlining` | Prevents the JIT from inlining this method at any call site | Stack-trace–sensitive code; recursive methods; benchmarks needing stable frames |
| `AggressiveInlining` | Overrides the JIT's size threshold — hints it to inline even large method bodies | Hot-path micro-helpers where call overhead is measurable |
| `AggressiveOptimization` | Skips Tier 0 entirely — compiles at Tier 1 quality on the very first call | Startup-critical paths that must be fast from call one, not after warmup |
| `NoOptimization` | Disables all JIT optimizations for this method | Debugging sessions; forcing predictable code layout for low-level analysis |
| `Synchronized` | Wraps the method body in a `lock(this)` (instance) or `lock(typeof(T))` (static) | Legacy synchronization — prefer explicit `lock` blocks in modern code |

**Why `NoInlining` matters for stack traces.** The JIT inlines small callees by copying their body into the caller — the inlined method then has no stack frame of its own. If that method throws, the stack trace will not mention it. Marking a method `[MethodImpl(MethodImplOptions.NoInlining)]` guarantees it always appears as a named frame, which is essential for accurate exception logging and for recursive methods (inlining a recursive call would cause infinite inlining / stack overflow).

**Why `AggressiveInlining` can hurt.** Inlining increases code size at every call site. If an inlined method is called from many sites, it inflates the instruction cache footprint — the resulting i-cache pressure can more than offset the savings from eliminating the call overhead. Use sparingly on truly tiny, provably hot methods like simple property accessors or mathematical operations in tight inner loops.

## 3. Ahead-of-Time (AOT) Compilation

### The Problem JIT Leaves Unsolved

Even with Tiered Compilation, JIT-based deployment has two inherent costs:
1. **Startup latency** — every method on the startup path must be JIT-compiled before it runs
2. **CLR dependency** — the entire CLR (`coreclr.dll`, `System.Private.CoreLib.dll`, etc.) must be distributed with the app or pre-installed on the target machine

AOT compilation moves IL-to-native translation to **build time**, eliminating runtime JIT cost.

### ReadyToRun (R2R) — Partial AOT

R2R is built into `dotnet publish --runtime <rid>`. The SDK's crossgen2 tool compiles IL to native code for the target platform and embeds **both** the native code and the original IL inside the same assembly file. On startup, the CLR uses the pre-compiled native code instead of JIT-compiling from scratch. Because the IL is still present, the JIT can always fall back to re-compile any method that the native code doesn't cover (portability stubs, methods that were skipped during R2R publish, or methods that need re-optimization at Tier 1).

- Faster startup compared to pure JIT — the most expensive startup-path methods are already native
- No restrictions on reflection, dynamic code generation, or `Assembly.LoadFile`
- Binary is still CLR-dependent — the CLR and base class libraries must be present
- Larger file size (IL + native code together)

### NativeAOT — Full AOT

NativeAOT, enabled by `<PublishAot>true</PublishAot>` in the `.csproj`, is a complete ahead-of-time compilation: the entire program — application code, base class library, and a minimal runtime — is compiled to a single self-contained native binary. There is **no CLR, no JIT, and no IL at runtime**.

**What NativeAOT produces:**
- A standalone native executable (`.exe` on Windows, ELF on Linux, Mach-O on macOS)
- The binary embeds a small "mini-runtime" (GC, exception handling, minimal reflection support) but not the full CLR
- Near-instant startup — no JIT compilation, no assembly loading, no type system bootstrapping

**NativeAOT hard constraints:**

| Constraint | Reason |
|---|---|
| No `Assembly.LoadFile` or `Assembly.Load(byte[])` | No runtime assembly loader exists |
| No `System.Reflection.Emit` | No JIT to compile dynamically-emitted IL |
| No unconstrained `Type.MakeGenericType` at runtime | Generic instantiations must be known at publish time for the AOT compiler to generate code |
| No `Activator.CreateInstance(Type.GetType(string))` without root declarations | Trimmer removes types not reachable from known roots |
| `Expression.Compile` on arbitrary lambdas is unsupported | Compiling an expression tree requires a JIT |

**`RuntimeFeature.IsDynamicCodeSupported`** is the runtime guard for AOT-incompatible code paths. It returns `false` under NativeAOT and `true` under JIT or R2R. Library code that uses dynamic code generation must check this flag and provide a static alternative for AOT callers.

### AOT Mode Comparison Table

| Feature | Interpreter (Mono) | JIT (CoreCLR default) | ReadyToRun | NativeAOT |
|---|---|---|---|---|
| Compile step | None at publish | None at publish | `crossgen2` at publish | Full compile at publish |
| Startup time | Slow | Moderate | Fast | Fastest |
| Peak throughput | Low | Highest (after warmup) | High | High |
| Binary size | Small + runtime | Small + runtime | Larger (IL + native) | Self-contained |
| Reflection | Full | Full | Full | Constrained — roots declared at build time |
| Dynamic codegen | Full | Full | Full | None |
| CLR required at runtime | Yes (Mono) | Yes (CoreCLR) | Yes | No — mini-runtime embedded |
| Deploy model | Framework-dependent | Framework-dependent | Either | Self-contained only |
| IL present at runtime | Yes | Yes | Yes | No |

### When to Choose Each Mode

- **JIT (default)** — most applications; maximum flexibility; framework-dependent deployment acceptable
- **ReadyToRun** — server applications and desktop apps where startup time matters but reflection/dynamic code is needed; easiest migration
- **NativeAOT** — CLI tools, cloud functions, microservices, mobile/embedded targets; cold-start is critical; no dynamic plugin loading needed

## 4. Type Initialization — Static Constructors and beforefieldinit

### What Type Initialization Is

Before any static member of a type is accessed for the first time, the CLR must initialize that type's static state. This includes running field initializers and the static constructor (`.cctor`). The CLR guarantees that initialization runs **exactly once** per AppDomain, even when multiple threads race to be the first caller — the CLR serializes initialization on a per-type internal lock.

### The `beforefieldinit` Flag

The C# compiler emits a `beforefieldinit` flag in the IL metadata of a type to tell the CLR how strictly to time initialization:

**With `beforefieldinit` = true (no explicit static constructor):**
- The CLR may initialize the type at any point *before* the first access to a static member — but not necessarily *immediately* before
- The JIT can hoist initialization to an earlier, more convenient code-generation point
- Result: looser timing, better JIT optimization freedom, slightly faster steady-state code

**With `beforefieldinit` = false (explicit `static` constructor declared):**
- The CLR must initialize the type *immediately* before the first access to any member of that type
- Precise timing: no earlier, no later
- The JIT cannot hoist or reorder initialization across the boundary
- Result: stricter timing, slight performance cost, but side effects happen exactly when expected

```
TYPE INITIALIZATION TIMING

Type WITHOUT explicit static constructor:
  beforefieldinit = true
  JIT is free to initialize early (may happen before first observed access)

  ... other code ...  <-- initialization could happen here
  first_access();     <-- OR here
                      -- CLR guarantees: initialized by first_access, not necessarily at first_access

Type WITH explicit static constructor:
  beforefieldinit = false
  CLR MUST initialize immediately before first_access

  ...                 <-- initialization does NOT happen here
  first_access();     <-- initialization happens precisely here, then member is accessed
```

### Static Constructors and the Singleton Pattern

The thread-safe, lazy-initialization singleton relies on precise type initialization:

```csharp
// The explicit static constructor sets beforefieldinit = false.
// CLR guarantees: Instance is initialized exactly at first access to Singleton members.
// Thread-safe: CLR's per-type initialization lock prevents double initialization.
private static readonly Singleton _instance = new Singleton();
static Singleton() { }  // explicit static ctor — forces precise initialization timing
```

Without the explicit static constructor, `beforefieldinit` would be true and the JIT could initialize `_instance` earlier — technically still safe (it only fires once) but the timing is less predictable.

### Initialization Order Pitfall

The CLR makes **no guarantees** about the initialization order of different types relative to each other. If type `A`'s static constructor accesses type `B`, and type `B`'s static constructor accesses type `A`, the result is a circular initialization — one of the types will see the other in a partially-initialized state. This is undefined behavior and produces subtle, hard-to-diagnose bugs. Never create cross-type static constructor dependencies.

## 5. Exception Handling in the CLR

### The SEH Foundation

C# `try/catch/finally/when` is mapped at the IL level onto OS **Structured Exception Handling (SEH)**. The CLR registers SEH handlers when a method is JIT-compiled. When a throw occurs, the OS SEH mechanism notifies the CLR, which then implements the managed exception protocol on top.

### Stack Unwinding

When an exception is thrown, the CLR performs **stack unwinding** in two conceptual passes:

**First pass — searching for a handler:**
The CLR walks up the call stack without unwinding it. For each frame, it evaluates `catch` clause types (and `when` filters) in order. The first matching `catch` wins. Crucially, **`when` filters are evaluated in this pass** — before any unwinding has occurred. This means a `when` filter runs while the stack is still fully intact, which allows it to inspect ambient state that a `catch` body could not (stack frames below the throw site are still visible in a debugger at this point).

**Second pass — executing handlers and unwinding:**
Having found the target `catch`, the CLR unwinds the stack from the throw site up to the catch frame. During unwind, **every `finally` block** in every frame between the throw and the catch is executed in order, from innermost to outermost. `finally` blocks run regardless of whether a `catch` was found — even if the exception propagates all the way to the top of the call stack uncaught, `finally` blocks still execute.

```
Call stack at time of throw:

  [Frame 5] Method that threw                  <-- throw site
  [Frame 4] Intermediate method (has finally)  --> finally runs during unwind
  [Frame 3] Intermediate method (no handlers)
  [Frame 2] Method with matching catch         <-- handler found here
  [Frame 1] Application entry point

Unwind executes: Frame 5 finally (if any) -> Frame 4 finally -> Frame 3 finally
Then: Frame 2 catch block executes
Then: Frame 2 finally (if any) executes
Then: execution resumes after Frame 2's try/catch
```

### `catch when` — Exception Filters

`catch (ExceptionType ex) when (condition)` introduces an exception filter. The condition is evaluated during the **first pass** (before unwinding begins). Key behavioral differences from a plain `catch`:

- The filter **does not catch** the exception if the condition is false — the search continues up the stack
- The filter does not affect the stack trace — the throw site is preserved
- The filter can be used for selective handling without paying the cost of a `catch` that immediately rethrows
- If the filter expression itself throws, that exception is silently swallowed and the filter result is treated as `false`

### `throw` vs `throw e` — The Most Common Pitfall

```csharp
catch (Exception ex)
{
    throw ex;   // BAD  — creates a new throw point here; stack trace is reset to this line
}

catch (Exception ex)
{
    throw;      // GOOD — rethrows the current exception; original stack trace preserved
}
```

`throw ex;` does not "rethrow" in the CLR sense — it throws a new exception event from the current frame, replacing the original stack trace. The original call site is permanently lost. The bare `throw;` statement tells the CLR to re-raise the existing exception object without modifying its stack trace.

### `ExceptionDispatchInfo` — Rethrowing Across Boundaries

When an exception must be captured at one boundary and re-raised at another — crossing thread boundaries, storing exceptions in queues, rethrowing from async `Task` completions — use `ExceptionDispatchInfo`:

```csharp
// Capture: snapshot the exception including its current stack trace
ExceptionDispatchInfo edi = ExceptionDispatchInfo.Capture(ex);

// Later, on a different thread or in a different scope:
edi.Throw();   // re-raises with original stack trace; adds a "--- End of stack trace ---" marker
```

`ExceptionDispatchInfo.Throw()` does not reset the stack trace. The rethrow frame is appended after a separator marker, but the original frames — including the original throw site — are preserved.

### `AggregateException`

`AggregateException` wraps multiple exceptions from parallel or async operations. It appears naturally in `Task.Wait()`, `Task.WhenAll()`, and PLINQ. Key members:

- `InnerExceptions` — read-only collection of all wrapped exceptions
- `Flatten()` — recursively unwraps nested `AggregateException`s into a single flat instance; essential when parallel operations themselves spawn parallel operations
- `Handle(Func<Exception, bool>)` — calls the predicate for each inner exception; any exception for which the predicate returns `false` is re-thrown as a new `AggregateException`

### Exception Handling Summary

| Construct | When it runs | Stack trace effect | Notes |
|---|---|---|---|
| `catch (T ex)` | Second pass (during unwind) | No effect | Catches and handles |
| `catch (T ex) when (cond)` | First pass (before unwind) | No effect | Filters without catching if false |
| `finally` | During unwind, every frame | No effect | Always runs (except `FailFast`) |
| `throw;` | Re-raise current exception | Preserved | Correct rethrow |
| `throw ex;` | New throw from current frame | Reset to current frame | Destroys original trace |
| `ExceptionDispatchInfo.Throw()` | Re-raise captured exception | Preserved + marker appended | Correct async/thread rethrow |

## 6. Thread & Execution Context

### `ExecutionContext` — Ambient State Flow

`ExecutionContext` is an ambient container managed by the CLR that flows automatically across async continuations. At every `await` point, the current `ExecutionContext` is **captured**. When the continuation resumes (on whichever thread picks it up), the CLR **restores** that `ExecutionContext` before running the continuation body. This ensures that ambient values set before an `await` are still accessible after it, regardless of thread.

The `ExecutionContext` carries:
- `AsyncLocal<T>` values (described below)
- Security context (impersonation token under Windows)
- `CultureInfo.CurrentCulture` and `CurrentUICulture`
- Any other values stored via the internal `AsyncLocal<T>` machinery

### `AsyncLocal<T>` — Unidirectional Context Flow

`AsyncLocal<T>` provides ambient values that flow **down** into child async operations using **copy-on-write semantics**:

```
Parent sets ambient.Value = "parent"
        |
        v
  Child task starts --> sees ambient.Value = "parent"  (copy flowed down)
        |
        | child sets ambient.Value = "child-modified"
        v
  Child's subtree sees "child-modified"
  Parent's scope still sees "parent"  (child's write is scoped to the child's context copy)
```

Changes made to an `AsyncLocal<T>` in a child scope are **never visible** to the parent scope after the child completes. The CLR creates a new `ExecutionContext` snapshot for the child; the parent's snapshot is unchanged. This prevents accidental cross-contamination between concurrent async branches.

If you need bidirectional communication (parent to child AND child back to parent), store a shared reference type (e.g., a `ConcurrentBag<T>` or `List<T>`) in the `AsyncLocal<T>` and mutate its contents rather than replacing the `AsyncLocal<T>` value itself. The object reference flows down (copy of the reference, not the object), so both parent and child see mutations to the same object.

### `SynchronizationContext` — Controlling Continuation Scheduling

`SynchronizationContext` controls **where** async continuations are scheduled. The CLR captures the current `SynchronizationContext` at each `await` point and posts the continuation to it when the awaitable completes.

| Environment | `SynchronizationContext` installed | Continuation behavior |
|---|---|---|
| ASP.NET Core | `null` | Runs on any `ThreadPool` thread (efficient) |
| WinForms / WPF | `WindowsFormsSynchronizationContext` / `DispatcherSynchronizationContext` | Marshalled back to UI thread |
| MAUI | Platform-specific UI context | Marshalled back to UI thread |
| Console app | `null` | Runs on `ThreadPool` thread |
| `Task.Run` callback | `null` (context suppressed) | Runs on `ThreadPool` thread |

`ConfigureAwait(false)` instructs the awaiter **not** to capture the current `SynchronizationContext`. The continuation will run on a `ThreadPool` thread instead of being marshalled back to the UI thread (or whatever context was current). This is the correct default for library code, which should never assume a particular thread or context.

### The UI Thread Deadlock Pattern

This is one of the most common async mistakes:

```
UI thread calls .Result or .Wait() on a Task
  |
  | UI thread BLOCKS here, waiting for Task to complete
  v
Task continuation needs to marshal back to the UI thread (via SynchronizationContext)
  |
  | UI thread is blocked -- cannot process the marshal request
  v
DEADLOCK: Task waits for UI thread; UI thread waits for Task
```

The fix is always to `await` the task rather than blocking synchronously. In library code, use `ConfigureAwait(false)` so the continuation does not try to return to the UI thread at all.

### `ThreadPool` — Managing Worker Threads

The CLR `ThreadPool` manages a pool of OS threads that execute `Task` work items and async continuations. Key facts:

- Minimum and maximum thread counts are configurable via `ThreadPool.SetMinThreads` and `ThreadPool.SetMaxThreads`
- The pool uses a hill-climbing algorithm to adjust the thread count dynamically based on observed throughput
- `async/await` continuations (where `SynchronizationContext` is null) post to the `ThreadPool` via `ThreadPool.QueueUserWorkItem` internally
- Thread injection: when all pool threads are busy and no completion is observed for ~500ms, the pool injects a new thread (up to the maximum)
- Thread starvation: saturating the `ThreadPool` with blocking synchronous work while awaiting further `ThreadPool` tasks can cause a deadlock-like stall; prefer `await` over blocking

### Execution Context Summary

| Concept | What it is | Flows across await? | Direction |
|---|---|---|---|
| `ExecutionContext` | Container holding all ambient state | Yes — automatically captured and restored | N/A |
| `AsyncLocal<T>` | Ambient value scoped to async call chain | Yes — copy-on-write, flows down | Down only |
| `SynchronizationContext` | Controls which thread runs continuations | Yes — captured at await, used on resume | N/A |
| `CultureInfo` | Current culture for formatting | Yes — via `ExecutionContext` | Down only |
| Thread-local storage (`[ThreadStatic]`) | Value scoped to an OS thread | No — a different thread = a different slot | None |

### Exception Handling Pitfalls

- **`throw e` resets the stack trace.** Always use bare `throw;` inside a catch to preserve the original call site. Use `ExceptionDispatchInfo.Capture(ex).Throw()` when rethrowing across async or thread boundaries.

- **`catch when` filter is evaluated before unwinding.** The filter sees the full stack intact. If the filter throws, the exception is silently swallowed and the filter returns false — never throw in a filter.

- **`finally` is not a replacement for `IDisposable`.** `finally` guarantees execution during normal unwind, but not on `Environment.FailFast`, out-of-memory crashes, or process-level kills. Deterministic cleanup belongs in `Dispose`.

- **Static constructor timing surprise.** The `.cctor` fires on first type access, not on assembly load. Code expecting initialization side effects at startup must explicitly touch a static member to trigger the constructor.

- **`beforefieldinit` and lazy initialization.** A type without an explicit static constructor may be initialized earlier than expected because `beforefieldinit` is true. If precise initialization timing matters (e.g., side effects must fire at a specific moment), add an explicit `static` constructor.

- **Cross-type static constructor cycles.** If type `A`'s static constructor accesses type `B` and type `B`'s accesses type `A`, one type will see the other partially initialized. The CLR does not deadlock — it allows re-entrant type initialization — but the partially-initialized state produces incorrect behavior.

- **`AsyncLocal<T>` does not flow up.** A child task modifying an `AsyncLocal<T>` value cannot propagate that change back to the parent scope. Wrap a mutable reference type inside `AsyncLocal<T>` for bidirectional data sharing.

- **Blocking on `Task.Result` in GUI applications.** In WinForms/WPF/MAUI, the `SynchronizationContext` marshals continuations to the UI thread. If the UI thread calls `.Result` or `.Wait()`, the continuation that resolves the task never runs — classic deadlock. Always `await`, or use `ConfigureAwait(false)` in library code.

- **NativeAOT and unconstrained reflection.** Any `Type.GetType(string)`, `Assembly.LoadFile`, or open-ended `Activator.CreateInstance` path that is not statically discoverable will be trimmed away at publish time. Guard all such paths with `RuntimeFeature.IsDynamicCodeSupported` and provide a static fallback for AOT deployments.
