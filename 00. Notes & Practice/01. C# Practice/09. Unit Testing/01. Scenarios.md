## Question 1

A team merges a refactor that renames an internal helper. All 400 unit tests pass, but staging fails because checkout still cannot reach the payment gateway. The unit suite ran in eight seconds; the staging test took four minutes. Classify what likely passed vs what failed, and why speed alone is not enough to skip the slower check.

## Question 3

A developer writes a test that creates the service, calls `CalculateTotal`, then asserts the result — but all setup is mixed with the call and check in one block with no comments. Rewrite the three phases as labeled steps without changing behavior.

## Question 4

Your solution has `BillingApp.csproj` and `BillingApp.Tests.csproj`. A junior developer adds `[TestMethod]` classes directly inside the app project so Visual Studio shows tests in one place. Explain why tests belong in the separate project and what ships to production if they stay in the app assembly.

## Question 5

Tax brackets require verifying six income bands. Compare writing six nearly identical `[Fact]` methods vs one `[Theory]` with six data rows. When would `[MemberData]` beat `[InlineData]`?

## Question 6

Two test classes share a static `List<Order>` populated in a static constructor. Tests pass locally in Visual Studio but fail randomly in CI with wrong counts. Explain the parallelism interaction and one fix that keeps tests independent.

## Answers

### Question 1
Unit tests passed because they isolate small units with doubles — they never hit the real payment gateway (integration boundary). Staging failed on an integration/end-to-end path (network, config, or wiring). Fast unit tests catch logic regressions; slower integration tests catch seam failures. Both layers are needed.

### Question 2
Example: `Validate_NullOrEmptyPassword_ThrowsArgumentException` or `Validate_EmptyPassword_ThrowsArgumentException` — method/scenario/expected pattern.

### Question 3
**Arrange:** create service and inputs. **Act:** call `CalculateTotal`. **Assert:** compare result to expected. Separating phases clarifies which step failed.

### Question 4
Test frameworks and test-only packages must not ship to production. Separate test project references production code via `ProjectReference`; only app assembly deploys. Tests in app project bloat deployment and couple test code to release builds.

### Question 5
One `[Theory]` with six rows avoids duplication and reports failing row inputs. `[MemberData]` when rows need objects (lists, custom types) or computed values that cannot be `[InlineData]` literals.

### Question 6
xUnit runs test classes in parallel by default; shared mutable static state races. Fix: remove shared mutation, use instance fields reset per test, or use `[Collection]` to serialize classes sharing state (prefer independent tests).

### Question 7
Once per class → `IClassFixture<T>` injected in constructor. Same instance across multiple classes → `[CollectionDefinition]` + `ICollectionFixture<T>` + `[Collection("Name")]` on each class.

### Question 8
xUnit creates a new test class instance per test; constructor = per-test setup. Implement `IDisposable` for teardown (maps to `[TestCleanup]`). `[TestInitialize]`/`[TestCleanup]` are MSTest per-test hooks.

### Question 9
Stub or mock with `Returns(false)` for stock check suffices for cancellation outcome. To assert email never sent, use mock `Verify(..., Times.Never)` or fake with empty sent list — spy/mock verification behavior.

### Question 10
Over-mocking internal call order tests implementation, not business outcome. High maintenance on refactor; low value vs asserting invoice total and essential side effects only.

### Question 11
Arrange: mock email + inventory setups, construct SUT with `.Object`. Act: `PlaceOrder`. Assert: success + `Verify(SendConfirmation(...), Times.Once)` with expected args.

### Question 12
Regression on pricing undetected until production; refactors break thresholds silently; no living documentation of expected behavior; slower manual QA.

### Question 13
Framework `Assert.Throws` fails the test if exception type not thrown and avoids swallowing wrong exceptions in catch blocks. Cleaner, standard failure messages.

### Question 14
`List<LineItem>` is not a compile-time constant for `[InlineData]`; MemberData static property builds complex rows in code.

### Question 15
`[ClassInitialize]` static method sets/increments counter once. Each `[TestMethod]` reads counter ≥ 1. Do not increment in `[TestInitialize]` if proving class-level once.

### Question 16
Use `[Theory]` with `[InlineData]` and/or `[MemberData]`. Each row supplies arguments matching the theory method signature.

### Question 17
Unit tests in `*.Tests` with fast doubles; integration tests in separate project/folder (e.g. `*.IntegrationTests`). Naming, categories, or CI job filters separate fast vs nightly runs.

### Question 18
Verify after Act — you must invoke `ProcessPayment` first so the mock records calls. Verify-before-Act passes vacuously (zero calls) even if SUT is broken.

### Question 19
`It.IsAny` when exact parameter values are irrelevant to behavior under test (focus on Never/Once). Exact Setup when specific args drive branch logic being tested.

### Question 20
Red-green-refactor. Red: failing test proves bug. Green: minimal fix. Refactor: improve structure without changing behavior; tests guard regression.
