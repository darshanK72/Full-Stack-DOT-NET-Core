## Answers

### Question 1

Long-lived dedicated workers map to manually created `Thread` (ch01): explicit lifecycle, naming, foreground/background choice. Thread pool fits short bursts (ch02); async fits I/O (ch04). **Foreground** threads keep the process alive until they end even if Main returns; **background** threads do not — the CLR may terminate them abruptly on shutdown. For graceful shutdown, use cooperative cancellation and `Join`, not abort.

### Question 2

Thread entry points are `void`; no return channel (ch01). Collect via **shared state under lock** (list of results) or **callbacks/events**. Parent waits with `Join` or `Join(timeout)` before reading shared results.

### Question 3

**Thread pool** (ch02): reuses workers, avoids 5,000 create/teardown costs and memory for stacks. Manual threads pay OS/CLR startup overhead per line; pool queues work on existing workers. Independent CPU work with no shared mutation is ideal pool batch work.

### Question 4

**ManualResetEvent/CountdownEvent**: `CountdownEvent(N)` decrements per completion and blocks until zero (ch02) — fits N validations. A single `ManualResetEvent` is better for one-shot “all done” if you manually track count, but `CountdownEvent` is the direct N-signal pattern.

### Question 5

`Task` represents asynchronous **operation** with completion, status, exceptions, and continuations (ch03); easier composition than joining raw threads. **`Task.WhenAll`** waits for many order pipelines. `Task.Run` schedules CPU work on the pool; async/await layers on tasks for I/O (ch04).

### Question 6

**`TaskCompletionSource<T>`** (ch03). Second `TrySetResult` fails (task already completed); use `TrySet*` to avoid races. Bridge callback APIs to awaitable tasks.

### Question 7

**`SemaphoreSlim`** (ch03/ch04/ch06): limits concurrent picks to 2 via `Wait`/`WaitAsync` without locking unrelated resources. One big `lock` serializes everything and kills throughput.

### Question 8

Async I/O frees the thread during wait (ch04); thread pool threads can serve other work. `Task.Run` + `Sleep` still **blocks** a pool thread for the whole delay — wastes capacity under load. Async is for I/O-bound scalability; parallel/thread pool for CPU batches.

### Question 9

Library code should **`ConfigureAwait(false)`** (ch04) to avoid marshaling back to ASP.NET request context unnecessarily. Callers that **block** with `.Result`/`.Wait()` on a context that the async method tries to re-enter cause **deadlock** (classic ASP.NET sync-over-async). Console has no sync context — less critical but still good library hygiene.

### Question 10

UI events cannot be awaited by the framework; **`async void`** is the exception (ch04). Exceptions on async void crash the process/unobserved path — no task to catch. Services should return `Task`/`Task<T>` so callers await and handle faults.

### Question 11

Loop attempts with delay `base * 2^attempt` (ch04), pass `CancellationToken` into delay and API call. Give up after 4 failures — rethrow last exception. Do not retry indefinitely; respect cancel during backoff wait.

### Question 12

Wrap only `WriteAsync`/file flush in `await gate.WaitAsync()` … `Release()` in `finally` (ch04 only-one pattern). Metadata fetch runs concurrently; writes serialize — throughput better than one global lock around entire export.

### Question 13

**Helps** when per-item CPU work is substantial and data is in memory — scales with cores (ch05). **Hurts** when work per item is tiny (partition/schedule overhead dominates) or threads contend on one lock every iteration. 100k SKU math with minimal sharing fits parallel well.

### Question 14

`Interlocked` only supports int/long (ch05/ch06). Use **lock** around decimal merge or **thread-local sums** merged once per worker in `Parallel.For` localFinally callback.

### Question 15

**`Break()`** (ch05): no new iterations after lowest break index; in-flight work may complete. `Stop()` is more aggressive but still not instantaneous for running bodies.

### Question 16

`counter++` is load-add-store (ch06). Interleaving loses increments: two threads read same value, both write incremented-once value. Need `lock` or `Interlocked.Increment`.

### Question 17

Locking on **`this`** exposes private lock to external callers who might also lock your object (ch06). Deadlock: Thread1 `Transfer(A,B)` locks A then B; Thread2 `Transfer(B,A)` locks B then A. Use **dedicated private readonly sync root** and **consistent lock ordering** (e.g. by hash/id).

### Question 18

**`ReaderWriterLockSlim`** (ch06): multiple read locks, exclusive write. Call **`Dispose()`** when table lifetime ends (implements IDisposable).

### Question 19

Plain dictionary indexer assignment is not atomic as a check-then-act sequence (ch07). **`GetOrAdd`** atomically inserts or returns existing; factory **may run more than once** under race — factory must be idempotent/side-effect safe.

### Question 20

**`BlockingCollection<T>`** (ch07) over concurrent queue — bounded capacity blocks producers, consumers `TryTake`, `CompleteAdding` signals end of production.

### Question 21

(a) **Async** — I/O-bound, don't block threads waiting on network (ch04). (b) **Parallel** — CPU-bound in-memory batch (ch05). (c) **Dedicated Thread** — long-lived device pump with explicit lifecycle (ch01); not pool/async model for exclusive hardware loop.

### Question 22

**ValueTask** (preview ch04/Advanced): when result is often synchronous/cached, avoid allocating `Task` objects. **IAsyncEnumerable**: large or unbounded row streams — process with `await foreach` without loading entire dataset into memory (Advanced C# async streams).
